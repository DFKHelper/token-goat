# Contributing

Dev environment notes specific to this repo. Shared conventions for agents and contributors live in [`AGENTS.md`](AGENTS.md); this file collects the rough edges around the local toolchain.

## Setup

```bash
npm install
npm test                     # fast test suite
npm run typecheck            # type check
npm run lint                 # ESLint
```

## Lefthook (pre-commit / pre-push)

Lefthook runs lint, the typechecks (source, tests, VS Code extension), `npm audit signatures`, the VS Code extension tests, a secrets scan and `npm run test:guards` on `pre-commit`, the commit-message checks on `commit-msg`, and a focused test run on `pre-push` (below). After a pull, merge or rebase, the `post-merge` and `post-rewrite` hooks run `scripts/post-merge.mjs`, which reinstalls dependencies when `package-lock.json` changed, rebuilds `dist/token-goat.mjs`, stops the resident hook servers, restarts the worker, refreshes the harness shims and instructions, and triggers a reindex, so a running agent never keeps using a bundle the checkout has replaced. The steps after the build run only in the checkout the global `token-goat` package resolves to (`npm root -g`, realpath'd); in a linked worktree, or in a checkout that is not the active install (for example when a registry copy is what runs), the script rebuilds the bundle and stops, and when npm cannot say it syncs as before. It prints which of the two it took and why. `TG_POST_MERGE_SYNC=1` forces the full sync in a non-active checkout; it does not lift the linked-worktree stop.

On `pre-push` the Windows suite runs first and the WSL (Linux) suite follows only when lint, typecheck and the Windows suite passed and either `TG_PREPUSH_WSL=1` is set or the pushed commits change a path listed in `.lefthook-scripts/wsl-paths.txt` (process spawning, shell handling, paths, file locking, install and native loading, dependencies); `TG_PREPUSH_WSL=0` skips it whatever changed, a pushed range the hook cannot determine runs it, and CI still runs the full suite on Linux, macOS and Windows. The hook prints which case applied, a `legs:` timing line and the 20 slowest test files of each leg that ran. Each suite leg runs only part of the suite, within a time budget, so the whole hook, from start to exit, finishes within 10 minutes (600 s). For every pushed ref the hook takes the commits from the remote's sha to the local sha (`scripts/prepush-select.mjs`) and builds a priority list of test files: every test under `tests/guards` and, when anything under `src/` changed (or a doubt could reach it), the built-bundle command matrix (`tests/command_matrix_e2e.*`) are never cut; next come the files that failed in the last run and the test files changed in the range, each cheapest first. After them come the tests that import a changed module, nearest first (`scripts/prepush-graph.mjs` follows the relative imports of `src/`, `tests/` and `scripts/`; a test that imports the module itself comes before one that reaches it through another module). Tests are added while the estimated wall time stays within the leg's budget (`scripts/prepush-budget.mjs`: 330 s for the Windows leg and 180 s for the WSL leg, set by `PREPUSH_BUDGET_S` and `PREPUSH_WSL_BUDGET_S`, and 510 s for both together: the 600 s hook limit less 30 s of hook overhead and a 10% margin for the estimate's error; an override cannot raise a leg past what the total leaves). The estimate is the sum of the files' last measured durations over the worker count, with a measured calibration factor; a file never timed counts as the mean of the timed files. The durations are refreshed after every leg into `durations.json` beside `last-failed.json`. Whatever the budget cut is printed as `deferred to CI: N files (~S s)` followed by the list, so nothing is skipped silently. Tests the import graph cannot see come after the importers, from one static text scan of the tracked test files (`scripts/prepush-readers.mjs`): first the tests that name a changed path as text, then, when `src/` changed, the tests that read `src/` through `fs` and the tests that spawn the built bundle. They are cut by the budget like the importers and appear in the deferred list the same way. A push that changes only Markdown or files under `docs/` runs the guards and the tests that name the changed document, not the full suite; Markdown under `src/`, `tests/`, `scripts/`, `.github/` and `.lefthook-scripts/` still runs everything. A new branch is diffed from its merge base with `origin/main`. A pushed ref whose commit is already in a remote-tracking ref of the remote being pushed to (the name git gives the hook; every configured remote when it is unknown) (a tag of a commit that was pushed earlier) brings nothing new and adds no test files, so such a push runs only the guards and the files that failed last time; when git cannot say, the diff is used. When a suite leg fails, its failing test files are recorded under the git directory (`token-goat-prepush/last-failed.json`) and added to the next push's list until a leg passes. Any doubt no longer runs the full leg: the never-cut files and the built-bundle matrix run, the rest of the budget goes to the remaining tests (importers first, then the text readers of the changed paths, then the cheapest files), and the note names the doubt while the rest is printed as deferred to CI. The doubts are: no ref lines on stdin, a deleted remote ref, a new one with no merge base on `origin/main`, a pushed commit that is not the checked-out one (its tests run on the checked-out tree), a range git cannot list, an empty range, more than 200 changed paths, a test setup file or a module that reaches one, an import graph that cannot be read, a changed path outside the `src/` and `tests/` TypeScript and JavaScript modules and the documents above (scripts, config, `package.json`, the lock file, `tsconfig`, test setup, fixtures, hook scripts, workflows), a deleted `src/` module or test helper, a failure record that cannot be parsed (it is moved aside to `last-failed.json.corrupt` by the next write), or a red run that named no failing file. The full leg remains only for `PREPUSH_FULL=1` and for a test tree that git cannot list. When the failed and changed test files alone would exceed the budget (a test that takes minutes by itself), the rest of them is cut to the budget like any other file, listed as deferred to CI, and the note says how many were deferred; the guards and the matrix are never cut, and when they alone are over the budget the note says so. A budget override takes plain digits only; anything else is ignored and the note says so. The estimate is not trusted on a loaded host: each focused leg runs the guards and the matrix first, then the rest under a wall-clock deadline taken from the hook's real elapsed time (the WSL leg's deadline is the time left of the 600 s after the measured hook overhead and the margin, not an estimate of the Windows leg; `PREPUSH_DEADLINE_S=N` sets it by hand, capped like the budget overrides, and `0` stops the rest at once). At the deadline no further file starts, and every selected file that did not finish is printed as `deferred to CI: N files (wall-clock deadline reached (host load))` and is not recorded as green; the leg passes when every file that did finish passed. A test file already running at the deadline finishes, so the hook can overrun by that file's own time, which the margin covers. `PREPUSH_FULL=1 git push` forces the full suite on both legs, with no reuse and no deadline (the older `TG_PREPUSH_FULL=1` still works), and lint and typecheck always run in full. Skipping unrelated files is acceptable because `.github/workflows/ci.yml` runs the full suite on every push to `main` (Windows in 4 shards, Linux in 3, macOS in 3) and on every pull request, the deferred list is printed on every push, and a release only goes out on a green main CI.

A check or test file that already passed on identical bytes is not run twice (`scripts/prepush-green.mjs`). The `pre-commit` lint, typecheck, test typecheck and guards record a green result under the git common dir (`token-goat-prepush/green.json`, at most 32 entries, written by atomic rename), and `pre-push` skips the same checks, and the Windows-leg test files, that are green on the same key and prints what it reused. The key is a git tree id of the working tree made through a temporary index, so an edited, unstaged or untracked (non-ignored) file changes it, plus the leg, platform, node version, a hash of `node_modules/.package-lock.json`, a hash of the `TG_*`, `TOKEN_GOAT_*`, `NODE_OPTIONS`, `NODE_ENV`, `CI` and `TZ` environment (the `PREPUSH_*` knobs excluded) and, for the test legs, a hash of `dist/`. A failed run, or a tree that changed during the run, records nothing, and an unreadable record file counts as empty. The WSL leg never reuses a result. `PREPUSH_FULL=1` ignores the record so the full path stays a real full run, and `TG_PREPUSH_NO_REUSE=1` neither reads nor writes it.

`lefthook` is a devDependency and `npm install` runs `prepare` → `lefthook install`, so a fresh clone gets the hooks automatically. If `.git/hooks/pre-commit` is missing, run `npx lefthook install` — the guards below only protect you if the hook actually exists.

A commit that changes a `package-lock.json` needs a subject starting `chore(deps)`, `chore(release)` or `release`; the `commit-msg` hook refuses anything else, and `tests/guards/lock_changes_only_in_dependency_commits.test.ts` checks every unpushed commit. Do not merge a Dependabot lock pull request: close it and run `npm run deps:refresh`, which resolves the same packages locally behind the cooldown. `npm run deps:refresh -- --verify` checks that the lock agrees with its own dependency specs and that no Linux platform package lacks the `libc` its registry manifest declares (npm 11.6.2 strips it; a refresh puts it back; the libc check asks the registry, so it needs network access), and `npm run deps:refresh -- --audit-commit <sha>` prints what a commit changed in the lock and exits 1 for each package published inside the cooldown, each integrity the registry does not serve, and each inconsistency, each newly added install script and each platform package missing its libc (it asks the registry for package metadata, so it needs network access).

The `commit-msg` hook checks the message itself. It refuses AI attribution trailers, any name on the confidential denylist, and a hard-wrapped body: write each paragraph and each list item on one line and let the viewer wrap it, because GitHub and `git log` show a message exactly as written. It also refuses a verification checklist ("Why didn't a test catch this?", "Mutation check:", "Dogfood:") in place of a description; what was tested belongs in the tests. `tests/commit_msg_style.test.ts` and `tests/commit_msg_hook_denylist.test.ts` run the real scripts.

The pre-commit guards (`tests/guards/`) are pure-introspection invariants with no I/O: no bundle build, no SQLite DB, no git fixtures. They run in ~2s and exist to catch the *implemented-but-unregistered / unfunctional command* class before a commit lands, rather than discovering it later at push or in CI. Keep them fast — do not move the full suite, the built-bundle smoke tests, or the command matrix into pre-commit.

The heavy coverage stays on `pre-push` / CI: the full suite plus the built-bundle command matrix (`tests/command_matrix_e2e.*.test.ts`), which runs every registered command against the shipped `dist/token-goat.mjs`. The suite is occasionally racy on Windows under heavy disk pressure; the gating fact is CI on `origin/main`, so when the pre-push hook hangs intermittently it is reasonable to push with `--no-verify`.

### The index must never be allowed to grow unbounded

A second invariant now rides both tiers, because violating it took the tool down rather than degrading it: **stored index bytes must stay proportional to source bytes.** The JSON extractor once stored each top-level key's whole *source line* as its body; minified JSON puts every key on line 1, so a 1.5 MB file with 1142 keys stored 1.6 GB. `global.db` reached 2.9 GB, and reindexing that one file pushed enough bytes through the FTS delete triggers to hold SQLite's writer lock past db.ts's 15s `busy_timeout` — reaching users as `database is locked` and as multi-minute stalls during `token-goat index`.

The permanent defense is architectural, not per-language: every parsed symbol reaches the DB through exactly one `INSERT INTO symbols`, and that INSERT bounds the body at `MAX_SYMBOL_BODY_CHARS`. That makes an unbounded-body bug in *any* present or future extractor incapable of bloating the index. An over-cap body is stored **empty, not truncated** — `read_commands.ts`'s `resolveBody` re-slices an empty body from source over the symbol's line range, so the cap is lossless; a truncated body would be served as though complete.

- [tests/guards/symbol_body_bound.test.ts](tests/guards/symbol_body_bound.test.ts) (pre-commit) — asserts the choke point is still singular, still routed through `boundSymbolBody`, still elides rather than truncates, still capped below 1 MB, and that `resolveBody`'s empty-body fallback still exists.
- [tests/index_amplification_guard.test.ts](tests/index_amplification_guard.test.ts) (pre-push/CI) — drives pathological fixtures through the real pipeline and asserts stored bytes ≤ 4× file size. On the pre-fix parser it reports `1200.0x`.

If you add a language extractor, you do not need a new fixture — the choke point bounds you by construction. If you touch `writeParseResult`, `boundSymbolBody`, or `resolveBody`, assume you are touching this invariant.

## Linked worktrees that share `node_modules`

If a linked worktree's `node_modules` or `vscode-extension/node_modules` is a junction or symlink into another checkout, delete that link (`[System.IO.Directory]::Delete(path, $false)` in PowerShell) before `git worktree remove`: git follows the link and empties the other checkout's `node_modules`, which then looks like an empty directory from every worktree that links to it.

In a fresh linked worktree, install the VS Code extension's dependencies with `node scripts/install_vscode_extension_deps.mjs`: it runs `npm ci --ignore-scripts` inside `vscode-extension` and runs no lifecycle scripts.

## Git Bash / MSYS path mangling

Git Bash (the shell that ships with Git for Windows) rewrites POSIX-looking paths that start with `/` into Windows paths, so a call like `gh api /repos/DFKHelper/token-goat/...` becomes `gh api C:/Program Files/Git/repos/DFKHelper/...` and fails with `invalid API endpoint`. Two ways around it:

```bash
# Option A — omit the leading slash (works for gh):
gh api repos/DFKHelper/token-goat/actions/runs/<id>

# Option B — disable MSYS path conversion for the call:
MSYS_NO_PATHCONV=1 gh api /repos/DFKHelper/token-goat/actions/runs/<id>
```

The same trick applies to any tool that takes URL-style paths on the command line.

## Release flow

1. Bump `version` in `package.json` and run `npm install` to update `package-lock.json`. That lock change goes in a commit whose subject starts `release` or `chore(release)`.
2. Fold `[Unreleased]` CHANGELOG entries into the new `[X.Y.Z] - YYYY-MM-DD` heading.
3. Commit, push `main`, create the GitHub release (`gh release create vX.Y.Z`).
4. The release event triggers `.github/workflows/publish.yml` which runs `npm publish`.
5. Verify at `https://www.npmjs.com/package/token-goat`.

## Adoption numbers

`npm run adoption` prints npm downloads, GitHub stars and GitHub forks for each week since the repository was created, newest week first. It rebuilds the table from the public npm and GitHub APIs on every run and stores nothing. It needs no token, because GitHub answers the star history and the forks list without one; set `GH_TOKEN` (`GH_TOKEN=$(gh auth token) npm run adoption` works locally) for GitHub's higher rate limit. `--json` prints the rows as data and `--since YYYY-MM-DD` starts later. The scheduled `adoption.yml` workflow puts the same table in its job summary every Monday. The script lives in the repository and does not ship in the npm package.
