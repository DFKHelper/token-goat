# Changelog

All notable changes to Token-Goat are documented in this file. Format follows Keep a Changelog. Token-Goat follows Semantic Versioning starting at 1.0.

## [Unreleased]

### Added

- **VHDL is now indexed**, extracting entities, architectures, packages (specification and body), functions, and procedures from `.vhd`/`.vhdl` files. A `/* ... */` delimited comment (added in VHDL-2008) is treated as non-nesting, matching IEEE Std 1076-2008 clause 15.9: the first closing `*/` ends it, however many `/*` appeared inside. A function or procedure declared without a body (a forward declaration in a package specification) is not indexed, matching this repo's existing convention elsewhere. Run `token-goat index` (or let the background worker catch up) to pick up VHDL files in an existing project: this changes what a `.vhd`/`.vhdl` file's index rows contain, so it reindexes.
- **Six template-engine formats are now indexed as HTML**: Jinja2 (`.j2`/`.jinja`/`.jinja2`), Handlebars (`.hbs`/`.handlebars`), ERB (`.erb`), EJS (`.ejs`), Nunjucks (`.njk`), and Twig (`.twig`). Each dialect's own template delimiters (`{{ }}`, `{% %}`, `{# #}`, `<% %>`, and their comment/triple-brace/trim variants) are blanked out before the file is handed to the same HTML extractor `.html` and `.liquid` files already use, so `id`/`class` attributes and headings in the surrounding markup are indexed the same way they would be in a plain `.html` file, while the templating expressions themselves are not. Run `token-goat index` (or let the background worker catch up) to pick these files up in an existing project: this adds index rows for six extensions that were previously unindexed, so it reindexes.
- **Five Lisp-family dialects are now indexed**: Common Lisp (`.lisp`/`.lsp`/`.cl`), Scheme (`.scm`/`.ss`), Racket (`.rkt`/`.rktl`), Clojure (`.clj`/`.cljs`/`.cljc`), and Emacs Lisp (`.el`). Each dialect gets its own extractor rather than one shared implementation, because their comment, string, and character-literal rules genuinely differ: block comments (`#| ... |#`) nest in Common Lisp, Scheme, and Racket, but neither Clojure nor Emacs Lisp has a block-comment form at all; a "skip the next form" comment exists as `#;` in Scheme and Racket and as `#_` in Clojure, but not in Common Lisp or Emacs Lisp; and a character literal is written `#\x` in Common Lisp/Scheme/Racket, plain `\x` in Clojure, and `?x` in Emacs Lisp. Run `token-goat index` (or let the background worker catch up) to pick up these files in an existing project: this adds index rows for eleven extensions that were previously unindexed, so it reindexes.
- **Haskell (`.hs`) is now indexed**, extracting `module`, `data`/`newtype`, `type`, `class`, and `instance` declarations along with top-level function bindings (a type signature and/or one or more equations, merged into a single symbol). Since Haskell's layout rule has no explicit delimiter around a top-level declaration, a declaration's span is found the same way every Haskell ctags generator finds one: a line with no leading whitespace starts it, and it runs to the line just before the next such line. A `{- -}` block comment nests, per the Haskell 2010 Language Report section 2.3; a `--` line comment does not start when the dash run is itself part of a longer legal operator lexeme (`-->`, per Report sections 2.3 and 2.4). Literate Haskell (`.lhs`) is not claimed by this adapter: telling code from prose in a bird-tracks or `\begin{code}` file needs its own masking pass this adapter does not implement. Run `token-goat index` (or let the background worker catch up) to pick up `.hs` files in an existing project: this adds index rows for an extension that was previously unindexed, so it reindexes.
- **OCaml (`.ml`/`.mli`) is now indexed**, extracting `module`, `module type`, `type`, `exception`, `class`, `external`, and top-level `let`/`let rec` bindings, found by the same no-leading-whitespace top-level-boundary heuristic `haskell.ts` uses. A `(* *)` block comment nests, per The OCaml Manual's "Comments" section -- but unlike every other nesting block comment this repo indexes, a `"` seen while scanning a comment switches into real string-lexing mode first (the manual: "Comments do not occur inside string or character literals"), so `(* " *)` does not close the comment at that `*)`: the unterminated string absorbs it, and the comment only ends at the first `*)` found once the scanner is not inside such a string. `{id|...|id}` quoted string literals (an arbitrary user-chosen delimiter, `{|...|}` when empty) are read literally with no escaping. A `'c'` character literal (including `\n`/`\'`/decimal/hex/octal escapes) is distinguished from a bare `'a`/`'b` type-variable tick by whether the text actually closes within the fixed lookahead each literal form requires. Run `token-goat index` (or let the background worker catch up) to pick up `.ml`/`.mli` files in an existing project: this adds index rows for two extensions that were previously unindexed, so it reindexes.
- **F# (`.fs`/`.fsi`/`.fsx`) is now indexed**, extracting `namespace`, `module`, `type`, `exception`, and top-level `let`/`let rec` bindings, found by the same no-leading-whitespace top-level-boundary heuristic `haskell.ts` and `ocaml.ts` use. A `(* *)` block comment nests and, like OCaml's (F#'s comment/string lexing is a direct descendant of OCaml's), is string-aware: a `"` seen while scanning a comment switches into string-lexing mode first, so an unbalanced quote inside a comment does not close it at the next `*)` -- the well-known F# "stray quote in a block comment swallows the rest of the file" gotcha is the direct observable consequence of this same rule. `"""..."""` triple-quoted strings are read literally with no escape processing; `@"..."` verbatim strings use `""` (not backslash) as their only escape, so a backslash inside one (`@"C:\temp\n"`) is two literal characters, never an escape; ordinary `"..."` strings use normal backslash escaping. Run `token-goat index` (or let the background worker catch up) to pick up `.fs`/`.fsi`/`.fsx` files in an existing project: this adds index rows for three extensions that were previously unindexed, so it reindexes.
- **Nix (`.nix`) is now indexed**, extracting `let`-bound names and attribute-set keys (`name = value;`, `a.b.c = value;`) as symbols, since Nix has no C-family top-level declaration syntax. Unlike every other block comment this repo indexes, Nix's `/* */` comment does NOT nest (Nix Reference Manual, "Syntax"): the first `*/` closes it, however many `/*` appeared inside. String interpolation (`${...}`) is tracked with a real mode stack rather than a flat scan, since a `${...}` antiquotation can contain a nested Nix expression, which can itself contain another string with its own `${...}`, arbitrarily deep; the stack also tracks brace depth within an interpolation so a `}` belonging to a nested record literal (`${ { a = 1; }.a }`) does not prematurely close it. Indented (`''...''`) strings use their own dedicated escapes -- `'''` for a literal `''` and `''${` for a literal `${` that does not open an interpolation -- distinct from `"..."` strings' backslash escaping. Run `token-goat index` (or let the background worker catch up) to pick up `.nix` files in an existing project: this adds index rows for an extension that was previously unindexed, so it reindexes.
- **Zed is now supported via `token-goat install --zed`.** Zed's first-party agent has no hooks API at all, so this registers token-goat as an MCP context server instead -- the only integration surface Zed offers -- in Zed's `settings.json` (`%APPDATA%\Zed\settings.json` on Windows, `~/.config/zed/settings.json` elsewhere), plus a small generated shim script that launches `token-goat mcp-serve`. The install merges surgically into an existing `settings.json`, preserving comments, other keys, and any other context servers already registered there, and is idempotent on repeat runs. Like Visual Studio's MCP-only integration, this is tools only: no read dedup, hints, image shrink, or output folding, since Zed has no hook to fire them from. `token-goat uninstall --zed` removes the entry and the shim; `token-goat doctor` reports whether the entry is present and warns if the shim or the paths it points at have gone stale. Nothing to reindex.
- **Cursor is now supported via `token-goat install --cursor`.** This registers token-goat as an MCP server in `~/.cursor/mcp.json` (`-p`/`--project` for `<project>/.cursor/mcp.json`), root `mcpServers`, entry shape `command`+`args` only -- confirmed against the installed Cursor 3.19.7 bundle's own JSON schema, which has no `type` field for a server entry and rejects unknown properties. `--cursor` deliberately never writes `~/.cursor/hooks.json`: the same bundle shows Cursor already imports Claude Code's hooks from `~/.claude/settings.json` by default (`thirdPartyExtensibilityEnabled` defaults on) and dedupes against its own `hooks.json` by exact command string, so a plain `token-goat install` for Claude Code already makes those hooks fire once inside Cursor with zero extra work; writing a second, independently-maintained copy would only risk a permanently-diverging duplicate, and `~/.cursor/hooks.json` may already be a real file another tool manages (observed on the machine this was verified against: a third-party tool's 8-event hook registration). A guard test (`tests/guards/cursor_never_writes_hooks_json.test.ts`) fails the build if a future change writes to it anyway. `token-goat uninstall --cursor` removes only the MCP entry; `token-goat doctor` reports it and whether Claude Code hooks are installed for Cursor to pick up. Nothing to reindex.

### Security

Most of these harden the containment walk and `install --vscode`'s project-scope default, which flipped from user scope back to project scope earlier in this same Unreleased block. Four concern builds already out. The first entry is one of them in part: **four** shipped flags have accepted a project-relative target, not three. `--vscode` is the fourth, and an earlier draft of this entry called it unreleased, which was wrong -- it wrote `<cwd>/.vscode/mcp.json` and `<cwd>/.github/copilot-instructions.md` unconditionally from its very first release, v2.6.23, four releases before v2.6.28 gave it a `-p`/`--project` switch and made user scope the default. Only `--visualstudio` and `--cursor` gained their project scopes here and were never released with one. The other three released defects are `~/.token-goat`'s mode and the two containment-walk defects. What the code did is stated plainly either way, because "unreleased" describes who was exposed, not what the defect was.

- **A repository could make a project-scope install read a private file, copy it into the working tree, and write back through the link.** Every installer that accepts a project-relative target was affected: `install --project`, `install --copilot --local`, `install --pi --local`, `install --vscode` (`--project` from v2.6.28 on), `install --visualstudio --project` and `install --cursor --project`. **Four of those have shipped**, with these affected ranges -- each re-derived from the tagged trees rather than from memory, since a wrong lower bound here tells a real user they were never exposed:

  - `install --project` / `-p`, **v2.0.0 through v2.9.10**. Project scope arrived with the TypeScript rewrite in v2.0.0 (`-p, --project` in that tag's `src/cli.ts`; the v1.x Python line had no project scope at all), and `<cwd>/.claude/settings.json` has been read and rewritten through whatever that path resolves to ever since. The stronger half -- copying the link target's *bytes* into the working tree -- starts later, at **v2.6.3**, the first release to define `backupFile`, whose body was a bare four-line `copyFileSync` to a `.bak.<ISO>` sibling -- and `copyFileSync` follows a symlink at the source.
  - `install --pi --local`, **v2.6.3 through v2.9.10**. v2.6.3 is the first release whose CLI passes `{ local: opts.local }` into `installPi`, pointing it at `<cwd>/.pi/extensions/token-goat.ts`.
  - `install --copilot --local`, **v2.6.6 through v2.9.10**. Not v2.6.5: that release's bridge already had the `local` option and the project hooks directory, but its CLI called `installCopilotCli()` with no arguments and documented `--local` as meaning something only alongside `--pi`, so the combination was unreachable. v2.6.6 is where `installCopilotCli({ local: opts.local === true })` first appears.
  - `install --vscode`, **v2.6.23 through v2.9.10**. This one was previously disclosed as unreleased and that was wrong. v2.6.23 is the first release containing `src/bridges/vscode_install.ts` at all, and its `installVscode(projectRoot = process.cwd())` had no scope option: every install wrote `<cwd>/.vscode/mcp.json` and `<cwd>/.github/copilot-instructions.md`, with the help text calling them "project-local". The `-p`/`--project` switch and the user-scope default only arrived at v2.6.28, so the flag spelling that names the exposure today is five releases younger than the exposure.

  `install --project`'s backup step used `copyFileSync`, which follows a symlink at the source; `--copilot --local`, `--pi --local` and `--vscode` had no backup step to copy anything out, but still read and rewrote through a symlinked `.github/copilot-instructions.md`, `.pi/extensions/token-goat.ts` or `.vscode/mcp.json`, so a clone could steer token-goat's own block into a file outside the tree. Nothing checked what any of those targets actually was. A clone that committed `.github/copilot-instructions.md` as a symlink to `~/.ssh/id_ed25519`, or `.vscode/mcp.json` as one to `~/.docker/config.json`, would get that file's bytes written to `<repo>/<name>.bak.<ISO>` -- untracked, inside the clone, and swept up by the next `git add -A`. The same follow also meant the installer read and rewrote through the link. Containment is now enforced by the write helpers themselves rather than by each installer remembering to ask for it. An installer declares its scope once at its entry point, and `backupFile`, `ensureDirSync`, the atomic writers and `upsertDelimitedBlock` each refuse a write that the declared project root does not contain, naming the path. The first shape of this fix was a check the installer had to call, and it reached one installer of five while four siblings wrote the same repository-controlled paths unguarded -- so the check moved into the write helpers, where an installer cannot forget to call it. What that does **not** do is fail closed on omission, and an earlier draft of this entry claimed it did. It cannot: `backupFile`, `ensureDirSync`, the atomic writers and `upsertDelimitedBlock` are the whole codebase's write path, not the installers' -- the indexer, the worker, snapshots, the created-configs ledger and `write-file` all go through them with no install run to declare anything -- so refusing every undeclared write would refuse essentially every write token-goat makes. Declaring a user root at the install dispatcher does not rescue it either: a project-scope install legitimately writes user-scope files (`~/.claude/CLAUDE.md`, the skill, the shared hook shim), and confining those broke `install -p` outright once already. So an installer that declares no scope writes exactly as it did before, and what catches the omission is a **structural** guard rather than a runtime one: a test enumerates every module that writes a repo-relative path and fails on any that does not declare a scope, a second enumerates every filesystem mutation inside those modules and fails on any that bypasses a containment-checking helper, and a third fails on any of them containing `async`/`await`, since the scope is a module-level variable restored synchronously. Each pins its own population with a floor, a ceiling and exact member anchors, so a rename or a moved file cannot empty it silently. A separate behavioural sweep and a behavioural sweep runs the built binary against poisoned clones for each of the six flags above. The containment check rather than a leaf `lstat` is what is needed, because a repository can equally commit `.github` itself as a directory symlink. Containment holds whether or not the file exists yet, which is the case that matters: `realpathSync` throws the moment any component is missing, so an implementation that resolves only whole paths falls back to a lexical comparison in precisely the situation an installer is always in -- about to create a file. Containment is therefore decided by walking the path one segment at a time from its root, following each link with `readlink` as it is met and re-appending the segments that do not exist yet -- not by resolving the nearest existing ancestor in one call, which is the shape that first shipped here and which had two blind spots of its own (see the two entries below). `copyFileSync` also now passes `COPYFILE_EXCL`, so the backup cannot be steered by a symlink planted at the destination; a name already taken -- by a planted link, or by token-goat's own backup of the same file earlier in the same millisecond, which a project-scope install really does produce -- gets a numeric suffix rather than aborting the install. User-scope installs are unchanged: a symlinked `~/.copilot/...` dotfile is a normal setup and still works.
- **A repository could switch off every VS Code hook by committing one file.** The user-scope hook stood down whenever `.github/hooks/token-goat.json` merely existed in the workspace, on the reasoning that a project-scope copy would answer instead. A clone that committed that path containing `{}` had no project copy to answer, so read dedup, session hints, image shrinking, edit-queue reindexing and the pre-approval path gate all went quiet for that workspace, with no error and no output -- indistinguishable from working. Standing down now requires two independent agreements: the ownership sidecar `token-goat.owners` naming `vscode`, and the created-configs ledger in token-goat's own data directory recording that an install on this machine wrote that exact path. A clone can still forge the sidecar, so this raises the cost of the attack rather than closing the class; the ledger is the half a clone cannot reach. Setting `TOKEN_GOAT_LOG` now prints one line to stderr whenever a copy stands down, so the silent case is observable.
- **A UNC workspace root made the VS Code hook open an SMB connection before the user approved anything.** That same lookup joined the workspace `cwd` VS Code supplied straight onto a path and statted it. On Windows, statting `\\host\share\...` opens a connection to `host` and offers an NTLM authentication, and the in-process hook path has no timeout to bound it. The lookup now runs through `vscodePathAllowed`, the same gate every pre-approval handler uses, which declines a two-separator root outright. A new guard (`tests/guards/pre_handler_fs_touches_are_gated.test.ts`) covers the structural half: `tests/vscode_pre_handler_path_gate.test.ts` sweeps the handler registry and so cannot see anything the relay does before dispatch, which is where this call sat and where two earlier pre-approval touches also sat. The new guard walks the call graph from `relayInProcess` up to the first handler dispatch and fails on any `fs`/`net` call that is neither gated nor named in an exemption table with its reason, so an unclassified call site is red on arrival rather than red once somebody notices.
- **The VS Code hook could create token-goat's data directory world-readable.** On a fresh install the hook can be the first thing that ever writes there, and the dedupe marker directory was created with a bare recursive `mkdir` and its prune stamp with a bare `writeFileSync`, both taking the process umask -- 0755 on a stock Linux box, leaving cached command output, fetched pages and the per-project index listable by every local user. Both now go through `ensureDirSync`/`atomicWriteText`, the helpers that harden the enclosing storage root to 0700 first, and so does every other directory creation in token-goat's own storage -- the created-configs ledger, the per-session sidecars for queued context and tool-failure tracking, the embedding model cache, the OCR cache and the skill-output directory, eight sites in all. Two of those eight (the OCR cache, and the per-session sidecars) resolve under `~/.token-goat` rather than under the data directory, and for one release the helper hardened the data directory only, so those two were routed and got nothing; see the entry below. A new guard (`tests/guards/storage_dirs_are_hardened.test.ts`) enumerates them from the call graph and fails on any bare `mkdir` on a storage path that is not named in an exemption table with its reason, so the next one is red on arrival rather than found by the next audit. Windows is unaffected: Node ignores POSIX modes there and the directory inherits its parent's ACL.
- **`~/.token-goat` was left at the umask default, so on a stock Linux box every local user could read another user's session snapshots.** This one is about released builds, not the unreleased project scope above: `~/.token-goat` has existed since before v2.9.10 and nothing has ever mode-hardened it, while the data directory next door was hardened to 0700. It is the more sensitive of the two roots. `session_snapshots/` holds verbatim copies of files the model read, `sessions/` holds session state and its pending-context sidecars, `ocr-cache/` holds text lifted out of images the user viewed, `image_shrink_cache/` copies of those images, and the blob subdirectories hold fetched web bodies -- so `saveSessionState` was redacting secrets before writing into a tree any local account could list and read. On a stock Debian or Ubuntu box `$HOME` is 0755, which is what makes this reachable rather than theoretical; a `$HOME` of 0700 already blocked it. `ensureDirSync` now hardens whichever of the two roots the requested path falls under, in the same two steps the data root uses (the parent is left at the umask default, because `$HOME` is not token-goat's to tighten), and an existing permissive directory is chmodded down on the next run. Windows is unaffected: Node ignores POSIX modes there. Not remotely exploitable -- it needs a local account on the same machine.
- **A dangling symlink sitting directly in a Windows drive root read as inside that root.** The containment walk found the nearest existing ancestor with `path.posix.dirname`, and `path.posix.dirname('x:/name')` is `'x:'` with no slash, so the loop ended before the drive root itself was ever tried and the merely-lexical answer was returned without the link ever being read. `isInsideRoot('x:/link', 'x:/')` therefore answered true for a link pointing anywhere. One level deeper the same shape was refused correctly, and POSIX was never affected (`dirname('/name')` is `/`), so this was invisible on two of the three CI platforms. Measured on a real `subst` drive against the built artifact, before and after.
- **A `..` segment could step out through a symlink and back in by name.** `<root>/link/../sneak.txt`, with `link` a junction pointing outside the root, read as inside it: `..` was collapsed lexically with `path.resolve` before any link was resolved, which cancels the link instead of the directory the link actually names. The walk now resolves each segment in order and applies `..` to where the path has actually arrived, so the same string is refused; an ordinary `sub/../a.ts` inside the root is still accepted.
- **Migrating a user-scope install to project scope deleted the recovery copies it had just written.** The first project-scope install after the upgrade migrates an existing user-scope one by calling the uninstall path, which ends by sweeping the `.bak.<ISO>` files token-goat created -- correct when the user asked to uninstall, wrong here. This is the one path that rewrites a user-scope file without being asked to, so it is exactly where the "every overwritten file gets a recovery copy" guarantee added earlier in this same Unreleased block had to hold, and it was the one place it did not: the copy was written and deleted seconds later, in the same run. A migration now runs the uninstall with backups kept; a real `uninstall` still sweeps them.
- **One long path from the model could hang the VS Code hook before the user approved anything.** The containment walk added earlier in this same Unreleased block resolved a path one segment at a time with no length limit, and the cost grew faster than quadratically: measured on one machine, a 106-byte path answered in 1.3 ms, a 6,946-byte one in 38 ms, and a 1.89 MB one in 1,301,906 ms -- 21 minutes of pinned CPU for a single call, against 14.9 ms for one `realpathSync` of the same string. The reachable path is the pre-approval gate every read, write and image hook goes through, on a path the model chose and the user has not yet approved. In VS Code that hook runs in-process with no timeout available, so the editor's hook does not get slow, it stops answering; under Claude Code it is a subprocess holding a core for as long as it takes. The walk now refuses any path over 4,096 bytes -- PATH_MAX on Linux, and four times the longest path Windows or macOS will hand it -- both on entry and on the resolved form as links expand it, and an over-length path is treated as unresolvable, which fails closed. The same 1.89 MB path now answers in about 2 ms. The queue the walk consumed was also an `Array.shift()`, quadratic on its own; that is now an index cursor.
- **An unreadable directory made the containment walk answer "inside the project" instead of "unknown".** Every error from the per-segment `lstat` was treated as "this component is not a symlink", which is true for a component that does not exist and false for one the process cannot read: an EACCES on an ancestor produced an under-resolved path and a permissive verdict, on the same pre-approval gate. Absence (`ENOENT`, `ENOTDIR`) still lets the walk continue, because an installer is always about to create a file that is not there yet; every other errno is now unresolvable, and unresolvable is never contained.
- **A storage root that failed to harden once was never hardened again.** `ensureDataDirPrivate` and `ensureHomeDirPrivate` recorded the root as done *before* attempting the `mkdir` and `chmod`, under a deliberately empty catch. One transient failure -- a backup tool holding the directory, a momentary EACCES, a parent that is briefly a file -- therefore banked itself as a success for the rest of the process, which in the CLI is one command and in the long-lived worker is the whole session, and every write after it landed in a directory left at the umask default with nothing retrying. The memo is now written only after the work actually completes.
- **`TOKEN_GOAT_HOME` was accepted as a relative path, which silently switched off 0700 hardening.** Its siblings `LOCALAPPDATA` and `XDG_DATA_HOME` already ran through a validator requiring an absolute path; this one had a bare empty-string check and returned whatever it was given. Since hardening is dispatched on whether a directory falls under `tokenGoatHome()`, a relative value resolved the storage tree against the current working directory and matched nothing -- and inside a VS Code hook the working directory is the workspace folder, so session snapshots of every file the model read would have been written into an untrusted clone at the umask default. It now goes through the same validator, and a relative or blank value falls back to `~/.token-goat`.
- **On Linux, uninstalling could delete a settings file token-goat never created.** The ledger recording which config files an install wrote folded its keys to lower case unconditionally, so on a case-sensitive filesystem `~/Repo/.zed/settings.json` and `~/repo/.zed/settings.json` -- two different files -- answered to one entry. `uninstall --zed` deletes an empty `settings.json` on exactly that answer. The mirror of the same bug meant the second directory's entry was seen as already present and never recorded, so its backups were orphaned at uninstall while the output said they had been removed. The ledger now folds case only where the filesystem does. macOS and Windows were unaffected, since there the two spellings really are one file.

### Documentation

- **The install guide now says plainly why there is no Windsurf agent-hook integration.** Windsurf's Cascade agent hooks (`cascadeHooksJson`) are pushed from Windsurf's own servers per team, not read from a file on disk -- confirmed by tracing every reference to that field across the installed Windsurf 1.110.1 bundle, where it only ever appears as a protobuf field or a class-constructor default alongside other server-pushed team settings. There is no local hook file for token-goat to install, so Windsurf keeps its existing terminal-output compression only, and a guard test (`tests/guards/windsurf_never_writes_cascade_hooks.test.ts`) now fails the build if a future change tries to write one anyway. Nothing to reindex.

- **The install guide now says plainly that JetBrains IDEs (WebStorm, IntelliJ, PyCharm, Rider, PhpStorm) have no integration today: no hooks, no MCP, no terminal filter.** Junie, the JetBrains ACP agent, documents `.junie/AGENTS.md` for guidelines and `~/.junie/mcp/mcp.json` for MCP servers, and a secondary source describes `~/.junie/config.json` for hooks -- but none of this was confirmed against a live Junie run: no `~/.junie` directory exists anywhere on the machine this was checked from, so the on-disk shape of any of those files is unverified. A guard test (`tests/guards/jetbrains_never_writes_junie_config.test.ts`) now fails the build if a future change writes one of those paths anyway without fresh live evidence. Separately, GitHub documents its Copilot-for-JetBrains plugin previewing agent hooks in `.github/hooks/` -- the same folder `--copilot` and `--vscode` already write -- which would mean a project already gets some pickup for free with no JetBrains-specific code, but the real plugin is not installed here (only its theme jar is present) so this is noted as unconfirmed, not relied upon. No `BRIDGE_CAPABILITY_MATRIX` row was added, matching the Windsurf precedent above: that matrix tracks hook-event parity for a real install writer, and JetBrains has none. Nothing to reindex.

### Fixed

- **`token-goat install --vscode` (and every other single-harness scope flag) silently also ran the base Claude Code install -- fixed.** A `--vscode`-only (or `--codex`-only, `--gemini`-only, etc.) install or uninstall used to unconditionally touch three files no single-harness integration needs: it rewrote `~/.claude/settings.json` (adding token-goat's hook entries), appended a delimited block to the user's own hand-maintained `~/.claude/CLAUDE.md`, and created `~/.claude/skills/token-goat/SKILL.md`. If you ran `install` with any single harness flag before this fix, check `~/.claude/settings.json` and `~/.claude/CLAUDE.md` for token-goat content you did not ask for (a `<!-- token-goat-begin -->` … `<!-- token-goat-end -->` block in `CLAUDE.md`, or a `token-goat` hook command in `settings.json`'s `hooks` section) and `~/.claude/skills/token-goat/` for a directory you did not expect; `token-goat uninstall` (no flag) removes all three cleanly. A plain `install`/`uninstall` with no harness flag, or `--hermes`, still installs the Claude Code base as before; every other harness flag now touches only its own files. A guard test (`tests/guards/scoped_install_never_writes_claude_code_base.test.ts`) fails the build if a scoped harness branch calls a Claude-Code-base install/uninstall function again, and a behavioural test (`tests/install_vscode_never_touches_claude_code_home.test.ts`) runs the real built binary against a disposable home directory and checks the literal file list. Nothing to reindex.
- **The installer could rewrite an existing file with no recovery copy -- fixed for every file it writes.** Before this fix, `writeJsonSettings` (used for `~/.claude/settings.json` and several harnesses' JSON configs) was the only writer that backed up the file it was about to overwrite. Nothing else did: an `upsertDelimitedBlock`/`stripDelimitedBlock` rewrite of `~/.claude/CLAUDE.md` or any harness's `AGENTS.md`/instructions file, `~/.claude/skills/token-goat/SKILL.md`, and the JSON merge-writers for VS Code's, Visual Studio's, and Cursor's `mcp.json` and Zed's `settings.json` all overwrote their target with zero recovery copy. Zed's `settings.json` in particular is not a token-goat-exclusive file -- it can hold a user's entire editor configuration (theme, keybindings, vim mode, every other extension's own settings) alongside the one `context_servers.token-goat` entry token-goat manages, so a bad merge there was not a one-line loss. Every one of those writers now writes a `<file>.bak.<ISO-timestamp>` sibling right next to the file, byte-for-byte before its own overwrite, capped at 5 backups per file and cleaned up again on a full `token-goat uninstall`. If you ran an affected install before this fix and still have the original file's content elsewhere (git, an editor's local history, a real filesystem backup), there is no `.bak` from token-goat to recover from for that earlier run -- only installs from this version onward are covered. A new guard test (`tests/guards/installer_writes_are_always_backed_up.test.ts`) enumerates every installer write site in `src/install.ts` and `src/bridges/*_install.ts` and fails the build if a new one is added without going through the backup path or an explicitly named, justified exemption (a purely generated shim/plugin script regenerated identically on every install, or token-goat's own internal bookkeeping ledger). A behavioural test (`tests/install_backs_up_preexisting_config_before_overwrite.test.ts`) runs the real built binary against a hand-authored `mcp.json`/`settings.json` with known content and checks the backup's bytes match the original exactly. Nothing to reindex.
- **Emacs Lisp no longer loses the rest of a line to a plain character-literal escape.** A basic escape naming a character outside alnum/`^`/`-` (for example `?\"`, `?\;`, `?\(`) left that one escaped character unmasked, so a following real string quote (or a definition on the same line) could be misread through it -- `?\"` in particular let the next `"` open a real string span, silently swallowing everything after it, including any `defun` on that line. A lone `\<c>` now always consumes exactly the one character it names, per Emacs Lisp's Basic Char Syntax. Run `token-goat index` (or let the background worker catch up) to pick up the fix: this changes what an `.el` file's index rows contain for any file with this pattern, so it reindexes.

- **Retrying a `read`/`brief` command with the exact qualified name token-goat suggested for an ambiguous symbol could still report the same ambiguity, with the same suggestion, forever.** When two same-named symbols sit at different places in one file and one of them is enclosed by the other (for example, an HTML file with a `<h2>Overview</h2>` heading and an unrelated element `id="Overview"` that falls inside that heading's section), token-goat's ambiguity message qualified the inner one as `Overview.Overview` -- using the enclosing heading's own name as the qualifier. Retrying with that exact `Overview.Overview` spec fed it back into the same lookup, which mistakenly treated the outer heading as containing itself and kept both candidates in play, so the retry it just suggested resolved nothing new. The lookup now only counts a symbol as "inside" a container when it is a different symbol from it, so this qualifier -- and every other qualified retry built the same way -- picks out exactly the one candidate it names. No reindex is needed.

- **A LaTeX `.cls` file is no longer reported as Salesforce Apex.** `.cls` is shared by Apex, VB6 class modules, and LaTeX document/package class files; the check that told Apex from VB6 and OpenEdge ABL never checked for LaTeX at all, so any `.cls` that was not VB6 or ABL fell through to the Apex default. A LaTeX `.cls` (one that starts with `\ProvidesClass{...}` or `\documentclass{...}`) is now recognized and reported as an unsupported file type instead, rather than misclaimed as Apex. There is no LaTeX symbol extractor yet, so a LaTeX `.cls` file's symbols are no longer indexed at all -- this changes what `token-goat index` does with any `.cls` file that used to be misindexed as Apex, so it reindexes any project that has one.

### Changed

- **`token-goat install --vscode` now installs into the current project instead of user scope, because a user-scope install was silently doing nothing outside the first folder of a multi-root workspace.** VS Code resolves an agent hook's working directory from the hook *file's* own location -- the workspace folder containing it, or the workspace's first folder when no folder contains it. A user-scope hooks file lives in `~/.copilot/hooks/`, which is inside no workspace folder, so every invocation ran with `folders[0]` as its working directory; since token-goat confines every pre-approval hook to that directory, read hints, image shrinking and edit interception did nothing at all for every other folder of a multi-root workspace, with no error and no output to notice. Captured live against VS Code 1.137.0 in a two-root workspace: the user-scope copy reported root A as its `cwd` for an event raised in root B, while a project-scope copy in root B reported root B. **If you already have the user-scope install, just run `token-goat install --vscode` again in each project you want it in** -- the first run detects the old install and moves it, printing a note saying so, rather than leaving both in place. That matters because VS Code runs *every* hooks file it discovers, in both scopes at once (also captured: two invocations of every event inside one session id), so an unmigrated machine would fire every hook twice. `--user` keeps the old behaviour deliberately, with a printed note naming the multi-root limitation it opts into; `-p`/`--project` is still accepted and now selects the default. `token-goat doctor` gained a check that reports a user-scope install still sitting there, and a stronger one for a machine that has both. Passing `-p` and `--user` together is an error rather than one silently winning. Where two copies of one hook do still reach token-goat -- a pathless event such as session start, or a terminal command, neither of which carries a path the workspace confinement can decide on -- exactly one is elected by an exclusive-create marker keyed on `(session id, event, the payload's own timestamp)`, under token-goat's data directory and never the repository or the working directory, pruned after an hour. Every part of that election fails open: if the marker cannot be written the hook runs, because a duplicate hook is recoverable and a silenced one is not. Nothing to reindex.

- **A default install is smaller: it no longer downloads `sharp`, or the libvips image library that comes with it.** Image shrinking is built into token-goat and needs no extra package, so `sharp` was being installed and never loaded. A default install goes from 70 packages to 62, and an install without optional packages is unchanged at 2. `sharp` is now a development dependency, where the tests use it as a second opinion on token-goat's own image output. Every copyleft licence in an installed copy came in with libvips and is gone with it, leaving six packages that need a human answer instead of twenty: see [SECURITY.md](SECURITY.md#dependency-licenses). Nothing needs reindexing.

### Fixed

- **`recall` no longer points you at a cached command output that is already gone.** Each `bash-output`/`web-output`/`mcp-output` entry `recall` finds used to always print the exact command to fetch its full body, even after that body's on-disk copy had already been cleaned up (by age, or by the normal count/size eviction every cache uses). Following that pointer returned nothing, with no warning it would. `recall` now checks whether the file is actually still there before printing the pointer, and says "blob expired" instead when it isn't. The index also no longer keeps a `recall` entry around forever once its blob is gone: entries expire on the same 24-hour clock the blob cache already uses, so the two can no longer drift apart. No reindex is needed.

- **`token-goat stats`'s own history table is now bounded instead of growing forever.** Every recorded saving event stayed in the database indefinitely; on one long-running machine this reached over 400,000 rows. Events older than 180 days are now rolled up into daily totals (by day, source, and harness -- the same breakdown `stats` already reports) and the individual rows removed, so long-window and all-time totals stay correct while the table stops growing without bound. No reindex is needed.

- **A handful of bundled third-party JavaScript files no longer pollute `refs` with a compiler-inserted call that names no real symbol.** esbuild inserts a `__name(fn, "name")` wrapper call around named functions in some build targets; indexing that call as a reference filled `refs` with call-sites for a name nothing in any project actually defines. Only this exact, unambiguous compiler artifact is excluded -- generic test-framework identifiers like `expect`/`it`/`describe` are deliberately left alone, since a broader exclusion list risks quietly hiding a real symbol some other query relies on. Run `token-goat index` to reparse: `__name` references recorded by a prior index are not retroactively removed, only future extractions no longer record new ones.

- **`refs`, `ask`, `semantic`, and `trace --bodies` now warn and self-heal when they answer from a file that changed on disk, the same way `symbol`/`read`/`skeleton`/`outline` already did.** Those four single-file commands already caught a stale row (index says one thing, the file on disk says another) and reindexed it on the spot before answering. `refs`, `ask`, and `semantic` answer from however many distinct files their query happens to match, and `trace --bodies` resolves each traceback frame's file the same way `symbol`/`read` resolve a spec's file -- none of them ran that check at all, so editing a file outside the edit hook (a manual save, an external tool, a merge) left them silently serving pre-edit content with no warning and no self-heal. All four now run the same check across every file they are about to answer from, printing one summary warning when any of them turn out stale. No reindex is needed; a stale hit corrects itself in place the moment one of these commands notices it.

- **A dead background worker is now revived by whatever queues work for it, not only by an editor's post-edit hook.** If the background worker had crashed, been killed by hand, or not survived a machine sleep/wake, only the Claude Code/Codex post-edit hook noticed and restarted it. Every other way a file gets queued for reindexing -- a Bash-command hook rewriting a file, `token-goat replace`/`write-file`, and the self-heal that runs when a stale read is served -- appended to the dirty queue and reported success without ever checking whether anything was running to drain it, so the queue could sit untouched indefinitely with no warning. The auto-revive check now lives at the one place every one of those paths already shares (the function that appends to the queue), so all of them nudge a dead worker back to life the same way the edit hook always did. No reindex is needed.

- **Stopping the background worker no longer silently drops an embedding that was still being computed.** `token-goat worker stop`, and a daemon restart that replaces an old one mid-batch, send the running daemon SIGTERM. The daemon used to exit immediately on that signal regardless of any embedding call still in progress, so that file's vectors never got written -- `symbol`/`read` stayed correct (parse rows commit before embedding starts), but `semantic` silently missed that file's content until something re-touched it. The daemon now waits (up to 5 seconds) for in-flight embeddings to finish before exiting, so a stop or restart during active indexing no longer drops that work; the wait is capped so a genuinely stuck embedding call can never block a replacement daemon from starting. No reindex is needed.

- **Reparsing a file no longer forces its embedding to be redone from scratch when the content didn't change.** Every reparse (a parser-fingerprint bump, a touched mtime, `--force-refresh`) rewrote the file's row without its `embed_sha`, so the next embedding pass always saw "no embedding on record" and recomputed one for content that already had a correct, unchanged embedding. The row write now carries the prior `embed_sha` forward whenever the new content hash matches the old one, and still resets it when the content actually changed, so re-embedding only happens for content that is actually new. No reindex is needed; a `reindex --force-refresh` you already have queued will now skip re-embedding files whose content it finds unchanged, where it previously redid them anyway.

- **`reconcile` now finds a file that a parser upgrade left stale, not only a file whose content changed.** The drift sweep behind `token-goat reconcile` compared a file's bytes on disk against the row's stored hash, and skipped straight to the next file the moment neither had moved. That misses the case a parser fix or a new parser version creates: a file nobody edited afterward still holds symbol and reference rows written by the old extractor. The per-file checks in the indexer and worker already knew to compare a row's `parser_sha` against the current parser fingerprint; `reconcile`'s own sweep never did, so a file only self-repaired if something happened to touch it later. `reconcile` now checks both, and reports how many files it found this way (`--dry-run` says "N files ... were unchanged on disk but indexed by an older parser"). Run `token-goat reconcile` to reindex anything a past parser change left behind; no output changes for a project already reconciled since its last parser upgrade.

- **A secret sitting near a length cutoff could survive as an unrecognisable fragment on four different surfaces, because the cutoff ran before redaction instead of after it.** Redaction requires a minimum match length; cutting a credential short first can leave too little of it for the pattern to recognise, so the leftover fragment shipped raw even though the surface "went through redaction" downstream. This hit the short preview token-goat builds for a cached MCP call's arguments (truncated to 120 characters before redaction ran), the shared tool-output pipeline every Bash filter uses (several length caps ran ahead of the redaction pass), and the compressed summary an MCP result is folded into (compression ran on the raw result text instead of the already-redacted one). A fourth, related gap let a raw agent-spawn prompt persist to disk unredacted entirely — the session field that tracks prompts for spawned agents never redacted at all, not merely too late. And a fifth, differently-shaped bug on the same tool-output path: the pre-hook that rewrites a Bash command into a compression call correctly redacts its result, but discarded that redacted text and fell back to the raw, unredacted original whenever compression didn't save enough bytes to clear its own worth-applying floor — a gate meant to decide whether *compression* was worth it was also discarding *redaction*, which it should never do. All five now redact ahead of any cutoff or compression step, or redact where none existed before. Two new local checks make this specific mistake shape hard to reintroduce: every length-shortening helper in the codebase must now be explicitly recorded as either safe or unsafe for secret-bearing text, and every field of the saved session state must be explicitly recorded as covered by redaction, with an unrecorded new one failing the check by default. Changed in [src/mcp_cache.ts](src/mcp_cache.ts), [src/tool_filters/base.ts](src/tool_filters/base.ts), [src/tool_filters/dispatch.ts](src/tool_filters/dispatch.ts), [src/hooks_mcp.ts](src/hooks_mcp.ts), and [src/session.ts](src/session.ts). No reindex is needed.

- **Pruning old config backups no longer risks deleting a file you made yourself.** Once a config file has more than 5 backups, the oldest ones are removed to keep the pile from growing forever. That prune used to pick candidates by matching `<name>.bak.*` against a directory listing, which is exactly the kind of name a user's own copy of the file could carry. It now consults the same record of what token-goat actually created that uninstall already uses, so a look-alike file you wrote by hand is never a candidate. No reindex is needed.

- **A stale build file no longer ships inside the published package.** `dist/_m.mjs`, left over from a build-output name retired earlier, was riding along in every release because `dist/` ships as a whole directory. The build now clears any leftover file in `dist/` it did not just write, the same way it already cleared old chunk files, so a renamed or retired build output cannot pile up again. No reindex is needed.

- **[SECURITY.md](SECURITY.md#dependency-advisories) no longer claims a clean `npm audit` for this repository when it isn't one.** Two moderate advisories now sit in development-only transitive dependencies (`adm-zip`, `hono`); neither reaches an installed copy of token-goat, which is what the other two rows in that table already measure. The page now says so, and names the packages, instead of rounding a real finding to "clean." No reindex is needed.

- **Uninstalling now takes the backup copies token-goat made of your config files with it.** Whenever an install rewrites a config, it first copies the old one to `<name>.bak.<timestamp>`. Those copies were never removed, so a machine that had installed a few times kept a copy of every config token-goat had ever touched, each holding whatever was in that file at the time, in a folder you had been told the product was gone from. Uninstall now deletes the ones it made, and only those: a backup counts as token-goat's only if token-goat recorded creating it, so a `.bak` file you made yourself stays put even when its name looks exactly the same. No reindex is needed.

- **The demo preview image loads everywhere again.** `demo/screenshots/approval-demo.webp` was a PNG carrying a `.webp` name, which some viewers refuse to render and others only render by guessing. It is now `approval-demo.png`, and the link in [the demo README](demo/README.md) points at the new name. Three images in `assets/` that nothing linked to are gone as well, so the published site no longer carries them. No reindex is needed.

- **Groovy slashy strings, Elixir sigils, and Scala symbol literals now read as the strings they are.** Each one used to look like code, or like a string that never ended, which moved or dropped the symbols around it:
  - Groovy `/.../` and `$/.../$` strings are read as strings, so a brace, an apostrophe, a `//` or a `/*` inside one no longer opens a block, a string, or a comment. Groovy tells a slashy string from a division by where the `/` sits: after an operator, a comma, an opening bracket, or a keyword such as `return`, it starts a string; after a value, it divides. `pack --strip-comments` follows the same rule, where before it could cut a line short at a `//` inside one of these strings.
  - Elixir sigils such as `~w(...)` and `~r/.../` can span lines, including the bracket forms that nest.
  - Scala `'symbol` literals are no longer read as the start of a character literal, so the rest of the line still gets indexed.

  Run `token-goat index` to reparse: the symbols and line numbers recorded for Groovy, Elixir, and Scala files change.

- **`xlsx-range` turns down a range bigger than it can scan instead of trying to read it.** Asking for `A1:XFD1048576` used to walk 17 billion cells and run out of memory. The ceiling is the same 20 million cell limit the other sheet reads already use, counted here from the range you ask for rather than the size the file declares. When a sheet is too large to scan, the message now suggests a smaller `--range` instead of pointing at a read with no limit of its own.

### Security

- **Reports now escape the text a document supplies, everywhere token-goat speaks in its own voice.** A file, a PDF, a video or a transcript can name itself after one of token-goat's own messages, and several commands printed that name straight into a line that reads as token-goat's. Every one of them now neutralizes it first, so the text still shows but no longer reads as an instruction from the tool:
  - `pdf-meta` prints the Title and Author from a PDF's information dictionary. Both are chosen by whoever made the file, and neither was checked or redacted on either the text or the `--json` branch. They now go through the same redaction and escaping every other document command already used, so a secret in a title is hidden and a forged message is shown as ordinary text.
  - `video-chapters` prints chapter titles and subtitle stream names read from the video file.
  - `transcript-outline` prints the first 60 characters of a cue, one line below the speaker labels that were already escaped.
  - `transcript` now wraps its output in the same "untrusted content" fence the other document commands use, and redacts secrets before printing. A spoken or pasted password in a meeting transcript was printed as it was.
  - `sharepoint-resolve` printed the sharing link you passed it, query string and all. SharePoint puts access tokens in that query string, so it is now removed before the link is shown, matching what the rest of that code already promised.
  - The error messages every command falls back to: a message quoting a spreadsheet's sheet names, a file name, or up to 50 lines of a file being edited went to the error stream unescaped.
  - `install --vscode`, `install --visualstudio`, `purge`, and `session-outline` print paths and transcript text that can carry the same forged names.

  None of this needs a reindex.

- **On VS Code with no folder open, hooks no longer treat your home directory as the project.** VS Code starts a hook in your home directory when no workspace folder is open, and it runs hooks before it asks you to approve the call. Token-goat used that directory as the boundary for which files a hook may open, which allowed any file under your home directory. Token-goat now marks a working directory it had to choose for itself and refuses to use one as a boundary, so these hooks open nothing until VS Code tells them where the workspace is. The rule that decides whether a path is inside the workspace is unchanged, and so is behavior when a folder is open.

### Changed

- **Hooks start faster.** The language adapters that read symbols out of Fortran, COBOL, Pascal, PowerShell and the other 50-odd file types without a tree-sitter grammar now load only where files are indexed. ## [2.9.5] - 2026-09-08

### Security

- **`token-goat ask` now fences and redacts the code it sends to its backend.** The command retrieves indexed symbol bodies and pipes them to whatever `TOKEN_GOAT_ASK_BACKEND` names, which is normally `claude` or `codex`. Those bodies are third-party text like any other file content, and this is the one surface in token-goat where such text reaches a model that holds tools rather than a model reading a tool result, so it is the worst place for it to arrive unmarked. The snippets now go through secret redaction and then the same `<untrusted-file-content>` fence every other surface uses, so a credential sitting in an indexed body is not shipped to the backend and a function body cannot carry instructions that read as part of the question. - **`token-goat doctor` no longer describes an empty MCP root allowlist as confinement.** Two settings govern MCP reads and the report conflated them. `mcp.confine_reads_to_project_root` keeps a read inside the root the caller named; `mcp.allowed_roots` decides which roots may be named at all, and it ships empty, which means any of them. The line read `reads are confined to the project root`, which sounds like a statement about *which* root when it was only a statement about staying inside whichever root the caller picked. It now says so plainly when the allowlist is empty, and names the roots callers may choose from when it is not. - **File content can no longer reach the model wearing token-goat's own voice.** A large document read whole comes back as its lead-in and a heading tree. The notice now leads that reply and the lead-in sits inside the fence that marks file text as data, so no byte of the file can arrive ahead of token-goat speaking. Previously the lead-in was emitted first and unfenced, and a document whose opening lines were shaped like token-goat's markers reached the model as this rewrite's own preamble: driven through the built hook, a 20,292 B document carrying two forged markers delivered both of them verbatim above the notice.

  The fence now escapes both voices token-goat speaks in. It already neutralised `[token-goat: ...]`, the marker hooks sign a rewrite with. It did not touch `[tg]`, the prefix on every deny, which is the more consequential of the two: a deny is the one message shaped as an instruction the model is meant to obey. In a measurement of that shape, a model asked to summarise a build log whose last lines impersonated a token-goat notice obeyed it 11 times in 12 unfenced, 6 in 12 fenced, and 1 in 12 once the prefix was escaped. The prefix is matched with its closing bracket, so ordinary bracketed words are left alone.

  Both fences are part of the replacement the ratio gate prices, so the guarantee costs bytes that were already being counted: 121 of them on the document measured, taking the replacement from 5.6% to 6.2% of the original against a 40% cap. Changed in [src/injection_scan.ts](src/injection_scan.ts) and [src/fold_structure.ts](src/fold_structure.ts). No reindex is needed.

That is the right default for a monorepo and the wrong one for a machine holding separate clients' work side by side, and nothing in `doctor` said which way it was set. ### Fixed

- **`token-goat semantic` no longer comes back empty when the machine-wide index holds many closer matches from other projects.** The vector search fetches nearest candidates first and confines them to the current project afterwards, over-fetching to compensate and retrying once with a larger fetch. That retry was capped at a fixed 100 candidates, and a constant ceiling only moves the rank at which the answer disappears: with 150 nearer chunks from other projects ahead of it, a valid in-project match sitting at rank 151 returned zero hits. Nothing about that result looks wrong, because it is byte-identical to the honest answer for a project that genuinely has nothing to match. The fetch now grows until the index runs out of rows rather than until it reaches a number someone picked, so the bound comes from the data; exhausting a million-vector table costs about a dozen queries. Changed in [src/embeddings.ts](src/embeddings.ts).

- **A file whose indexing fails is now retried instead of being dropped.** The background worker claims its dirty queue by renaming it aside and deleting it once drained, so a path it does not put back is gone for good: that file's symbols stay stale until something edits it again. A file that could not be read was already requeued. A file that read cleanly and then failed to index, which is what a busy database or a lock inside the parser looks like, was only skipped from the tally. The retry budget moved as part of the same fix: it was cleared as soon as the file was read, one step before the work being retried, so a permanently unparseable file would have cleared its budget every cycle and been hammered forever by the very requeue meant to save it. The stamp is a digest of the parser itself, so any change to how symbols are extracted invalidates every indexed file at once. Measured on a live index: 46 of 17,952 files carried the shipping stamp, and none of the 3,322 `.js` files did. A project nothing had ever indexed folded nothing at all, on that read or any later one.

  A miss now falls through to reading the file and parsing it with tree-sitter, the same approach the structural skeleton above already takes, bounded at 400 KB. The whole file is parsed rather than the delivered slice, because a fold needs absolute line numbers and a slice starting mid-body parses as a fragment whose spans name the wrong lines. Replayed over 1,562 real shell reads with no index present, this takes what is withheld from 558,622 bytes to 669,520, three points of everything delivered; across 4,299 real reads of source windows spanning every project, 13.8% to 14.7%. It also beats a freshly built index, because a file read from disk cannot be stale. It costs about 80 ms on a 125 KB file.

  The fallback is refused unless the delivered lines match the file on disk exactly, ignoring a trailing carriage return, and one mismatched line abandons the whole file: once any line has moved, every line number after it is suspect. That makes this stricter than the index path it falls back from, which only ever checked the index against disk and took the delivered text on trust.

- **A read of a source file no longer hashes that file and queues it for reindexing when it cannot fold anything.** With paragraph folding now on, every install enters the fold path on every read. The symbol-span lookup that only a body fold can use ran regardless of whether body folding was enabled, costing a whole-file hash and an index query, and on a miss it appended the file to the reindex queue. A miss is the common case rather than the rare one, so a stock install would have queued most source files for reindex on every read and folded nothing in return. Fixed in [src/fold_delivery.ts](src/fold_delivery.ts).

- **Every bash-compression credit is now priced at the same rate as everything else in the ledger.** `bash_compress:*` savings were converted from bytes to tokens at bytes/3, a third richer than the bytes/4 rate every other kind sums into the same total under. `compressedTokensSaved` now delegates to the shared bytes/4 pricing constant. Fixed in [src/tool_filters/base.ts](src/tool_filters/base.ts).

- **`changed` and `changed --symbol` now credit the diff they replace, not the changed files' full size.** A single invocation could book the entire on-disk size of every file `git diff` touched as savings, even for a one-line edit on a large file -- the same shape `refs` fixed once already for a search-shaped result. Both modes now price against a minimal-context `git diff --unified=0` scoped to the reported files, the artifact an agent would otherwise have had to read to learn the same thing. Fixed in [src/read_commands.ts](src/read_commands.ts).

The type-based tier filter runs in the same place and was not counted as one, so a query narrowed only by type printed its result as an exact total. That query now gets the floor wording too, and only where the filter actually dropped something: a query it passed through untouched still reports the exact total. Fixed in [src/read_commands.ts](src/read_commands.ts).

- **A file with more than 500 symbols is now indexed in full.** Every language adapter stopped emitting symbols at 500 per file and said nothing, so a large SQL schema, GraphQL schema, Makefile, Terraform module, or Protocol Buffers file lost its later declarations from the index with no way to tell short of noticing they were unfindable. This repo's own largest indexed file already sat at 439 symbols, 88% of the old cap, and growing. Measured before raising it: a synthetic 35,000-statement (1.7 MB) SQL file, just under the separate `indexing.large_file_skip_kb` byte-size gate that already bounds worst-case file size, indexed in 2.4 seconds and grew the project database by 11.7 MB. That cost is acceptable for a limit this rarely reached, so the cap is raised rather than merely disclosed: from 500 to 10,000 symbols per file, in `common.ts`'s shared `makeSymbolEmitter` and in the ten adapters (`sql_idx.ts`, `graphql_idx.ts`, `makefile_idx.ts`, `proto_idx.ts`, `terraform_idx.ts`, `html.ts`, `sfc_idx.ts`, `apex.ts`, `bash_idx.ts`, `powershell_idx.ts`) that each carried their own duplicate copy of the same 500 constant. **Upgrading reindexes.** The cap change is in every language adapter, so every indexed file is read again once on first use after upgrading; nothing extracted from an already-under-cap file changes; the reparse happens because the parser's fingerprint changed. See [src/languages/common.ts](src/languages/common.ts).

- **A block-comment marker inside a template literal no longer folds the code beneath it away.** The comment planner tracked whether it was inside a comment but not whether it was inside a string, so a line whose text began with `/*` opened a comment run wherever it appeared, including inside a template literal. The run stayed open until some later line happened to contain `*/`, and everything in between was replaced by one line reading "more comment lines". Sweeping this project's own tree found it live: `tests/languages.test.ts` folded 763 rows that way, 598 of them executable code, opened inside a SQL literal and closed 764 rows later inside an unrelated protobuf fixture. The planner now follows template-literal state across lines, in the languages where a template literal exists, and a marker inside one is read as the string content it is. A genuine comment block folds exactly as before. Fixed in [src/code_fold.ts](src/code_fold.ts).

- **A paragraph fold now applies only to markdown.** The fold was offered to `.rst` and `.txt` as well, matching the set that gets a "read this with `section` instead" hint. Pointing a reader at a narrower command is safe on any document; folding one is only safe where the planner can recognise the structure it must leave alone, and every rule it has for that is markdown: fences, headings, pipe tables, block quotes. A `.txt` has no markup for those rules to find, so a wrapped log record read as a paragraph and folded to its first sentence, discarding the stack trace under it. `.rst` marks its literal blocks by indentation and `..` directives that none of those rules see either. Fixed in [src/fold_delivery.ts](src/fold_delivery.ts).

- **Running a fold's own pointer now returns what it promised.** A folded paragraph and a folded comment block each print a ranged Read of the exact span removed, and that Read came back through the same fold. For a paragraph that was a fixed point: the one row it returned was the same over-long paragraph, folded again to the opening sentence it was already showing, and no number of runs would resolve it. A read carrying an explicit offset or limit is now left alone, which is the rule the comment notice already described and the code did not follow: a reader who asks for a range has narrowed the read themselves. Function bodies still fold in a ranged read, their pointer being a `token-goat read "file::symbol"` that does not come back through here. Fixed in [src/fold_delivery.ts](src/fold_delivery.ts) and [src/hooks_read.ts](src/hooks_read.ts).

- **Compressing a very large command output now keeps the end of it, where the answer usually is.** Every filter shares one cap that bounds how much output it will inspect, and past 500 KB that cap kept the first 500 KB and discarded the rest. The verdict of a command is almost never at the front: a test runner's summary and failure section, a compiler's last diagnostic, an installer's result all land at the end. Running this project's own suite produced 2,406,737 bytes whose final 200 hold `Test Files 577 passed (577)` and `Tests 12100 passed | 17 skipped (12117)`, and what arrived was 5.5 KB of mid-run console output carrying neither line. A failing run was worse, because vitest prints its failures at the end too, so a red suite arrived reading green.

  The cap now splits its budget between the head and the tail and names how many lines it dropped in between. The split is even: the head holds the command echo and the earliest errors, the tail holds the verdict, and nothing measured here justified favouring one over the other. Cuts land on line boundaries, so no line is presented as whole when it is half, and no character is split. Same suite, same 99.8% reduction, and now with all four summary lines and the failing test's own name and assertion in what comes back. Fixed in [src/tool_filters/helpers.ts](src/tool_filters/helpers.ts) and [src/tool_filters/base.ts](src/tool_filters/base.ts), so every filter gets it at once.

  The token budget that shrinks a delivered body under context pressure had the same shape, and would have undone the fix above wherever it applied: a 1,071,063-byte run capped to 2,000 tokens came back holding its first 57 lines and nothing else. It now keeps both ends too. All four callers pass command output, so that is right for every one of them.

- **A failure at the end of a long output now gets the context that explains it.** After compression, output over 1,000 lines is thinned to its head, its tail, and a few lines around each of the first ten error-shaped lines found. In a long log those first ten are usually incidental, a line that merely contains the word `error`, and the failure that actually stopped the run is far past them. On the failing run above the filter kept 60,720 lines holding 139 such matches: the first ten fell between lines 379 and 3,813, while the failing test sat at line 60,685. The result named a failure count without naming the test. The budget is now taken from both ends of the list rather than the front, because which end matters depends on the tool: a compiler's first error is usually the cause and the rest cascade from it, while a test runner's failure is the last thing printed. The same run now comes back with the file, the test name and the assertion, in 4,188 bytes. Fixed in [src/tool_filters/helpers.ts](src/tool_filters/helpers.ts).

- **A resource table now keeps the row that is not healthy, wherever it sits.** `kubectl get` and `aws --output table` results are cut to their first ten rows. Nobody runs those commands to read the first ten rows: they run them to find the one thing that is not working, and which line that is depends on the order the API happened to answer in. A sixty-pod listing with the broken pod fortieth came back as forty healthy rows and a count. Rows carrying a not-ready status are now taken first, the remaining budget is filled from the top, and the survivors are printed in their original order so it still reads as a table. The same listing now returns nine running pods, the `CrashLoopBackOff` one, and a line saying one row was kept for its status. The statuses recognised are drawn from what those two tools actually print rather than from the general error-signal pattern, which matches `error` as a substring and would have promoted a healthy pod for being named `error-handler`. Fixed in [src/tool_filters/helpers.ts](src/tool_filters/helpers.ts).

- **Two more caps stopped spending their whole budget on the front.** `kubectl diff` walks manifests in the order given, so a fifty-line cap with no tail dropped every resource past the first few outright; it now keeps thirty-five lines from the front and fifteen from the end. A commit's patch under `git log -p` runs file by file, so a thirty-line cap showed the alphabetically first file and nothing else; it now keeps a tail as well, weighted towards the head because a hunk's opening carries the file header that says what changed. Fixed in [src/tool_filters/containers.ts](src/tool_filters/containers.ts) and [src/tool_filters/git.ts](src/tool_filters/git.ts).

- **A suppressed `rg` match group now says whether it lost on merits or on filename.** Context-mode searches keep the five groups with the most matches, and a sort leaves equal scores in the order ripgrep printed them, which is alphabetical by path. Where the cut falls between two equal scores the survivors were picked by filename, and the note said only that groups had been suppressed. A search where every file has one match is exactly that case, and it is the common one. The note now distinguishes the two. Fixed in [src/tool_filters/shell_file.ts](src/tool_filters/shell_file.ts).

- **The two steps after the cap no longer put the head bias back.** Compression runs as a fixed sequence, and keeping the end of a large output is only worth anything if the steps downstream of it agree. Two did not. The final byte cap every filter passes through was a plain head trim, so on any output large enough for it to bind it deleted the tail the line cap immediately above it had just chosen to keep. The line cap had a smaller version of the same problem: it gathers a few lines of context around each error signal it selected from both ends, then sorted that set by line number and kept the front of it, which is the earliest signals by construction, so a budget too tight for all of them dropped the late-file failure first. The byte cap now keeps both ends, and context is now gathered signal by signal in an order that alternates front and back and walks the back signals from the very end inwards, stopping when the budget runs out. A 7,419,007-byte failing run comes back as 1,200 bytes carrying the failing test's name, its assertion and all three summary lines. Fixed in [src/tool_filters/helpers.ts](src/tool_filters/helpers.ts).

  The both-ends clamp itself also now charges its own elision marker against the budget it was given. The marker is about forty bytes, which is immaterial against the 500 KB input cap it was written for and decisive for a caller passing sixty: a fifty-line input capped at sixty bytes came back at eighty-three. Where the reservation leaves no room to split, the cap falls back to a single character-safe prefix, which is the only shape that fits.

- **A match count taken from a shortened search now says it is a floor.** Searching with `grep` or `rg` over more than a few dozen hits returns a per-file tally instead of the lines, and that tally is the answer the search was for, not a description of what compression did to it. It was counted after the 500 KB cap above had already thrown work away, and printed flat. A search of 9,000 matching lines across 40 files reported `grep: 4685 matches across 40 file(s)`, with the per-file numbers understated by the same margin. The same search now reads `grep: at least 3653 matches across 40 file(s) (counted over a truncated input; per-file counts below are lower bounds)`. A search whose output fits is unaffected and still reports its exact total. Filters learn about the cap through a new optional argument to `compress`, so the other eighty-odd of them need no change. Fixed in [src/tool_filters/shell_file.ts](src/tool_filters/shell_file.ts) and [src/tool_filters/base.ts](src/tool_filters/base.ts).

- **Folding a range of a file now returns every line the range asked for.** A fold is planned from the symbol spans the index holds, then clipped to the lines actually delivered, which is what lets it work on part of a file at all. Clipping is not enough on its own. When the requested range sits entirely inside one long function, every delivered line is body. The clip removes nothing, and the whole range collapses to a single line pointing at a declaration the reader never saw. A request for lines 100 to 140 came back with none of them. Nothing shipped could reach this, because the one caller declined ranged reads outright, and it had to be settled before the shell side could fold anything, since ranged reads are 14.61 MB of that 15.61 MB and declining them there would have meant declining the work. A body is now folded only when its own declaration is among the lines delivered. A whole-file read starts at line one, so no span can fail that and nothing about it changes. Fixed in [src/code_fold.ts](src/code_fold.ts).

- **A shell read no longer records a rewrite that was not sent.** What a shell read delivered is cached so a later read of the same file can be matched against it. The cache was written before the last check that decides whether a rewrite is worth sending, so when that check declined, the full output went to the reader while the shortened copy went to the cache. The direction is safe, since the worst it can do is show a line twice. It is now also correct: what goes into the cache is what was sent. Fixed in [src/hooks_bash.ts](src/hooks_bash.ts).

- **A shell read run after `cd` into another directory no longer matches a same-named file in the directory it started from.** The session's record of what it has already shown is kept per file, and a read written as `cd docs && sed -n '1,40p' README.md` was filed under the `README.md` beside the shell rather than the one in `docs`. Two files can hold identical text, which is the whole reason that record is per file, so the wrong entry could answer a read of a file it knows nothing about. The directory each leading `cd` moves to is now resolved in turn, the way the suggestion hints have always resolved it. Changed in [src/hooks_bash.ts](src/hooks_bash.ts).

### Changed

- **Body folding now ships on.** `hints.fold_code_bodies` has been off since it was added, for a stated reason: the bytes a fold saved were recorded and what it folded was not, so the other half of the trade, how often a reader has to come back for a span that was folded away, could not be worked out from stored data. Recording the folded symbols closed that gap, and the join has now been run.

  Over 823 folds that named a symbol, 62.3% were followed within half an hour by a `read` of that symbol. On its own that reads as a heavy cost. It is mostly not: 55.8% of the same folds were *preceded* by a read of the same symbol in the same window, which no fold can have caused, and pairing each folded symbol with a different fold's timestamp scores 24.3%. A symbol gets folded because it sits in a file the session is working through, and that is the same population that gets looked up. What the fold itself provokes is the 6.6-point excess, against a saving of a whole function body each time.

  It stays project-locked: a checked-in `.token-goat.toml` cannot set it either way, because how much of its own source a repository shows a reader is not the repository's call. Your own config and `TOKEN_GOAT_FOLD_CODE_BODIES` still set it freely. Set `fold_code_bodies = false` under `[hints]` to go back to whole bodies.

  `token-goat doctor` no longer reports the environment turning this on as a weakened posture, on the same grounds as the folds that already shipped on: `true` restates the default and `false` shows the reader more, so neither direction weakens anything. It still reports which layer decided the value.

- **`outline` now ends each symbol's note on a complete sentence.** The note was cut at 140 characters, on the understanding that this keeps roughly the first sentence. It does not. Measured over 448 documented symbols in this project's own source, cutting at the cap leaves 297 of them ending mid-clause, which costs the full 140 characters and still does not finish the thought.

  A docstring's first sentence is its summary, by convention in every language token-goat parses, so that is where the cut goes now. Where no sentence ends within the cap, the old behaviour stands and the note is cut at the last word boundary before it. Notes come out 10.6% shorter overall and 250 of the 448 now end on a complete thought, against 151 before. None came out longer. An ellipsis still marks anything dropped, so a note that was already a single sentence is unchanged. Changed in [src/read_commands.ts](src/read_commands.ts). `--json` is untouched and still carries the whole docstring.

- **A Read of part of a file now folds long bodies, instead of being passed over.** Folding declined any Read carrying `offset` or `limit`, on the grounds that it is already narrow enough. That holds for a read of thirty lines in the middle of a function. It does not hold for the shape that produces most of them: a large file paged through a window at a time, which is a whole-file read wearing a range. Measured over 814 sessions, ranged reads of source files number 4,801 and carry 14.89 MB, and 84% of them open a window of twenty lines or more. All of it was passed over.

  What decides now is the same rule the shell side already uses: a body is folded only when its own declaration is among the lines delivered. A window sitting inside one function fails that test and every line comes back, which is the behaviour the old rule was reaching for. A window that opens on a declaration folds it. Reading 55 lines of this project's `src/served_lines.ts` from the line `planServedElisions` is declared on now returns 10.

  A fold names the range it removed, so those line numbers have to be the file's own. Claude Code reports where a window starts, and that is what the numbers are taken from: across 798 ranged reads, 566 carried it and 562 of those agreed exactly with the offset asked for. The four that disagreed were negative offsets, which get clamped to the first line. Where the two do not agree, or where nothing reports a start at all, the read passes through whole rather than being folded against numbers that were guessed. Changed in [src/hooks_read.ts](src/hooks_read.ts). No reindex is needed.

- **A single enormous line in shell output is now shortened, whatever command produced it.** Output was checked two ways before delivery: how many lines it has, and how many bytes it is altogether. One very long line passed both, so a body of a few thousand bytes that happened to be one minified line, one base64 blob, or one JSON record written on a single line went through at full length. Only the grep filter had an answer to this, a clip centred on the match, and every other command had nothing. The check now runs once, for all of them, just before the line count. A line that an earlier step already clipped is left alone, so no line ends up carrying two notices. The limit is 1,000 characters: measured over 814 sessions holding 77.1 MB of shell output, lines longer than that hold 1.62 MB, of which 1.32 MB sits outside grep and so had nothing clipping it until now. Such lines are almost all machine-written. A shorter limit reaches more, but it starts cutting real content: a wide table row, a long list of paths. What is delivered is what gets kept, so those characters would not be recoverable afterwards. A 5,508-byte body whose one long line was 5,008 characters now comes back at 1,597. Changed in [src/tool_filters/base.ts](src/tool_filters/base.ts) and [src/tool_filters/helpers.ts](src/tool_filters/helpers.ts). No reindex is needed.

- **A `cd` on its own line above a command is now seen through, like `cd ... &&` always was.** Only the `&&` form was recognised, so in a multi-line block every rule that looks at what a command does saw `cd` and stopped there. The read underneath it was invisible: not deduplicated against what the session had already shown, not compressed, not offered a narrower command. This is the commonest way a multi-line block starts. Measured over 201 sessions, reads written this way carry 1.26 MB of lines that had already been delivered, on top of the 1.93 MB reachable before. `cd dir; command` is recognised on the same terms. Changed in [src/hooks_bash.ts](src/hooks_bash.ts).

- **A folded read now records which file and which symbols it folded.** The ledger already stored how many bytes each fold saved, and nothing about what it removed. That left the other half of the trade unmeasurable: how often a reader has to come back for a span that was folded away could not be worked out from stored data, however long the feature ran. That missing number is the reason `hints.fold_code_bodies` ships off by default, and nothing about running it for longer was going to produce it.

  Each `read:body_fold` row now carries the file and the folded symbol names, in the same `file::symbol` shape a recovery read would use, so a later `token-goat read` can be matched back to the fold that prompted it. A folded comment block has no symbol to name and carries the line range its notice points at instead. The text is capped so that one file with hundreds of folds cannot bloat a row, and a file whose path alone fills the cap still records the path, which is the part a match needs. Recorded in [src/code_fold.ts](src/code_fold.ts) and passed through the shared rewrite helper in [src/hooks_common.ts](src/hooks_common.ts), which accepted this value from other callers and dropped it on the way to the database. Rows written before this release stay empty. No reindex is needed.

- **A read that cannot fold because the index is behind now queues that file, so the next read of it folds.** Folding a function body needs line spans from the index, and those spans are only trusted when both the file's content and the parser that produced them still match. When either has moved on the read passes through whole, which was the right call and also a dead end: nothing marked the file for reparsing, so unless something happened to edit it, every later read of it missed for the same reason. Measured over 201 sessions of real reads, 32 whole-file reads folded and another 22 would have folded once reindexed, which is 76% more folded bytes than the feature currently produces. The queue entry is written on the way past, and the background worker picks it up on its next pass about two seconds later. Only files in a language token-goat recognises are queued. Nothing needs to be run by hand, and this is not a reindex of the project: it is one file at a time, as reads reach it. Changed in [src/hooks_read.ts](src/hooks_read.ts).

- **A shell read of a file now withholds only the lines already shown, instead of all of them or none.** Reading a file with `sed`, `cat`, `head` or `tail` was already checked against what this session had delivered, but the check was all-or-nothing: it fired only when the whole output sat inside one earlier read, so `sed -n '100,140p'` after `sed -n '120,160p'` was nested in nothing and shipped every line again, half of them for the second time. Overlapping reads that do not nest are the ordinary case, and the shell is where most file reading actually happens. Measured over 201 sessions, the old rule caught 0.49 MB across 211 of 3,848 range reads, while another 1.96 MB of already-shown lines went out a second time inside reads that merely overlapped.

  Each already-shown stretch is now replaced in place by one line giving its line numbers and the command that returns it, and everything else arrives untouched. On a real pair of overlapping reads of this project's README, 56% of the second read was withheld. Line numbers come from the command's own ranges rather than from counting rows, so they name real lines in the file; a `tail` says nothing about where its window starts, so it is left alone rather than annotated with a guess. Only whole lines count as shown, so a read returning a fragment of a line keeps it. The search is shared with the read hook, which already worked this way: it moved to the new [src/served_lines.ts](src/served_lines.ts), and the shell side that calls it is in [src/hooks_bash.ts](src/hooks_bash.ts). No reindex is needed.

- **Paging a file with several `sed` ranges in one command now counts as one read of that file.** A file is often read in pieces: two or three ranges of it in a single command, with an `echo` between them to mark the breaks. Every rule that matches a read against what the session has already shown looked at one command at a time, so this shape was invisible to all of them and its lines went out again in full. Measured over 201 sessions it carries 0.64 MB of already-shown lines, on top of the 3.19 MB reachable before. On a real overlapping pair of reads of this project's README, 55% of the second read was withheld.

  A command that ranges over two different files is left alone. The record of what has been shown is kept per file, and filing one read under two of them would let a read of one answer for the other. Because an `echo` between the ranges can print any number of lines, no delivered line can be tied to a numbered line of the file, so the notice standing in for a withheld stretch counts its lines rather than naming them: a wrong line number reads exactly like a right one. Changed in [src/hooks_bash.ts](src/hooks_bash.ts). No reindex is needed.

- **A fold notice now names the file relative to the project root instead of by full path.** The notice appears once per folded span and repeats the path each time, so on Windows the path was most of what the notice cost. Over the same 201 sessions the notices totalled 10.9 KB by full path against 9.0 KB relative. A file outside the project, or a read with no project around it, still shows the full path, and either way the notice is still a command that runs as printed. Changed in [src/hooks_read.ts](src/hooks_read.ts).

## [2.9.4] - 2026-09-06

### Added

- **`token-goat doctor` now reports how much of a project's index was written by a different build of the parser.** Every indexed file is stamped with a digest of the extraction logic that parsed it, and a mismatch already counts as stale everywhere it matters: `token-goat index` reparses the file, the background worker reparses it, and the new body fold refuses to fold it. What nothing reported is how many files are in that state. The stamp only refreshes when something touches the file, so after an upgrade a project goes on answering `symbol`, `read`, `outline` and `skeleton` from the previous extractor with no sign that it is doing so. On the index this was found on, 95% of one project's 1,155 files were behind, and 71% of 17,508 files across every project. The check warns past a quarter and names the fix: a plain `token-goat index` in that project, which is enough on its own, since a parser mismatch reparses without `--force`.

- **Long function bodies and long comment blocks can now be folded out of a source file the first time it is read.** Every existing way token-goat shrinks a read depends on having seen the file before: it withholds lines already delivered, or turns a repeat read into a pointer. A first read has no earlier copy to compare against, and first reads are the large majority of what the read hook handles. The new `hints.fold_code_bodies` setting keeps each function's declaration and its first eight lines, replaces the rest with a single line naming the symbol, the exact line range removed and the command that returns it, and leaves everything outside a folded span exactly as it was. Imports, signatures, type declarations and short comments survive untouched. Measured on this repository's own source, counting only the first 2,000 lines of each file because that is where a Read stops: of 256 files, 229 fold, and 43% of what a read of them delivers is removed.

  It replaces the result of a read that succeeded rather than blocking the read. Refusing a read costs a round trip, and the agent may fetch the file another way or give up on the task; changing what the same successful call returns costs neither.

  Folding only the body sits between two worse options. A signatures-only view is about an eighth of what a read delivers, so serving one withholds the other seven eighths while still looking like an answer. Keeping the first lines of each body leaves a reader everything a signature list has, plus enough of each implementation to judge whether it needs the rest, and the rest is one named command away. A long top-level constant folds on the same reasoning: its declaration line says what it is and the rest is data.

  Comment blocks fold on the same terms, which reverses an earlier decision. Comments are 46% of this repository's source bytes and they carry the design rationale, so stripping them would be the largest saving available and the least honest one. A fold is not a strip. The first two lines of a block stay, which is the summary a doc comment opens with and the title of a banner, and everything under them becomes one line giving the exact range to read back, so the contract a reader needs in order to decide whether they want the rest is still on screen. A block has to run twelve lines before any of this applies: an ordinary note is left alone, an essay is not. Blocks are found in the delivered text rather than in the index, which is why they fold on a file the indexer has never seen, the case that used to return nothing at all. Which lines count as comment is decided by the file's extension and never by sniffing the content, because a run of lines starting with `#` is a comment block in Python and a run of headings in Markdown, and folding a document's headings would destroy the one structure a reader navigates by.

  It is off by default. On a first read there is no earlier copy for the reader to notice an omission against, and how often a reader has to go back for a folded body has never been observed. A repository cannot switch it on either: `hints.fold_code_bodies` is refused from a checked-in `.token-goat.toml`. How much of its own source a repository shows a reader is not the repository's call. Your own config and `TOKEN_GOAT_FOLD_CODE_BODIES` still set it freely, and `token-goat doctor` reports it when the environment turns it on.

  Four things stop a fold. A read that already names an offset or a limit is surgical and is left alone. A file holding anything that looks like a secret is passed through whole rather than handed back redacted. A class or interface is never folded, because its span covers the member signatures the fold exists to preserve, and neither is a type alias, which is a union or an object shape and so covers the same thing. And a file whose index no longer matches what is on disk loses its body folds, checked on both the content digest and the digest of the parser that produced the rows: a stale line span cuts in the wrong place, and a first read gives no way to catch it. Its comment blocks still fold, since those are read off the text that just arrived and cannot be stale.

  One thing had to be fixed for this to be safe. The record of what a read delivered was taken from the file on disk, which is the same text right up until something rewrites it. After a fold it is not, and the record would have claimed the folded lines were shown; a later read coming back for exactly those lines would then have had them withheld as already seen, from a reader that never saw them once. It now records what was actually delivered, in [src/hooks_read.ts](src/hooks_read.ts) alongside the new [src/code_fold.ts](src/code_fold.ts). No reindex is needed.

### Removed

- **A compression path that was built, tested, fixed four times, and never once run.** `tryWrapCompoundSegments` took a command joined by `&&`, split it, and wrapped each recognized part on its own, so `git diff && git log` would come back with both halves compressed instead of neither. It arrived in June as part of the output-filter framework, and the commit that added it said plainly that nothing was wired to it yet. The rest of that framework was connected over the following weeks. This one function never was, and the import line in [src/hooks_bash.ts](src/hooks_bash.ts) that names eight of its siblings reads as complete without it.

  Nothing failed, which is why it lasted. Six tests covered it and all six passed. A test that hands the function its own wrapper proves the function agrees with the test, which is just as true of code that nothing calls. Four separate fixes went into it while it was unreachable, and two of those said so in their own changelog entries before patching it anyway, on the grounds that it read as deliberate code.

  It was measured before being removed. Applying the real function to every command in a long session history accepts 1.6% of them, and set against what the existing whole-output compressor already delivers, connecting it would have recovered under a megabyte over ten weeks. The one shape it looked built for, `cd somewhere && run something`, is already handled: the hook strips that prefix before it looks at anything, so the command arrives as a single command and compresses the ordinary way. Against that megabyte it needed a second wrapper protocol beside the existing one, a process spawn per part on every matched command, decided before the command runs and therefore before anyone knows the output is big enough to be worth compressing, and it produced output the post-run step could not unwrap, so a second pass would compress the already-compressed text and drop the inner notices. Removed with its two private helpers and its tests, from [src/tool_filters/dispatch.ts](src/tool_filters/dispatch.ts). The quote-aware helpers the live single-command path shares with it, `hasUnquotedOperator` and `shlexSplit`, stay where they are. No reindex is needed.

### Fixed

- **Both of the read hook's rewrites were dead code on Claude Code, because they parsed a rendering the hook never receives.** A Read result reaches a hook as the file's own text in `tool_response.file.content`; the numbered `cat -n` form is applied afterwards, for display. The two of them, the new body fold and the elision of lines already delivered, both looked for that numbered form and treated its absence as nothing to work with, so both declined on every real read. The body fold booked no saving at all across a full session while the rest of the read hook ran normally, and the read that produced this entry was one of them.

  Neither rewrite needs the rendering. What they need is one row per line with a line number attached. A result that arrives unnumbered is now read as exactly that, numbered from the delivered start line, and written back unnumbered into the field it came from: a numbered rendering there would be numbered a second time on display. Both forms work, so a harness that does send numbered text is unaffected. In [src/hooks_read.ts](src/hooks_read.ts). No reindex is needed, and nothing about an existing index changes.

  Every test agreed with the bug. Each one built its own numbered fixture from the regular expression the parser uses, and a comment above one of them stated that numbering is what the Read tool delivers, written from that expression rather than from a Read. Tests like that only prove the parser matches text shaped the way the parser expects. The new cases in [tests/code_fold.test.ts](tests/code_fold.test.ts) use the envelope read off real session records instead, where all 104 Read results carried unnumbered text and none carried a numbered one.

- **A Read asking for five lines of a compacted document got a summary of the whole thing instead.** When a reference doc has a compact sidecar built by `compact-doc`, the read hook serves that summary in place of the file. It was doing this for every read of that file, including ones that named a line range. A read of `CLAUDE.arch.md` for lines 50 to 54 came back with the compact of the entire document, starting at line 1, and nothing told the caller its range had been dropped. The 5 lines asked for are 192 bytes; the compact served instead is 9,295, so on a ranged read the mechanism cost about 48 times what it saved and answered a question nobody asked.

  A ranged read is already surgical, which is the exact reason the subagent markdown check further down the same file leaves one alone. That rule was written once and applied in one of the two places that needed it. The intercept in [src/hooks_read.ts](src/hooks_read.ts) now skips any read carrying an offset or a limit, and the read proceeds normally. What made this hard to see is that the one exemption anybody had thought about was tested: there is a case in [tests/hooks_read.test.ts](tests/hooks_read.test.ts) proving a `Grep` is left alone, written when that exemption was added. Ranged reads never got one. The new test covers all three shapes an offset or limit can arrive in, and asserts first that the same file read whole still is intercepted, so it cannot quietly pass by the feature breaking entirely.

  The served message now also says what the extract leaves out. It is built by taking each heading and the first couple of sentences under it, so front matter and any prose above the first heading are gone entirely, sections are cut short, and long code blocks stop after ten lines. Front matter matters more than it sounds: a doc whose title, version or schema lives in its YAML header hands the agent a compact where that block never existed. The old wording called it a compact and offered `--force` and `--show`, both of which return the same summary again, so a caller missing something had nothing that would get it. The message now names what is dropped and points at a line range or `token-goat section` for one heading in full. No reindex is needed.

- **The saving claimed for a compacted document was quoted as 80 to 95 percent, and most documents do not reach it.** The figure appeared in four places, including the README and the command reference. Measured across the 44 markdown files in this repository over 4 KB, the median saving is 67% and only 13 of the 44 land inside the advertised band. The spread runs from 5% to 99%, because the compact keeps prose sitting under headings and a document made mostly of tables or code leaves it little to keep: the README saves 66%, [CLAUDE.arch.md](CLAUDE.arch.md) saves 91%. The claim now reads 60 to 95 percent with the median beside it, in [README.md](README.md), [docs/cli.md](docs/cli.md), [src/doc_compact.ts](src/doc_compact.ts) and [src/hooks_read.ts](src/hooks_read.ts). No reindex is needed.

- **`hint-stats` printed two kinds of percentage in one column with nothing to tell them apart, and compared straight across they say the opposite of what is true.** Some hints ask the agent to run a specific command instead of what it was about to do, and those score only when the agent runs it. Others ask the agent not to do something at all, and those score by absence: the watch window closing with no repeat read is the compliance the hint asked for, so it counts as a success. Both landed in the same `efficacy` column as a bare number, where a category scored on an absence sits near the top and one scored on an action sits near the bottom. Nothing about that ordering means the first kind of hint works better. It means the two are measured on different scales, and this table was read the other way before anybody checked the scoring.

  The source comment in [src/hint_stats.ts](src/hint_stats.ts) already said the split was disclosed both there and in the command's output. Only the first half was true. The absence-scored rows now carry a `*` and the table explains underneath what it means, so the two scales are visible as two scales. [tests/cli_hint_stats.test.ts](tests/cli_hint_stats.test.ts) holds both halves of it: the marked row must be marked, an action-scored row must not be, and the note must stay quiet when no absence-scored category has fired, since a note that always prints stops being read. No reindex is needed.

- **Four rows of the architecture doc's component map pointed at files that are not there.** `CLAUDE.md` tells an agent to read [CLAUDE.arch.md](CLAUDE.arch.md) on demand to find where a thing lives, so a row naming a path that does not exist sends the reader nowhere and, on the published docs site, returns a 404. Two rows named a module whose contents had moved: the git-history hints are in [src/read_commands.ts](src/read_commands.ts) and the `ask` command is registered inline in [src/cli.ts](src/cli.ts). One named a file that never existed under that name after the TypeScript port, since the daemon's pid handling and its detached entry points sit in [src/worker.ts](src/worker.ts) beside the loop they start. The last named a file deliberately retired on 2026-07-05, whose row outlived it by two months.

  A stale link fails quietly, which is why all four lasted: the table still renders, it still looks complete, and the only symptom is a reader arriving at nothing. [tests/guards/doc_links_resolve.test.ts](tests/guards/doc_links_resolve.test.ts) now checks every repo-relative link in every living document against `git ls-files`, which is the right oracle rather than the filesystem: this repository is developed on a case-insensitive one that resolves `security.md` against `SECURITY.md` perfectly happily, while the docs site and a Linux checkout do not. The two changelogs are out of scope by design and the guard says so, because an entry describing a past release correctly names the file that release touched even after the file is gone, and rewriting those links would falsify the history the file exists to keep. No reindex is needed.

## [2.9.3] - 2026-09-04

### Security

- **The image decoders now refuse a file that would make them allocate gigabytes, hang, or return the wrong picture.** Token-goat shrinks images before the model sees them, and it recently swapped its native image library for one written in TypeScript. The old library enforced the pixel limit inside the decode. The new check reads the width and height out of the file's header and multiplies them, which is a much weaker thing to know, because it says nothing about how many frames an animation has or how far a compressed stream expands. Three files got past it. A GIF of 11.5 KB claiming a 1600 by 1600 canvas and 500 frames asked for 5.1 GB, since every frame is a full canvas and all of them are held at once. A PNG of 510 KB claiming 4000 by 4000, which is exactly the limit, expanded its image data to 512 MB where 61 MB was needed, and 512 MB was simply the size picked for the test file rather than a ceiling the code imposed. Every buffer is now checked against a fixed 256 MB limit before it is allocated, and the PNG check is exact rather than approximate: the file format says precisely how many bytes those dimensions can produce, so anything beyond that is not data the picture needs.

  A 64-byte TIFF was worse than any of them. Pages in a TIFF form a chain, each one holding the position of the next, and nothing stops a file pointing back at a page already read. Token-goat followed the chain without remembering where it had been, so it never came back. It allocates nothing while doing this, so the operating system never steps in and stops it: for a file being read by an agent, that is a read that simply never finishes. Token-goat now remembers the positions it has visited and stops when one repeats.

  The limit covers what the shrink writes as well as what it reads. Reading an animation costs four bytes per pixel per frame; writing the smaller copy costs five, so between 22 and 26 frames of a 1600 by 1600 animation the file being read was inside the limit and the copy being written was not, and the memory used was the two added together. Measured against the installed build, 21 frames of that size still shrinks, from 1,029 KB down to 78 KB, and 22 frames is now declined. The still-image path is fixed alongside it: pulling one frame out of a GIF used to decode the whole animation and throw the rest away, so it now asks for the one frame it wants.

  Two quieter faults are fixed with them, and they are the worse pair. The PNG decoder accepted several formats it cannot actually read and then read them anyway, so a 16-bit image came back as different colours: an opaque red pixel turned into a transparent yellow one. The BMP decoder accepted every colour depth but could only draw two of them, and returned a fully blank image for the rest without reporting a problem. In both cases token-goat re-encoded the wrong picture and handed it to the model as the contents of the file. Both now stop rather than guess, which means the original image is passed through untouched, and an untouched original is the right picture. No reindex is needed. See [src/image_engine.ts](src/image_engine.ts).

- **The test suite now runs a static pass over every interpreter sink in the source tree, and CI runs the dataflow half.** Every structural guard in this repository up to now records a bug somebody already found, which leaves the shapes nobody has looked at uncovered. [tests/guards/dangerous_sinks_are_named.test.ts](tests/guards/dangerous_sinks_are_named.test.ts) is keyed on shape instead. It asserts that `eval`, `new Function`, `node:vm` and the string form of `child_process.exec` appear nowhere in `src`, with no way to exempt one, and it requires every `shell: true` and every `execSync` to be listed with the reason it cannot be an argv array instead. All four of the first group are at zero today and nothing said so, which meant the first one added would have arrived in an ordinary review with nothing objecting.

  The other half of a security scan asks whether untrusted data reaches one of those sinks, which needs dataflow across files and a query engine far too heavy for a suite that also runs on Windows and macOS. That half is [a CodeQL job](.github/workflows/codeql.yml), on pushes to main and on a weekly schedule, since a query pack updated next month can find a bug in code that has not changed since. Every way that job can quietly stop looking leaves a green check and an empty alerts list, which reads like good news, so [tests/guards/codeql_scan_is_wired.test.ts](tests/guards/codeql_scan_is_wired.test.ts) holds it to the extended query suite and to not excluding the directory it exists to scan.

  `eslint-plugin-security` is the obvious thing to reach for here and was measured before any of this was written: 1,691 findings across 177 of 255 source files, 96% of them from three rules that do not fit this codebase. One duplicates a stronger check `npm run lint` already runs, one flags reading a file whose name came from a variable, which is the product, and one flags every computed array index. A suppression list of that size is worse than no rule, because it reads like a decision. The measurement is written down in [CLAUDE.arch.md](CLAUDE.arch.md) so the choice does not get made again blind. No reindex is needed.

- **The Copilot CLI hook shim now rejects an event name it never declared, and a guard covers every bridge that builds a shell command from one.** Each bridge installs a small hook shim, and its last resort is to run `token-goat hook <event>` through a shell. The Copilot CLI shim looked its event name up in a table and went ahead if the lookup returned anything. A plain JavaScript object answers that lookup for eight names it was never given, among them `constructor` and `toString`, so those resolved to a function, were pasted into the command, and reached the shell. None of the eight contains a character a shell treats specially, so the result was a command that failed rather than a second command that ran. The shim now asks whether the table actually declares the name.

  The rest of the surface was audited at the same time rather than by diff. Four of the seven bridges already check the name against a fixed list. Two check nothing and are safe only because every place that calls them passes a fixed string, which is true of today's callers rather than of the code. [tests/guards/shell_concat_is_constrained.test.ts](tests/guards/shell_concat_is_constrained.test.ts) now holds all three shapes, and checks the two unvalidated ones at both steps: every caller passes a fixed string, and the step that actually builds the command passes along only the value the first check covers. A new bridge that skips the check fails the guard rather than shipping. No reindex is needed.

- **Background shell and background task poll deltas are now fenced, and a guard now checks every place token-goat replaces a tool result.** When `BashOutput` or `TaskOutput` is polled a second time, token-goat replaces the repeated output with just the new bytes under a short notice of its own. The notice and the new bytes were glued together with nothing between them, so a background process that printed a line in the marker's shape was writing text the model would read as token-goat's. The notice now sits above the fence and the process output inside it, the same arrangement compound Bash output already uses.

  The wider problem was that nothing checked for this. [tests/guards/substituted_output_reaches_fence.test.ts](tests/guards/substituted_output_reaches_fence.test.ts) now walks every function that hands the model a replacement body and requires it to either fence what it kept or appear in a list with the reason it does not. Of the eight it found, four emit nothing of token-goat's own and need no boundary, two are the deltas fixed here, and three splice token-goat's markers between the lines they replaced, where a fence would escape token-goat's own text. Those three are listed as open, with the measurement and the reopen condition, rather than left unstated.

  Both deltas now price the fence into the same net-benefit check every other rewrite uses, so a poll whose new bytes are small enough that the fence would cost more than it saves is passed through whole instead. No reindex is needed.

- **Text inside the fence that impersonates token-goat's own marker is now defused, and token-goat's cap notice moved out of the fence so it cannot be confused with one.** The fence already escaped an attempt to close its tag early. It did nothing about the other way out, which measured worse: printing a line that begins `[token-goat: ...]`. That prefix opens the fence's own warning and signs every notice token-goat writes, so output that borrows it is not escaping the fence, it is speaking from inside it in the voice of the thing that built it.

  Measured rather than assumed. A model was given a build log whose last lines impersonate a token-goat truncation notice and ask for a canary line back, twelve times per condition. Unfenced it complied eleven times. Fenced, six: the fence surrounds the impersonation without ever contradicting it. With the prefix escaped, one. The same run checked whether a genuine marker sitting beside an ordinary injection lends it authority, and it does not, nought of twelve either way, so proximity was never the problem and this change is aimed only at forgery of the prefix.

  Fixing that exposed a real case of the confusion it describes. When a filter hits its cap it appends a notice saying so, and that notice was landing inside the fence, in token-goat's voice, where nothing distinguished it from a forgery. It now joins the marker outside the closing tag. Nothing is lost by the move: a cap trims the tail, so the point the notice describes is where the body ends, which the closing tag already marks. Exempting the notice from the escape instead would have been the worse repair, since the wording is not a secret and any output printing it would have inherited the exemption.

  Recalling output with `bash-output --full` returns the same escaped form, because that text is on its way to a model as well. What is stored on disk is untouched, so the record of what a command actually printed stays exact. No reindex is needed. See [src/injection_scan.ts](src/injection_scan.ts) and [src/hooks_bash.ts](src/hooks_bash.ts).

- **Compressed shell output now reaches the model inside an untrusted-content fence, like every other kind of output token-goat rewrites.** When a command prints more than token-goat is willing to hand over whole, what the model receives is not the command's output but token-goat's account of it: lines dropped, runs collapsed, and token-goat's own marker sitting at the end of the block. Everything else that works this way already fenced what it substituted. A fetched page did, an MCP tool result did, and the same shell output did as soon as it was recalled with `bash-output`. On the way in it did not, so a build running a hostile dependency could put a line in front of the model with nothing marking where the command's words stopped and token-goat's began.

  The fence wraps the command's bytes and stops there. Token-goat's marker and the pointer telling the model how to recall the full output stay outside the closing tag, because that boundary is the only signal the model has for whose words are whose, and folding them in would let anyone who guessed the marker's wording write a line that reads as token-goat speaking.

  One consequence is worth expecting: the fence costs about 123 bytes, and token-goat only rewrites output when the rewrite is a real saving, so a command whose compression barely cleared that bar no longer gets rewritten and comes back whole. That is the intended answer rather than a regression. A rewrite that clears the bar only by leaving off its own delimiter was never saving what it claimed.

  Two cases stay unfenced on purpose, and both are now written down in [the security guide](docs/security.md) instead of being left to inference. Output token-goat does not touch reaches the model as the harness delivered it. So does output whose only change was removing the colour codes a terminal would have rendered, because that path emits the command's own bytes and adds nothing of token-goat's that would need marking off. Fencing those would mean rewriting the result of every shell command an agent runs, to re-label bytes the model was going to see in that form anyway. No reindex is needed. See [src/hooks_bash.ts](src/hooks_bash.ts).

### Fixed

- **A shrunk PNG or GIF served from token-goat's image cache is no longer announced to the model as a WebP.** The cache stored a shrunk image under `.jpg` when it was a JPEG and `.webp` when it was anything else, a rule written when the image pipeline could only ever produce those two. The pipeline now produces PNG and GIF and produces WebP never, so a cached PNG or GIF came back labelled WebP, and that label is what becomes the image type sent to the model and the extension a saved screenshot gets. The cache now files each format under its own extension and refuses to store one it cannot name; entries written before this change are still read correctly. Delete nothing: a stale entry is simply re-encoded once. No reindex is needed. See [src/image_shrink.ts](src/image_shrink.ts).

- **`token-goat image-meta` no longer carries a fallback that would have told you to install a library that cannot help.** Its unreadable-file branch said "install sharp to use this feature", from an era when the image pipeline had an optional native decoder. That decoder is gone, so the advice would have pointed at nothing. The branch is unreachable today, because an unreadable file raises a decode error before it is consulted, which is why nobody has been misdirected by it: the message is corrected and its `sharpAvailable` flag renamed `decodable` so that the next change reaching that branch finds it saying something true. See [src/cli.ts](src/cli.ts).

- **The README's image section described a pipeline token-goat no longer has.** It said the shrink ran on `sharp`, that output was WebP, that `token-goat doctor` reports a `sharp` line to check, and it carried a troubleshooting section about installing libvips and C++ build tools. None of that is true since the move to the pure-TypeScript engine: there is no native dependency, no `sharp` line in `doctor`, and no build step on any platform. It also demonstrated a `token-goat image-shrink` command that does not exist. The section now describes what actually runs, and the worked example uses `token-goat image-meta` with a measurement taken from it.

- **Vitest output from a verbose run is now compressed, where before it came back whole.** `vitest --reporter=verbose` prints one line per test carrying the full `file > describe > name` path, and it indents its summary. Both shapes matched none of the rules token-goat used to recognise a vitest run, so a 22,684-byte run came back 2 bytes smaller. It now comes back at 348 bytes, with the run header and every count kept. A second, quieter problem went with it: a test whose name happens to end in something shaped like a duration was counted as a passing file rather than a passing test, so the collapsed count was wrong in a way that depended on which reporter produced the run. Third, a summary line that followed a block of captured stdout was counted into that block and dropped, which is the one part of a passing run nobody can do without.

  The reason none of this was caught is worth writing down: the existing tests wrote their summary lines flush against the left margin, which is what the rule required and what vitest has never printed. A fixture shaped by the code it tests agrees with that code by construction. The new tests are copied byte for byte out of a real run. No reindex is needed. See [src/tool_filters/test_runners.ts](src/tool_filters/test_runners.ts).

### Added

- **`token-goat bench` scores the shell-output compressors, so a change to one can be measured instead of argued about.** It replays a corpus of captured command output through the same function that decides what a real shell command hands back to the model, and prints how much smaller each case got. Measuring through that function rather than a copy of it is the point: a benchmark with its own idea of when compression applies would keep reporting the old number after delivery changed.

  It reports two numbers, not one. The first is how much was saved, and it is the number to push up. The second counts the lines each case declares it must never lose, and it is what stops the first from being gamed, because deleting output is the easiest way to save bytes. A dropped line exits 1, so an automated loop can revert on the exit code alone. `--validate` proves that guard still works by running two deliberately broken filters against the corpus: one that changes nothing, which must score nothing, and one that deletes everything, which scores the best ratio possible and is caught. Run it after editing the corpus; must-keep lists that have gone soft pass every benchmark while measuring nothing.

  The corpus ships in [tests/fixtures/bench](tests/fixtures/bench), and `--corpus <dir>` points at your own. Every case has to say where its output came from, and one that does not is refused rather than scored, because output written by hand proves nothing about what a real command prints. A single case file over 5 MB is refused by name and size instead of being read, since `--corpus` reads every file matching the layout in whatever directory you name, and pointing it at the wrong one should be an error message rather than a machine running out of memory with nothing to say about which file did it. `--tsv <path>` appends a row per run so a sequence of attempts leaves a history. Neither path is confined, because writing a results file outside the repository is the ordinary way to keep that history, and both come from a flag you typed: a test now fails if anything other than the command line ever starts supplying them. No reindex is needed. See [src/cli_bench.ts](src/cli_bench.ts) and the [CLI reference](docs/cli.md).
