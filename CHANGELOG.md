# Changelog

All notable changes to Token-Goat are documented in this file. Format follows Keep a Changelog. Token-Goat follows Semantic Versioning starting at 1.0.

## [2.9.4] - 2026-09-06

### Added

- **`token-goat doctor` now reports how much of a project's index was written by a different build of the parser.** Every indexed file is stamped with a digest of the extraction logic that parsed it, and a mismatch already counts as stale everywhere it matters: `token-goat index` reparses the file, the background worker reparses it, and the new body fold refuses to fold it. What nothing reported is how many files are in that state. The stamp only refreshes when something touches the file, so after an upgrade a project goes on answering `symbol`, `read`, `outline` and `skeleton` from the previous extractor with no sign that it is doing so. On the index this was found on, 95% of one project's 1,155 files were behind, and 71% of 17,508 files across every project. The check warns past a quarter and names the fix: a plain `token-goat index` in that project, which is enough on its own, since a parser mismatch reparses without `--force`.

- **Long function bodies and long comment blocks can now be folded out of a source file the first time it is read.** Every existing way token-goat shrinks a read depends on having seen the file before: it withholds lines already delivered, or turns a repeat read into a pointer. A first read has no earlier copy to compare against, and first reads are the large majority of what the read hook handles. The new `hints.fold_code_bodies` setting keeps each function's declaration and its first eight lines, replaces the rest with a single line naming the symbol, the exact line range removed and the command that returns it, and leaves everything outside a folded span exactly as it was. Imports, signatures, type declarations and short comments survive untouched. Measured on this repository's own source, counting only the first 2,000 lines of each file because that is where a Read stops: of 256 files, 229 fold, and 43% of what a read of them delivers is removed.

  It replaces the result of a read that succeeded rather than blocking the read. Refusing a read costs a round trip, and the agent may fetch the file another way or give up on the task; changing what the same successful call returns costs neither.

  Folding only the body sits between two worse options. A signatures-only view is about an eighth of what a read delivers, so serving one withholds the other seven eighths while still looking like an answer. Keeping the first lines of each body leaves a reader everything a signature list has, plus enough of each implementation to judge whether it needs the rest, and the rest is one named command away. A long top-level constant folds on the same reasoning: its declaration line says what it is and the rest is data.

  Comment blocks fold on the same terms, which reverses an earlier decision. Comments are 46% of this repository's source bytes and they carry the design rationale, so stripping them would be the largest saving available and the least honest one. A fold is not a strip. The first two lines of a block stay, which is the summary a doc comment opens with and the title of a banner, and everything under them becomes one line giving the exact range to read back, so the contract a reader needs in order to decide whether they want the rest is still on screen. A block has to run twelve lines before any of this applies: an ordinary note is left alone, an essay is not. Blocks are found in the delivered text rather than in the index, which is why they fold on a file the indexer has never seen, the case that used to return nothing at all. Which lines count as comment is decided by the file's extension and never by sniffing the content, because a run of lines starting with `#` is a comment block in Python and a run of headings in Markdown, and folding a document's headings would destroy the one structure a reader navigates by.

  It is off by default. On a first read there is no earlier copy for the reader to notice an omission against, and how often a reader has to go back for a folded body has never been observed. A repository cannot switch it on either: `hints.fold_code_bodies` is refused from a checked-in `.token-goat.toml`. How much of its own source a repository shows a reader is not the repository's call. Your own config and `TOKEN_GOAT_FOLD_CODE_BODIES` still set it freely, and `token-goat doctor` reports it when the environment turns it on.

  Four things stop a fold. A read that already names an offset or a limit is surgical and is left alone. A file holding anything that looks like a secret is passed through whole rather than handed back redacted. A class or interface is never folded, because its span covers the member signatures the fold exists to preserve, and neither is a type alias, which is a union or an object shape and so covers the same thing. And a file whose index no longer matches what is on disk loses its body folds, checked on both the content digest and the digest of the parser that produced the rows: a stale line span cuts in the wrong place, and a first read gives no way to catch it. Its comment blocks still fold, since those are read off the text that just arrived and cannot be stale.

  One thing had to be fixed for this to be safe. The record of what a read delivered was taken from the file on disk, which is the same text right up until something rewrites it. After a fold it is not, and the record would have claimed the folded lines were shown; a later read coming back for exactly those lines would then have had them withheld as already seen, from a reader that never saw them once. It now records what was actually delivered, in [src/hooks_read.ts](src/hooks_read.ts) alongside the new [src/code_fold.ts](src/code_fold.ts). No reindex is needed.

### Removed

- **A compression path that was built, tested, fixed four times, and never once run.** `tryWrapCompoundSegments` took a command joined by `&&`, split it, and wrapped each recognized part on its own, so `git diff && git log` would come back with both halves compressed instead of neither. It arrived in June as part of the output-filter framework, and the commit that added it said plainly that nothing was wired to it yet. The rest of that framework was connected over the following weeks. This one function never was, and the import line in [src/hooks_bash.ts](src/hooks_bash.ts) that names eight of its siblings reads as complete without it.

  Nothing failed, which is why it lasted. Six tests covered it and all six passed. A test that hands the function its own wrapper proves the function agrees with the test, which is just as true of code that nothing calls. Four separate fixes went into it while it was unreachable, and two of those said so in their own changelog entries before patching it anyway, on the grounds that it read as deliberate code.

  It was measured before being removed. Applying the real function to every command in a long session history accepts 1.6% of them, and set against what the existing whole-output compressor already delivers, connecting it would have recovered under a megabyte over ten weeks. The one shape it looked built for, `cd somewhere && run something`, is already handled: the hook strips that prefix before it looks at anything, so the command arrives as a single command and compresses the ordinary way. Against that megabyte it needed a second wrapper protocol beside the existing one, a process spawn per part on every matched command, decided before the command runs and therefore before anyone knows the output is big enough to be worth compressing, and it produced output the post-run step could not unwrap, so a second pass would compress the already-compressed text and drop the inner notices. Removed with its two private helpers and its tests, from [src/tool_filters/dispatch.ts](src/tool_filters/dispatch.ts). The quote-aware helpers the live single-command path shares with it, `hasUnquotedOperator` and `shlexSplit`, stay where they are. No reindex is needed.

### Fixed

- **Both of the read hook's rewrites were dead code on Claude Code, because they parsed a rendering the hook never receives.** A Read result reaches a hook as the file's own text in `tool_response.file.content`; the numbered `cat -n` form is applied afterwards, for display. The two of them, the new body fold and the elision of lines already delivered, both looked for that numbered form and treated its absence as nothing to work with, so both declined on every real read. The body fold booked no saving at all across a full session while the rest of the read hook ran normally, and the read that produced this entry was one of them.

  Neither rewrite needs the rendering. What they need is one row per line with a line number attached. A result that arrives unnumbered is now read as exactly that, numbered from the delivered start line, and written back unnumbered into the field it came from: a numbered rendering there would be numbered a second time on display. Both forms work, so a harness that does send numbered text is unaffected. In [src/hooks_read.ts](src/hooks_read.ts). No reindex is needed, and nothing about an existing index changes.

  Every test agreed with the bug. Each one built its own numbered fixture from the regular expression the parser uses, and a comment above one of them stated that numbering is what the Read tool delivers, written from that expression rather than from a Read. Tests like that only prove the parser matches text shaped the way the parser expects. The new cases in [tests/code_fold.test.ts](tests/code_fold.test.ts) use the envelope read off real session records instead, where all 104 Read results carried unnumbered text and none carried a numbered one.

- **A Read asking for five lines of a compacted document got a summary of the whole thing instead.** When a reference doc has a compact sidecar built by `compact-doc`, the read hook serves that summary in place of the file. It was doing this for every read of that file, including ones that named a line range. A read of `CLAUDE.arch.md` for lines 50 to 54 came back with the compact of the entire document, starting at line 1, and nothing told the caller its range had been dropped. The 5 lines asked for are 192 bytes; the compact served instead is 9,295, so on a ranged read the mechanism cost about 48 times what it saved and answered a question nobody asked.

  A ranged read is already surgical, which is the exact reason the subagent markdown check further down the same file leaves one alone. That rule was written once and applied in one of the two places that needed it. The intercept in [src/hooks_read.ts](src/hooks_read.ts) now skips any read carrying an offset or a limit, and the read proceeds normally. What made this hard to see is that the one exemption anybody had thought about was tested: there is a case in [tests/hooks_read.test.ts](tests/hooks_read.test.ts) proving a `Grep` is left alone, written when that exemption was added. Ranged reads never got one. The new test covers all three shapes an offset or limit can arrive in, and asserts first that the same file read whole still is intercepted, so it cannot quietly pass by the feature breaking entirely.

  The served message now also says what the extract leaves out. It is built by taking each heading and the first couple of sentences under it, so front matter and any prose above the first heading are gone entirely, sections are cut short, and long code blocks stop after ten lines. Front matter matters more than it sounds: a doc whose title, version or schema lives in its YAML header hands the agent a compact where that block never existed. The old wording called it a compact and offered `--force` and `--show`, both of which return the same summary again, so a caller missing something had nothing that would get it. The message now names what is dropped and points at a line range or `token-goat section` for one heading in full. No reindex is needed.

- **The saving claimed for a compacted document was quoted as 80 to 95 percent, and most documents do not reach it.** The figure appeared in four places, including the README and the command reference. Measured across the 44 markdown files in this repository over 4 KB, the median saving is 67% and only 13 of the 44 land inside the advertised band. The spread runs from 5% to 99%, because the compact keeps prose sitting under headings and a document made mostly of tables or code leaves it little to keep: the README saves 66%, [CLAUDE.arch.md](CLAUDE.arch.md) saves 91%. The claim now reads 60 to 95 percent with the median beside it, in [README.md](README.md), [docs/cli.md](docs/cli.md), [src/doc_compact.ts](src/doc_compact.ts) and [src/hooks_read.ts](src/hooks_read.ts). No reindex is needed.

- **`hint-stats` printed two kinds of percentage in one column with nothing to tell them apart, and compared straight across they say the opposite of what is true.** Some hints ask the agent to run a specific command instead of what it was about to do, and those score only when the agent runs it. Others ask the agent not to do something at all, and those score by absence: the watch window closing with no repeat read is the compliance the hint asked for, so it counts as a success. Both landed in the same `efficacy` column as a bare number, where a category scored on an absence sits near the top and one scored on an action sits near the bottom. Nothing about that ordering means the first kind of hint works better. It means the two are measured on different scales, and this table was read the other way before anybody checked the scoring.

  The source comment in [src/hint_stats.ts](src/hint_stats.ts) already said the split was disclosed both there and in the command's output. Only the first half was true. The absence-scored rows now carry a `*` and the table explains underneath what it means, so the two scales are visible as two scales. [tests/cli_hint_stats.test.ts](tests/cli_hint_stats.test.ts) holds both halves of it: the marked row must be marked, an action-scored row must not be, and the note must stay quiet when no absence-scored category has fired, since a note that always prints stops being read. No reindex is needed.

- **Four rows of the architecture doc's component map pointed at files that are not there.** `CLAUDE.md` tells an agent to read [CLAUDE.arch.md](CLAUDE.arch.md) on demand to find where a thing lives, so a row naming a path that does not exist sends the reader nowhere and, on the published docs site, returns a 404. Two rows named a module whose contents had moved: the git-history hints are in [src/read_commands.ts](src/read_commands.ts) and the `ask` command is registered inline in [src/cli.ts](src/cli.ts). One named a file that never existed under that name after the TypeScript port, since the daemon's pid handling and its detached entry points sit in [src/worker.ts](src/worker.ts) beside the loop they start. The last named a file deliberately retired on 2026-07-05, whose row outlived it by two months.

  A stale link fails quietly, which is why all four lasted: the table still renders, it still looks complete, and the only symptom is a reader arriving at nothing. [tests/guards/doc_links_resolve.test.ts](tests/guards/doc_links_resolve.test.ts) now checks every repo-relative link in every living document against `git ls-files`, which is the right oracle rather than the filesystem: this repository is developed on a case-insensitive one that resolves `security.md` against `SECURITY.md` perfectly happily, while the docs site and a Linux checkout do not. The two changelogs are out of scope by design and the guard says so, because an entry describing a past release correctly names the file that release touched even after the file is gone, and rewriting those links would falsify the history the file exists to keep. No reindex is needed.

## [2.9.3] - 2026-09-04

### Security

- **The image decoders now refuse a file that would make them allocate gigabytes, hang, or return the wrong picture.** Token-goat shrinks images before the model sees them, and it recently swapped its native image library for one written in TypeScript. The old library enforced the pixel limit inside the decode. The new check reads the width and height out of the file's header and multiplies them, which is a much weaker thing to know, because it says nothing about how many frames an animation has or how far a compressed stream expands. Three files got past it. A GIF of 11.5 KB claiming a 1600 by 1600 canvas and 500 frames asked for 5.1 GB, since every frame is a full canvas and all of them are held at once. A PNG of 510 KB claiming 4000 by 4000, which is exactly the limit, expanded its image data to 512 MB where 61 MB was needed, and 512 MB was simply the size picked for the test file rather than a ceiling the code imposed. Every buffer is now checked against a fixed 256 MB limit before it is allocated, and the PNG check is exact rather than approximate: the file format says precisely how many bytes those dimensions can produce, so anything beyond that is not data the picture needs.

  A 64-byte TIFF was worse than any of them. Pages in a TIFF form a chain, each one holding the position of the next, and nothing stops a file pointing back at a page already read. Token-goat followed the chain without remembering where it had been, so it never came back. It allocates nothing while doing this, so the operating system never steps in and stops it: for a file being read by an agent, that is a read that simply never finishes. Token-goat now remembers the positions it has visited and stops when one repeats.

  The limit covers what the shrink writes as well as what it reads. Reading an animation costs four bytes per pixel per frame; writing the smaller copy costs five, so between 22 and 26 frames of a 1600 by 1600 animation the file being read was inside the limit and the copy being written was not, and the memory used was the two added together. Measured against the installed build, 21 frames of that size still shrinks, from 1,029 KB down to 78 KB, and 22 frames is now declined. The still-image path is fixed alongside it: pulling one frame out of a GIF used to decode the whole animation and throw the rest away, so it now asks for the one frame it wants.

  Two quieter faults are fixed with them, and they are the worse pair. The PNG decoder accepted several formats it cannot actually read and then read them anyway, so a 16-bit image came back as different colours: an opaque red pixel turned into a transparent yellow one. The BMP decoder accepted every colour depth but could only draw two of them, and returned a fully blank image for the rest without reporting a problem. In both cases token-goat re-encoded the wrong picture and handed it to the model as the contents of the file. Both now stop rather than guess, which means the original image is passed through untouched, and an untouched original is the right picture. No reindex is needed. See [src/image_engine.ts](src/image_engine.ts).

- **The test suite now runs a static pass over every interpreter sink in the source tree, and CI runs the dataflow half.** Every structural guard in this repository up to now records a bug somebody already found, which leaves the shapes nobody has looked at uncovered. [tests/guards/dangerous_sinks_are_named.test.ts](tests/guards/dangerous_sinks_are_named.test.ts) is keyed on shape instead. It asserts that `eval`, `new Function`, `node:vm` and the string form of `child_process.exec` appear nowhere in `src`, with no way to exempt one, and it requires every `shell: true` and every `execSync` to be listed with the reason it cannot be an argv array instead. All four of the first group are at zero today and nothing said so, which meant the first one added would have arrived in an ordinary review with nothing objecting.

  The other half of a security scan asks whether untrusted data reaches one of those sinks, which needs dataflow across files and a query engine far too heavy for a suite that also runs on Windows and macOS. That half is [a CodeQL job](.github/workflows/codeql.yml), on pushes to main and on a weekly schedule, since a query pack updated next month can find a bug in code that has not changed since. Every way that job can quietly stop looking leaves a green check and an empty alerts list, which reads like good news, so [tests/guards/codeql_scan_is_wired.test.ts](tests/guards/codeql_scan_is_wired.test.ts) holds it to the extended query suite and to not excluding the directory it exists to scan.

  `eslint-plugin-security` is the obvious thing to reach for here and was measured before any of this was written: 1,691 findings across 177 of 255 source files, 96% of them from three rules that do not fit this codebase. One duplicates a stronger check `npm run lint` already runs, one flags reading a file whose name came from a variable, which is the product, and one flags every computed array index. A suppression list of that size is worse than no rule, because it reads like a decision. The measurement is written down in [CLAUDE.arch.md](CLAUDE.arch.md) so the choice does not get made again blind. No reindex is needed.

- **The Copilot CLI hook shim now rejects an event name it never declared, and a guard covers every bridge that builds a shell command from one.** Each bridge installs a small hook shim, and its last resort is to run `token-goat hook <event>` through a shell. The Copilot CLI shim looked its event name up in a table and went ahead if the lookup returned anything. A plain JavaScript object answers that lookup for eight names it was never given, among them `constructor` and `toString`, so those resolved to a function, were pasted into the command, and reached the shell. None of the eight contains a character a shell treats specially, so the result was a command that failed rather than a second command that ran. The shim now asks whether the table actually declares the name.

  The rest of the surface was audited at the same time rather than by diff. Four of the seven bridges already check the name against a fixed list. Two check nothing and are safe only because every place that calls them passes a fixed string, which is true of today's callers rather than of the code. [tests/guards/shell_concat_is_constrained.test.ts](tests/guards/shell_concat_is_constrained.test.ts) now holds all three shapes, and checks the two unvalidated ones at both steps: every caller passes a fixed string, and the step that actually builds the command passes along only the value the first check covers. A new bridge that skips the check fails the guard rather than shipping. No reindex is needed.

- **Background shell and background task poll deltas are now fenced, and a guard now checks every place token-goat replaces a tool result.** When `BashOutput` or `TaskOutput` is polled a second time, token-goat replaces the repeated output with just the new bytes under a short notice of its own. The notice and the new bytes were glued together with nothing between them, so a background process that printed a line in the marker's shape was writing text the model would read as token-goat's. The notice now sits above the fence and the process output inside it, the same arrangement compound Bash output already uses.

  The wider problem was that nothing checked for this. [tests/guards/substituted_output_reaches_fence.test.ts](tests/guards/substituted_output_reaches_fence.test.ts) now walks every function that hands the model a replacement body and requires it to either fence what it kept or appear in a list with the reason it does not. Of the eight it found, four emit nothing of token-goat's own and need no boundary, two are the deltas fixed here, and three splice token-goat's markers between the lines they replaced, where a fence would escape token-goat's own text. Those three are listed as open, with the measurement and the reopen condition, rather than left unstated.

  Both deltas now price the fence into the same net-benefit check every other rewrite uses, so a poll whose new bytes are small enough that the fence would cost more than it saves is passed through whole instead. No reindex is needed.

- **Text inside the fence that impersonates token-goat's own marker is now defused, and token-goat's cap notice moved out of the fence so it cannot be confused with one.** The fence already escaped an attempt to close its tag early. It did nothing about the other way out, which measured worse: printing a line that begins `[token-goat: ...]`. That prefix opens the fence's own warning and signs every notice token-goat writes, so output that borrows it is not escaping the fence, it is speaking from inside it in the voice of the thing that built it.

  Measured rather than assumed. A model was given a build log whose last lines impersonate a token-goat truncation notice and ask for a canary line back, twelve times per condition. Unfenced it complied eleven times. Fenced, six: the fence surrounds the impersonation without ever contradicting it. With the prefix escaped, one. The same run checked whether a genuine marker sitting beside an ordinary injection lends it authority, and it does not, nought of twelve either way, so proximity was never the problem and this change is aimed only at forgery of the prefix.

  Fixing that exposed a real case of the confusion it describes. When a filter hits its cap it appends a notice saying so, and that notice was landing inside the fence, in token-goat's voice, where nothing distinguished it from a forgery. It now joins the marker outside the closing tag. Nothing is lost by the move: a cap trims the tail, so the point the notice describes is where the body ends, which the closing tag already marks. Exempting the notice from the escape instead would have been the worse repair, since the wording is not a secret and any output printing it would have inherited the exemption.

  Recalling output with `bash-output --full` returns the same escaped form, because that text is on its way to a model as well. What is stored on disk is untouched, so the record of what a command actually printed stays exact. No reindex is needed. See [src/injection_scan.ts](src/injection_scan.ts) and [src/hooks_bash.ts](src/hooks_bash.ts).

- **Compressed shell output now reaches the model inside an untrusted-content fence, like every other kind of output token-goat rewrites.** When a command prints more than token-goat is willing to hand over whole, what the model receives is not the command's output but token-goat's account of it: lines dropped, runs collapsed, and token-goat's own marker sitting at the end of the block. Everything else that works this way already fenced what it substituted. A fetched page did, an MCP tool result did, and the same shell output did as soon as it was recalled with `bash-output`. On the way in it did not, so a build running a hostile dependency could put a line in front of the model with nothing marking where the command's words stopped and token-goat's began.

  The fence wraps the command's bytes and stops there. Token-goat's marker and the pointer telling the model how to recall the full output stay outside the closing tag, because that boundary is the only signal the model has for whose words are whose, and folding them in would let anyone who guessed the marker's wording write a line that reads as token-goat speaking.

  One consequence is worth expecting: the fence costs about 123 bytes, and token-goat only rewrites output when the rewrite is a real saving, so a command whose compression barely cleared that bar no longer gets rewritten and comes back whole. That is the intended answer rather than a regression. A rewrite that clears the bar only by leaving off its own delimiter was never saving what it claimed.

  Two cases stay unfenced on purpose, and both are now written down in [the security guide](docs/security.md) instead of being left to inference. Output token-goat does not touch reaches the model as the harness delivered it. So does output whose only change was removing the colour codes a terminal would have rendered, because that path emits the command's own bytes and adds nothing of token-goat's that would need marking off. Fencing those would mean rewriting the result of every shell command an agent runs, to re-label bytes the model was going to see in that form anyway. No reindex is needed. See [src/hooks_bash.ts](src/hooks_bash.ts).

### Fixed

- **A shrunk PNG or GIF served from token-goat's image cache is no longer announced to the model as a WebP.** The cache stored a shrunk image under `.jpg` when it was a JPEG and `.webp` when it was anything else, a rule written when the image pipeline could only ever produce those two. The pipeline now produces PNG and GIF and produces WebP never, so a cached PNG or GIF came back labelled WebP, and that label is what becomes the image type sent to the model and the extension a saved screenshot gets. The cache now files each format under its own extension and refuses to store one it cannot name; entries written before this change are still read correctly. Delete nothing: a stale entry is simply re-encoded once. No reindex is needed. See [src/image_shrink.ts](src/image_shrink.ts).

- **`token-goat image-meta` no longer carries a fallback that would have told you to install a library that cannot help.** Its unreadable-file branch said "install sharp to use this feature", from an era when the image pipeline had an optional native decoder. That decoder is gone, so the advice would have pointed at nothing. The branch is unreachable today, because an unreadable file raises a decode error before it is consulted, which is why nobody has been misdirected by it: the message is corrected and its `sharpAvailable` flag renamed `decodable` so that the next change reaching that branch finds it saying something true. See [src/cli.ts](src/cli.ts).

- **The README's image section described a pipeline token-goat no longer has.** It said the shrink ran on `sharp`, that output was WebP, that `token-goat doctor` reports a `sharp` line to check, and it carried a troubleshooting section about installing libvips and C++ build tools. None of that is true since the move to the pure-TypeScript engine: there is no native dependency, no `sharp` line in `doctor`, and no build step on any platform. It also demonstrated a `token-goat image-shrink` command that does not exist. The section now describes what actually runs, and the worked example uses `token-goat image-meta` with a measurement taken from it.

- **Vitest output from a verbose run is now compressed, where before it came back whole.** `vitest --reporter=verbose` prints one line per test carrying the full `file > describe > name` path, and it indents its summary. Both shapes matched none of the rules token-goat used to recognise a vitest run, so a 22,684-byte run came back 2 bytes smaller. It now comes back at 348 bytes, with the run header and every count kept. A second, quieter problem went with it: a test whose name happens to end in something shaped like a duration was counted as a passing file rather than a passing test, so the collapsed count was wrong in a way that depended on which reporter produced the run. Third, a summary line that followed a block of captured stdout was counted into that block and dropped, which is the one part of a passing run nobody can do without.

  The reason none of this was caught is worth writing down: the existing tests wrote their summary lines flush against the left margin, which is what the rule required and what vitest has never printed. A fixture shaped by the code it tests agrees with that code by construction. The new tests are copied byte for byte out of a real run. No reindex is needed. See [src/tool_filters/test_runners.ts](src/tool_filters/test_runners.ts).

### Added

- **`token-goat bench` scores the shell-output compressors, so a change to one can be measured instead of argued about.** It replays a corpus of captured command output through the same function that decides what a real shell command hands back to the model, and prints how much smaller each case got. Measuring through that function rather than a copy of it is the point: a benchmark with its own idea of when compression applies would keep reporting the old number after delivery changed.

  It reports two numbers, not one. The first is how much was saved, and it is the number to push up. The second counts the lines each case declares it must never lose, and it is what stops the first from being gamed, because deleting output is the easiest way to save bytes. A dropped line exits 1, so an automated loop can revert on the exit code alone. `--validate` proves that guard still works by running two deliberately broken filters against the corpus: one that changes nothing, which must score nothing, and one that deletes everything, which scores the best ratio possible and is caught. Run it after editing the corpus; must-keep lists that have gone soft pass every benchmark while measuring nothing.

  The corpus ships in [tests/fixtures/bench](tests/fixtures/bench), and `--corpus <dir>` points at your own. Every case has to say where its output came from, and one that does not is refused rather than scored, because output written by hand proves nothing about what a real command prints. A single case file over 5 MB is refused by name and size instead of being read, since `--corpus` reads every file matching the layout in whatever directory you name, and pointing it at the wrong one should be an error message rather than a machine running out of memory with nothing to say about which file did it. `--tsv <path>` appends a row per run so a sequence of attempts leaves a history. - **The check that stops a file name adding a second command has been rebuilt, because the first version could be walked past.** The original counted double quotes and let a suggestion through when the count came out even. Counting is not the same as checking where the quotes sit: a name carrying two of them closes the quote token-goat opened, runs whatever comes next, and opens a fresh one so the total still comes out even. One extra character was enough. The check now splits the suggestion on its quotes and looks at the parts that sit outside them, so an even count no longer buys anything. What it looks for there changed too. The first version listed the characters that turn one command into two, and a review walked past that list with a redirection: a name like `a" > ~/.bashrc "b.ts` contains none of them, keeps the quote count even, and truncates a file without running a second command at all. That closes the whole class instead of the one member of it that was noticed.

A name containing an invisible text-direction character can make the command you are shown read differently from the command that would run, and a name containing a control byte can move the cursor and overwrite what came before it. One visible consequence: `python -c` and `node -e` snippets containing a `;` are now compressed like any other recognized command. No reindex is needed. See [src/tool_filters/helpers.ts](src/tool_filters/helpers.ts), [src/tool_filters/dispatch.ts](src/tool_filters/dispatch.ts) and [tests/tool_filters.test.ts](tests/tool_filters.test.ts).

- **A command that starts with `cd somewhere &&` no longer hands every output filter a garbled command line.** Filter selection already peeled a leading `cd DIR &&` off the command so the real tool landed first (that is how `cd /app && npm test` finds the npm filter at all), but the wrapper then re-derived the argument list a second time, from the original unpeeled command, and passed *that* to the filter. So the filter was chosen from one command and handed another: every filter that reads its own flags saw `cd` as the program name and the directory as the first argument. That is 45 filters, among them grep and rg (which look up the search pattern to decide where to clip a long line), make (target), cargo, dotnet, maven, gradle, go, webpack, gh, kubectl, helm, ansible, and the git log/diff/status filters. The visible symptom on grep was that a long matching line shipped at full length on a `cd`-prefixed search while the identical bare search clipped it, because the pattern the clipper looked for was the directory name and was nowhere on the line. In a corpus of real sessions, 592 of 1,884 long-line grep results were `cd`-prefixed. The wrapper now derives the argument list once, through the same peeling helper filter selection uses, so the two cannot drift apart again. No reindex is needed. See [src/bash_runner.ts](src/bash_runner.ts), [src/tool_filters/dispatch.ts](src/tool_filters/dispatch.ts) and [tests/bash_runner.test.ts](tests/bash_runner.test.ts).

- **A short grep result containing one enormous matching line no longer ships that line whole.** Below 30 matching lines the grep/rg filter passed its output through verbatim, and nothing anywhere in the pipeline looked at an individual line: the whole-output line and byte caps only measure the result as a whole. So a twelve-line search whose ninth hit landed inside a minified bundle sent that 5,000-character line in full. Measured across 4,664 real session transcripts (32,720 grep/rg results, 42.8 MB), 2.89 MB sat beyond 1,000 characters per line, spread over 1,872 results. Lines longer than 1,000 characters are now clipped to a window **centered on the match**, not to their first 1,000 characters: a head trim would have thrown away the answer whenever the hit sat past the cut, which is exactly what happens in minified files. The `path:lineno:` field (or the bare `lineno:` grep prints for a single file) is always kept, and every removed run is marked with its exact character count. When the match cannot be located by a plain substring scan (a regex pattern, `-i`, `-v`, `-e`/`-f`, `-z`, rg's `-U` or `-S`), the line is left completely untouched rather than trimmed blind. A clip that would cost more in markers than it removes is also discarded. The existing filter accounting is reused unchanged: no new stat kind, and the same net-savings floor that already decides whether the filter's output is worth shipping still applies, measured on the bytes actually emitted. No reindex is needed. See [src/tool_filters/helpers.ts](src/tool_filters/helpers.ts), [src/tool_filters/shell_file.ts](src/tool_filters/shell_file.ts) and [tests/tool_filters_shell_file.test.ts](tests/tool_filters_shell_file.test.ts).

- **`token-goat refs` no longer claims it saved you the whole contents of every file a reference lives in.** The `symbol_read` saving for `refs` was measured against the on-disk size of every file that contained a match, added together. A `refs` call that found call sites in 40 files credited itself all 40 files read end to end. There is a 100KB-per-file ceiling on that kind of baseline, but it bounds each file and never their sum, so a multi-file result walked straight past it: on one real ledger `refs` reported an average of 466KB saved per call, and the `symbol_read` line item alone was 298MB over 640 calls. Nobody reads 40 whole files to find call sites; they run a search. The baseline is now the search that `refs` actually replaces (one `path:line: label` hit line per reference), which is a deliberate lower bound on what a real `grep -n` would have printed, since a grep line carries the whole source line and a textual grep also returns comments and unrelated same-named symbols. The reported number for `refs` drops sharply and by design; nothing about what `refs` prints changes, and only the `symbol_read` events produced by `refs` are affected. The same counter recorded by `read "file::symbol"`, where the alternative genuinely is reading one file whole, is untouched. Historical rows already in the stats database keep their old inflated numbers; they are a record of what was recorded at the time and are not rewritten. No reindex is needed. See [src/read_commands.ts](src/read_commands.ts) and [tests/refs_stat_baseline.test.ts](tests/refs_stat_baseline.test.ts).

Comment only, no behavior change. No reindex is needed. See [src/baseline.ts](src/baseline.ts).

- **A subagent's read could make the parent's re-read of the same file wrongly say "unchanged."** Read-dedup state (has this agent already read this file?) has been keyed per agent since an earlier fix, salting the key with the subagent id when one is present so sibling agents don't conflate each other's reads. The snapshot store that powers the unchanged/diff messages was never given the same treatment: every snapshot save and lookup in [src/hooks_read.ts](src/hooks_read.ts) still used the plain, unsalted session id. Since every subagent spawned from one parent shares the parent's session id, a subagent reading a file after the parent overwrote the parent's saved snapshot with the subagent's own copy. The parent's next re-read then compared the live file against content it never actually saw: reporting "unchanged" for a file that had in fact changed, or computing a diff against the wrong starting point. Snapshot keys are now built the same way session state keys already are, through one shared `sessionStateKey()` helper (moved to [src/hook_registry.ts](src/hook_registry.ts) so both callers use the identical code path). No reindex is needed.

- **`session-audit` can see its own history again after a deny message is reworded.** The table that classifies deny messages into kinds had an entry for the old `MEMORY.md` wording removed once the code stopped emitting it. Removing the entry made 21 real denies unclassifiable (`memory_md_reread_deny` fell from 51 events to 30, 41% of that kind's recorded history), with a passing test suite and no error anywhere, which would have quietly shrunk the denominator under any rate later derived for that kind. The entry is restored, and a test now fails if a superseded wording stops being recognized. No reindex is needed. See [src/session_audit.ts](src/session_audit.ts) and [tests/deny_outcomes.test.ts](tests/deny_outcomes.test.ts).

- **The deny-outcome census in `session-audit` no longer counts a deny as "abandoned" just because it can't see how the agent actually responded.** Two blind spots meant the census was crediting itself work the agent had already routed around. First, the check for a substituted `token-goat` command only matched a command that started with `token-goat`/`tg`, so `cd somewhere && token-goat section file.ts::Heading` and `node dist/token-goat.mjs read file.ts::Foo` were both counted as no substitution at all; that check now also matches after a shell separator (`;`, `&`, `|`, `(`, or whitespace). Second, there was no way to see the single most common real response to a deny: reading the same file with a shell command instead (`sed`, `grep`, `cat`, `head`, `tail`, `awk`, `rg`, `less`, `nl`, `python`, or `node`). Every one of those fell through to "abandoned" before. - **Fix the deny-outcome Edit-error canary denominator mismatch.** The per-kind `editErrorWithin10Count` was previously compared against `editErrorBaseline.rate` directly, but they have different denominators: the per-kind count is errors out of that kind's denies, while the baseline is errors out of corpus-wide edits. Added `editWithin10Count`: the number of denies where an Edit on the denied path occurred within 10 calls (regardless of error), making the ratio `editErrorWithin10Count / editWithin10Count` directly comparable to `editErrorBaseline.rate`. On this project's corpus: 32 errors out of 426 at-risk Edits on denied paths (7.51%) versus 398 errors out of 22,106 corpus-wide Edits (1.80%), revealing a 4.17x elevation in error rates for Edits on recently-denied paths, not a weak signal. Both `editWithin10Count` and `editErrorWithin10Count` now appear in text and JSON output. No reindex is needed. See [src/session_audit.ts](src/session_audit.ts).

- **`session-audit` now measures what actually happens after a Read is denied, instead of assuming the worst case.** Every deny (a re-read block, a large-file block, a stale-cache serve, and 20 other message shapes) was credited as a saving equal to the full withheld bytes, on the assumption that a denied read always turns into a costly retry. That assumption was never checked. A deny can also be a wash (the agent substitutes the surgical command it should have used) or a genuine win (the agent abandons a read it did not need), and nothing distinguished the three.

  `session-audit` now classifies every deny message into one of 24 kinds and, for each one, measures the tool calls that follow it in the same transcript: whether the next few calls were a plain re-read (a real retry), a `token-goat read`/`section`/`symbol`/etc. command against the same file (a substitution, not a retry), nothing at all before the transcript ended (unresolved), a later re-read that's correct by design because a compaction happened first, or none of the above (abandoned). Counts and rates for all five outcomes appear next to the existing "Read interception" section, and `--json` adds a `denyOutcomes` array with per-kind medians of withheld bytes, remaining calls, and the next API call's raw token usage. Nothing is converted to a billed-token estimate; the raw usage numbers are reported as-is. No reindex is needed. See [src/session_audit.ts](src/session_audit.ts).

- **Compact `token-goat --help` output under 4096 bytes.** The top-level help was 23,988 bytes: a 133-line guide that named every command with a full description, was run 138 times in a corpus, and cost ~60KB per session on average. It is now a 2,318-byte grouped command index organized by category (reads, analysis, file formats, indexing, session, skills, compression, config, data, utilities). All 148 command names still appear. The full original listing is still there when you want it: `token-goat help --full` prints it in one go, `token-goat <command> --help` prints one command's help, and `token-goat commands --grep <pattern>` searches. Keeping `--full` working needed care, because replacing the short help sets a property on the program object that hides the built-in formatter from everything else that asks for it, including `--full` itself; the original is now saved before that happens, and a test fails if `--full` ever returns less than the short index it is supposed to expand. No reindex is needed. See [src/cli.ts](src/cli.ts) and [tests/help_full_restores_long_form.test.ts](tests/help_full_restores_long_form.test.ts).

- **Skill notices now offer `skill-section` before `skill-body`.** When a skill is cached, too large, or has a compact slice available, the denial notice now offers the cheapest recall command (`skill-section`) before the more expensive alternatives (`skill-body --compact` and `skill-body`). No reindex is needed.

- **Top symbols list no longer includes test-file variables.** `token-goat map --compact` and agent briefings were reporting test-file local variables and short names (out, file, result, slice, find) as top project symbols, actively misleading. Now filters out files matching `*/tests/*`, `*/test/*`, `*/__tests__/*`, `*/spec/*` and `*.test.*`, `*.spec.*`, and excludes names shorter than 4 characters. Also changed ref counting from `COUNT(*)` to `COUNT(DISTINCT file_path)` to rank by number of files using a symbol rather than raw reference count. No reindex is needed.

- **Reading the same unchanged file twice through the shell no longer costs twice.** Reading a file with `cat`, `head`, `tail`, or `sed -n '1,40p'` went through the shell rather than the read tool, and the shell path had no memory: nothing was cached, nothing was compared against a previous run, and the same file read five times sent its full contents five times. In one recent session the same 40-line slice of a changelog was read six times, at roughly 6,500 tokens each.

  Now, when one of those reads runs again and comes back byte-for-byte identical to the earlier run, the repeated copy is replaced with a single line saying the file has not changed and giving the command to bring the contents back. Nothing is summarized or thrown away: the two versions are the same bytes, so what is dropped is a duplicate, and the full text stays available through `token-goat bash-output <id>`. A read of a file that did change is left completely alone, as is anything that is not a plain file read, because for a test run or a build "the same output as last time" is the answer rather than a repeat. The comparison is also limited to the conversation you are in: the stored copy outlives a session, but the first read in a new one is left whole, because the point is to drop a copy you already have rather than to hand you a pointer to text you have never seen. Measured on this project, one repeated read went from 4,031 bytes to 189.

  This replaces the output rather than advising against the read, which matters: the advice token-goat used to give about shell reads was followed 2.7% of the time, while the places where it acts on the content directly land above 95%. Savings show up in `token-goat stats` under `bash_compress:identical-reread`. No reindex is needed.

- **Reading part of a file you have already read costs nothing extra.** The collapse above only recognized the exact same command run again. The reads that actually repeat are not spelled the same: in one measured session the three most expensive shell calls were `sed -n '1,40p' CHANGELOG.md`, `head -40 CHANGELOG.md`, and `sed -n '1,30p' CHANGELOG.md`, roughly 6,600 tokens each. Three different commands, three different results, and the third showed nothing the first two had not.

  A read of a file is now checked against everything already served for that same file this session, not just against an identical command. When every line coming back was already shown, in order, as part of a wider read, the repeat is replaced with a line saying so and giving the command to bring the earlier output back. The check is on the text itself rather than on line numbers, which matters because line numbers stop being true the moment a file changes in a way token-goat did not see, such as a pull in another terminal.

  It only holds back a read that adds nothing. A read reaching past what was shown is left whole, since part of it is new. A match has to line up with whole lines at both ends, so a read that starts or stops in the middle of a line already shown is left alone rather than being answered with lines the model never saw as lines. Two files that happen to hold the same text are kept apart, because the recall command has to point at the file that was actually read. And the record is dropped whenever the text behind it stops being trustworthy: when the file is edited, and when the conversation is compacted and the earlier output is no longer in context. Savings show up in `token-goat stats` under `bash_compress:contained-reread`. No reindex is needed.

- **A file opened the ordinary way now counts as already read when the shell asks for it again.** The check above compares a shell read against everything already served for that same file, but only shell reads were ever written into that record. A file first opened with the read tool was invisible to it, so `sed -n '1,40p' README.md` run after reading README.md came back in full, and the half of that check meant to catch this never fired once in a month of real sessions. Measured on this project's own sessions, a third of the shell reads that name a line range ask for lines the conversation is already holding.

  A finished read now records the lines it actually handed over, so a later shell read of those same lines is recognized and replaced with the same one-line pointer. What gets recorded is the file's own text rather than the read tool's numbered display, because the plain text is what `sed` and `cat` will print and what the comparison is made against. A read that asked for part of a file records only that part, so a later read reaching past it is left whole rather than being answered with lines nobody was shown. A read that came back truncated records nothing at all: it delivered less than it asked for, and there is no way from here to tell where it stopped. Savings continue to show up in `token-goat stats` under `bash_compress:contained-reread`. No reindex is needed. See [src/hooks_read.ts](src/hooks_read.ts).

- **A file is no longer sent again when the exact lines are already in the conversation.** Everything token-goat did about repeated reads counted them: how many times a file had been opened, how large it was, how recently it was touched. Counting is a guess, and because it is a guess there is a safety valve, which leaves the four most recently read files alone so a read that is genuinely needed is never blocked on one. That valve covers the case where the answer is most obvious: a file read a moment ago is a file whose contents are certainly still in the conversation. Over a month of real sessions, 830 reads returned a line range that had already been handed over, and sitting inside that window was the main reason nothing happened.

  When the lines can be checked rather than guessed at, they are. Before a repeated read goes through, the text it would return is compared against the text already given out for that same file this session. If every line matches, whole line for whole line, the read is answered with a line saying so and the command to bring the earlier copy back, instead of the file. Counting still decides everything else; this only takes over where there is proof.

  The comparison is on the text, never on line numbers, so it goes the safe way in every case that matters. A file changed since it was last read no longer matches, and the read goes through. A read asking for more than was given before carries lines nobody has seen, and goes through. A read of something never delivered goes through. Turning re-read denial off turns this off too, because a setting that asks for hints instead of blocks is not overridden by having better evidence. Savings show up in `token-goat stats` under `read_served_deny`. No reindex is needed. See [src/hooks_read.ts](src/hooks_read.ts).

- **A read that asks for more than you already have now sends back only the part you do not.** Everything above is all-or-nothing: a read is replaced with a pointer when every single line of it was already delivered, and left completely alone otherwise. That leaves out the shape most repeated reads actually take. Opening a file, then opening it again to see further down, asks for the lines you just read plus some new ones, and because part of it is new the whole thing comes back, first lines included.

  A finished read is now compared against what has already been handed over for that same file in this conversation, line by line. Any stretch that was shown before, in the same order, is replaced with one line naming the line numbers it stands in for and the command to bring them back. Everything else comes through exactly as it arrived, with its own line numbers and its own spacing, unchanged byte for byte, so a later reference to "line 47" still points at line 47. Reading a 60-line file whose first 40 lines had already been read returned 1,924 bytes instead of 5,321.

  Its caution is in what it declines to do. A stretch is only held back when dropping it saves more than the line replacing it costs, so five short lines are left alone rather than swapped for a longer notice, and the rewrite as a whole still has to clear the same minimum saving as every other rewrite before it is used at all. A result holding anything the redactor would strip is passed through whole, because handing back a redacted copy of your own file would show you less than a plain read does. A truncated result is left alone, since there is no telling what it left out. A file changed on disk since it was served no longer matches and comes through in full. And where this fires, the advice token-goat would otherwise have given about the same read is not shown, so you are never charged for both.

  Savings show up in `token-goat stats` under `read:served_elide`. Set `elide_served_lines = false` under `[hints]` to turn it off. No reindex is needed. See [src/hooks_read.ts](src/hooks_read.ts).

- **Color codes in shell output no longer cost anything.** A command run with color on sends the escape sequences that paint a terminal along with its text. There is no terminal on the other end of a tool call, so those bytes arrive as tokens and say nothing. They are not a rounding error either: on a real `git diff` of this project they were 13.2% of the output, and `token-goat`'s own colored output is over half escape bytes by weight.

  Shell output that nothing else compressed now has its escape sequences removed. This is the one change on that path that holds nothing back. What comes through is byte-for-byte the same output with color turned off, so there is no summary, no marker, and no recall command, because there is nothing to recall: a marker would only spend bytes announcing that nothing was lost.

  It runs on commands that failed, too. The compressing paths deliberately leave a failed command alone so its diagnostics arrive whole, and here removing color is what keeps a failed build whole rather than shortening it. It stays out of the way otherwise: output with no escapes is untouched, and output whose escapes are too few to be worth a rewrite is left as it is, so a single colored word does not trigger one. Turn it off with `disabled_filters = ["ansi"]` under `[bash_compress]`, or with the existing `TOKEN_GOAT_BASH_COMPRESS=0`. Savings show up in `token-goat stats` under `bash_compress:ansi`. No reindex is needed. See [src/hooks_bash.ts](src/hooks_bash.ts).

- **The index now catches up on what changed while nothing was watching.** Every way token-goat noticed a file had changed ran from a hook: the edit hook queues what the agent edits, the shell hook queues what a branch switch or an in-place rewrite touches, and a command naming a file reparses it on the spot. Between them, a change made during a session is covered. Nothing covered a change made outside one. A pull in another terminal, a save from an editor, a code generator run from a different window: the file on disk moves on and the stored copy does not, and the commands most likely to be asked first are exactly the ones that never name a file, so none of them triggers the per-file repair. `semantic`, `symbol` by name, `find`, `refs`, `callers`, `arch` and `dead` all answer from whatever was stored, and a stale answer looks the same as a correct one.

  Starting a session now sweeps the project once and queues anything whose content no longer matches what was stored, so the repair happens before the first question rather than after a wrong answer. It compares the two things that have to agree rather than trying to list the ways they can disagree, so a cause nobody thought of is covered by the same code. The sweep reads a timestamp per file and nothing else in the ordinary case, and only reads a file's contents when its timestamp moved, so the steady-state cost on a session start is one filesystem call per tracked file. A moved timestamp is treated as a suspicion and confirmed by content, never taken as proof: switching branches rewrites every timestamp in the repository while leaving most files identical, and a sweep that believed timestamps would queue the whole project every time you changed branch. It is bounded by a time budget, it never fails a session start, and it says nothing at all when the stored copy is already correct. When the budget cuts it short it says so and reports no deletions at all, because a file it never reached looks exactly like one that was deleted, and guessing there would queue live files for removal. It holds back the same way in a folder git cannot list at all, which happens when the folder is not a repository, when git is missing, and when git simply fails: an empty list of files there is not the same thing as an empty project, and reading it as one would report every stored file as deleted and drop the whole index for that folder. It says which of the two it is instead of picking. **Files it finds are queued for reindexing, which is the point**; nothing else needs a reindex. Set `TOKEN_GOAT_RECONCILE=0` to switch the sweep off, or `TOKEN_GOAT_RECONCILE_BUDGET_MS` to change its budget. The same sweep is available as `token-goat reconcile`, with `--dry-run` to see the drift without queueing it. See [src/reconcile.ts](src/reconcile.ts) and [src/hooks_session_start.ts](src/hooks_session_start.ts).

- **`token-goat affected` names the test files a change can reach.** Given a list of changed files it walks the project's import graph backwards, so a test that imports a helper that imports the changed file is reported alongside a test that imports it directly. The intended use is narrowing a run to the tests a change can actually break: `git diff --name-only | token-goat affected --stdin --quiet` prints bare paths ready to hand to a test runner.

  It answers a different question from `test-for`, and neither replaces the other: `test-for` asks which tests mention a file's symbols by name, one step, from the stored symbols; this asks which tests reach a file through imports, however many steps away. ### Changed

- **Indexing no longer takes most of the machine while it runs.** Building embeddings runs a small neural model, and the runtime that executes it, ONNX Runtime, decides for itself how many threads to use when nobody tells it otherwise: it takes the whole host. Measured here on a 26-core machine, creating that session took the process from 13 operating-system threads to 30, and every single embedding call then spread across all of them. Two indexing paths did this: the background worker, which is invisible because it runs detached with its output discarded, and the `token-goat index` command. Neither asked for fewer threads, and neither asked the operating system to schedule it behind whatever the user was actually doing. On a large index that is felt as the whole computer stalling for as long as the walk lasts, with nothing on screen to explain it.

  Both are now fixed, with two settings that work independently. `worker.embed_threads` (default 4, range 1 to 16, `TOKEN_GOAT_EMBED_THREADS`) caps how wide one embedding call can spread; the same measurement showed a session created with an explicit count adds no threads at all. `worker.priority` (default `below_normal`, also `low` or `normal`, `TOKEN_GOAT_WORKER_PRIORITY`) is what both indexing paths now ask the operating system for, which costs nothing on an idle machine because the scheduler only steps a process down when something else wants the processor. Nothing above `normal` can be set, so a checked-in project file cannot put a background indexer ahead of your own work; an unrecognised value falls back to the default rather than to the system default, because a typo there would silently restore the old behaviour. Where the platform refuses the change, which some hardened Linux setups and sandboxes do, indexing continues exactly as before rather than failing.

  Indexing takes longer in exchange, and on a machine that is otherwise idle it takes longer than it used to. Indexing this project's own `src` through the built binary took 210 seconds at the new default of 4 threads and 384 seconds at 2, one run each on one machine, so treat those as the size of the effect rather than precise figures. Four is where it settled because of what a foreground responsiveness probe found on a 26-core machine: with the priority set below normal, 2, 4 and 6 threads are all indistinguishable from an idle machine, and they stay indistinguishable when the indexer and the probe are confined to the same 4 processor cores, and still when 4 threads are confined to 2 cores, which is more threads than cores. The same probe reads a 10% drop at 16 threads, and a 69% drop with a 292 millisecond stall at 4 threads on 2 cores, once the priority is normal instead. So it is the priority, not the thread count, that keeps the rest of the machine usable, and the cap is what remains where the platform refuses to change priority at all. Existing embeddings are unaffected and **no reindex is needed**: the model output was compared at the old and new thread counts and all 4224 values were bit-identical, maximum difference zero, so vectors written before and after this change are interchangeable. See [src/embed_model.ts](src/embed_model.ts), [src/process_priority.ts](src/process_priority.ts), [src/worker.ts](src/worker.ts) and [src/cli.ts](src/cli.ts).

Summed over a whole project the effect is invisible: matching on meaning quietly covers a small part of the index, keyword search keeps answering, and the output looks like a complete result. One real index had 356 of 11,000 files reachable that way, and every check reported healthy. Two places now say so. `token-goat doctor` has an **Embedding coverage** row giving the covered and indexed counts, which warns below a quarter and names the setting to raise; and `semantic` says the same thing in one line when matching on meaning returns nothing at all and some indexed files have no embeddings, so an empty result cannot be mistaken for a searched-everything result. Both are read-only: nothing re-embeds, no configuration changes, and **no reindex is needed**. See [src/index_health.ts](src/index_health.ts), [src/cli_doctor.ts](src/cli_doctor.ts) and [src/read_commands.ts](src/read_commands.ts).

- **`scope` could report "no symbols enclosing line N" for a line that a symbol does enclose.** The command read a capped page of the file's symbols out of the index and only then filtered that page for the ones covering the requested line. Because the database applied the cap first, a file with more than 10,000 indexed symbols lost everything past the cap before the filter ran, and a line covered only by one of those printed the same "No symbols enclosing" wording as a line nothing covers, with no notice on either channel that the answer had been discarded. The enclosing test now runs inside the query, so the cap can no longer come between the question and the row that answers it. The check that separates a missing file from an indexed-but-uncovered line is unchanged, and the extra lookup it needs runs only when nothing was found. See [src/graph_commands.ts](src/graph_commands.ts) and [src/index_reader.ts](src/index_reader.ts). No reindex is needed.

- **`scope --json` printed absolute paths where `scope` printed repo-relative ones.** The text output ran every path through the shared display-path helper and the JSON branch emitted the stored row as-is, so the same command answered the same question two different ways depending on the flag, and leaked the machine's directory layout in one of them. Both branches now render the path identically. The only assertion this payload had was that it was an array, which is why the split went unnoticed. See [src/graph_commands.ts](src/graph_commands.ts).

- **`scope file:99999999999999999999` reported a line number nobody typed.** A run of digits too long for a double to hold exactly was accepted by the digits-only check and then silently rounded, so the failure message named line 100000000000000000000 for that input. Line numbers that cannot be represented exactly are now rejected up front, with the same wording the other two invalid-line cases already use, quoting what was actually typed. See [src/graph_commands.ts](src/graph_commands.ts).
