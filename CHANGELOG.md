# Changelog

All notable changes to Token-Goat are documented in this file. Format follows Keep a Changelog. Token-Goat follows Semantic Versioning starting at 1.0.

## [Unreleased]

### Changed

- **The README is a third of its former size, and the long reference material has moved to its own pages.** It had grown to 208 KB across 19 sections, and three of them were two thirds of that on their own: the CLI reference alone was 88 KB, which is more than most people will ever read in one sitting. The command reference now lives in [docs/cli.md](docs/cli.md), installation and the file-by-file list of what lands on your machine in [docs/install.md](docs/install.md), and the network, storage and uninstall detail in [docs/security.md](docs/security.md). Each of those keeps a short summary where it used to sit, with a link out. What someone deciding whether to install has to read stays on the README rather than moving behind a link: the three install commands, the no-telemetry statement, the disclosure naming the columns that hold your source code, the command that purges everything, and the pointer to the dependency advisories. Every cross-reference between the four files was rewritten and then checked by resolving each link and each heading anchor, so nothing points at a section that moved. The pages are published on the project site as well as readable on GitHub, and the npm tarball now carries them alongside the README, since a relative link in a shipped README pointing at a file the package does not contain leaves anyone reviewing it offline following a link to nothing. The two guards that pinned documentation to `README.md` by name now read the whole reader-facing set instead, and each one first checks that it found a substantial amount of text, so a mistyped path cannot read as full coverage. Site config changed with them: four working notes that share that directory and that nothing links to are no longer published. The other notes there keep generating, because the changelog links into them by name and excluding a page the changelog points at turns that link into a dead one. No reindex is needed. See [README.md](README.md), [docs/cli.md](docs/cli.md), [docs/install.md](docs/install.md), [docs/security.md](docs/security.md), [_config.yml](_config.yml), [package.json](package.json), [tests/readme_coverage.test.ts](tests/readme_coverage.test.ts) and [tests/ignores_pack_scope.test.ts](tests/ignores_pack_scope.test.ts).

Nothing published links to either, so dropping them costs no working link. [AGENTS.md](AGENTS.md) and [CLAUDE.arch.md](CLAUDE.arch.md) stay published, because the README and both changelogs link to them by name. Both files remain readable on GitHub. No reindex is needed. See [_config.yml](_config.yml).

- **The dependency tree is current again.** With the `sharp` conflict cleared, the updates that had been waiting behind it landed. Two of them reach an install: `sharp` 0.35.3 to 0.35.4, which powers image shrinking, and `puppeteer-core` 25.8.0 to 25.9.0, which takes the screenshots. The other six are development-only and none of them ships: `eslint`, `typescript-eslint`, `@types/node`, `js-yaml`, `fast-xml-parser` and `onnxruntime-node`. Every version was resolved as of a week ago rather than as of today, which is the same seven-day wait [.github/dependabot.yml](.github/dependabot.yml) applies to every proposed update, and the reason nothing published in the last week is in here. `npm audit --omit=dev` reports no findings, with or without optional packages. The VS Code extension carries its own manifest, and its `@types/node` moved to the same 26.4.0. No reindex is needed. See [package-lock.json](package-lock.json) and [vscode-extension/package-lock.json](vscode-extension/package-lock.json).

### Fixed

- **`sharp` can take dependency updates again.** It was listed twice with the same range: once as an optional dependency and once as a version override. Dependabot reads that as a conflict and stops resolving the file, so no update touching `sharp` could be prepared, and a grouped update that happened to include it failed as a whole. The override now uses npm's reference form, `"sharp": "$sharp"`, meaning whatever version the project already asks for. The override still does its job: [`@xenova/transformers`](https://www.npmjs.com/package/@xenova/transformers) asks for `sharp@^0.32.0`, and without an override npm installs a second, older copy nested underneath it. Re-resolving after the change leaves the lock file untouched, at the same 544 entries and the same versions, so nothing you install changes. No reindex is needed. See [package.json](package.json).

## [2.9.1] - 2026-09-02

### Fixed

- **`image-meta` and `image-text` no longer price an image as if it were text.** An image is not billed by how many bytes its file takes up; it is billed by area, in 28x28-pixel blocks, and one image can never cost more than the vision tier allows (1,568 tokens normally, 4,784 at the high tier). Both commands were running the image's **byte count** through the divisor meant for text, which is the wrong unit altogether. One recorded row credited 1,856,507 tokens for a single 7.4 MB image, more than a thousand times anything it could actually have cost. Both commands now price the image they replaced the way the API charges for it. `image-meta` reads the real pixel dimensions, so it is exact; `image-text` never learns them, so it uses the tier ceiling, which is the honest bound rather than a made-up number. Running `image-meta` on this project's own logo now records 871 tokens where it used to record 169,129. The correct helper already existed and was already used by image shrinking, which was fixed earlier; these two commands were simply never moved over. The byte figures both commands report are unchanged and were always right. The `stats --methodology` text has been corrected to say images are priced in visual tokens, since it previously stated that every entry used the bytes-over-four rule. Rows already in the stats database keep their old inflated values. No reindex is needed. See [src/cli.ts](src/cli.ts), [src/image_shrink.ts](src/image_shrink.ts), [src/cli_stats.ts](src/cli_stats.ts), [tests/image_stats_vision_tokens.test.ts](tests/image_stats_vision_tokens.test.ts), [tests/cli_image_meta_vision_stat.test.ts](tests/cli_image_meta_vision_stat.test.ts) and [tests/cli_image_text_vision_stat.test.ts](tests/cli_image_text_vision_stat.test.ts).

- **Compressed Bash output no longer claims a saving larger than what the model was ever going to receive.** Claude Code cuts a Bash result off at 20,000 characters: it writes the full text to a file and hands the model the shortened body plus a pointer to that file. Token-goat was measuring its compression against the *whole* command output, so shrinking a 30 MB command to 8 KB was booked as sparing 30 MB, when the model would only ever have been shown 20 KB of it. In the recorded numbers this is not a rounding error: 499 rows, each one an output above the cut-off, carried 17.1% of every token token-goat has ever claimed to save, and 157 grep and rg rows alone carried 421 million of them. Savings are now measured against the delivered slice, so an oversized output is credited at most the cut-off minus whatever was actually printed. The 20,000 figure was measured from recorded sessions and is **Claude Code's** behavior, not a universal one, so it is applied only on Claude Code; Codex, opencode and the rest keep their full uncapped figure until someone measures theirs. **Nothing about which outputs get compressed changes**: the decision to compress still looks at the real output size, because a compressed summary is still better than an arbitrary first 20 KB. Only the recorded number changes, and it goes down. Rows already written to the stats database keep their old inflated values; they record what was believed at the time and are not rewritten. No reindex is needed. See [src/delivery_cap.ts](src/delivery_cap.ts), [src/bash_runner.ts](src/bash_runner.ts), [src/hooks_bash.ts](src/hooks_bash.ts), [tests/bash_delivery_cap.test.ts](tests/bash_delivery_cap.test.ts) and [tests/bash_runner_delivery_cap.test.ts](tests/bash_runner_delivery_cap.test.ts).

- **Rewritten tool results for built-in tools now reach the model.** When token-goat compresses a Bash result, folds a Grep result, fences a fetched page or withholds lines a Read already served, it hands the harness a replacement through the `updatedToolOutput` field. That field has to carry the same shape the tool itself returns, and token-goat was sending a plain string. A string is only right for MCP tools, whose results are strings; for every built-in tool the harness kept the original output instead. Across recorded sessions that shows up as 337 Bash, 52 WebFetch, 32 WebSearch and 10 Grep rejections, and a count matching rejections to the rewrites causing them found 412 of 412 built-in-tool replacements discarded, on every version present. The tests asserted the shape token-goat itself produced, so the suite did not catch it. The replacement is now built by copying the tool's own result and swapping only the field that held the text, so every other field the tool sent survives untouched: for Bash that includes `persistedOutputPath`, which is the model's only way to fetch an output that was capped. Building a fresh object from a fixed list of field names would have dropped those, so it is deliberately not done that way. The field to swap is chosen by the same rule the hook used to read the text in the first place, from one shared resolver, so the two can no longer disagree about which field holds the body. When no text field can be found, as with WebSearch, the plain string is still sent and the harness still discards it, which is safer than putting the text in a field that never held it. Harnesses other than Claude Code take a plain string here and are unaffected. No reindex is needed. See [src/hook_registry.ts](src/hook_registry.ts), [src/hooks_common.ts](src/hooks_common.ts) and [tests/rewrite_output_shape.test.ts](tests/rewrite_output_shape.test.ts).

- **The text of a `Read` result is now read from where Claude Code puts it.** Claude Code sends a Read result as a small wrapper with the file's text nested one level down, under `file.content`. The helper that pulls text out of a tool result only looked at top-level field names, none of which matched, so it returned an empty string for every real Read. Two things depended on it and quietly did nothing: the check that spots a truncated Read before it is cached as a complete one, and the newer feature that withholds lines the same session already served, which therefore never fired. The helper now looks in the nested position after the top-level names fail, and both work again. No reindex is needed. See [src/hooks_common.ts](src/hooks_common.ts) and [src/hooks_read.ts](src/hooks_read.ts).

- **A `|`, `;` or `&&` inside quotes no longer looks like shell syntax to the compression gate.** Before a command's output can be compressed, the gate has to decide whether it is a single command or a pipeline, and it decided with plain substring checks: any `|` anywhere in the string meant "pipeline, leave it alone". A quoted regex alternation is not a pipeline. `grep -E 'foo|bar' src/` and `python3 -c "import sys; print(x)"` are both single commands, and both were disqualified from compression entirely. In a corpus of real sessions, 346 of the 1,553 grep results rejected for "has a pipe" (22%) contained no shell pipe at all. The gate now masks quoted spans before looking for the operator, using the same helper the neighboring background-`&` check already used, so there is still only one masking implementation. Genuinely compound commands are rejected exactly as before, and an unbalanced quote is still rejected. `$(` and a backtick keep their unmasked check on purpose, since double quotes do not suppress command substitution. One visible consequence: `python -c` and `node -e` snippets containing a `;` are now compressed like any other recognized command. No reindex is needed. See [src/tool_filters/helpers.ts](src/tool_filters/helpers.ts), [src/tool_filters/dispatch.ts](src/tool_filters/dispatch.ts) and [tests/tool_filters.test.ts](tests/tool_filters.test.ts).

- **A command that starts with `cd somewhere &&` no longer hands every output filter a garbled command line.** Filter selection already peeled a leading `cd DIR &&` off the command so the real tool landed first (that is how `cd /app && npm test` finds the npm filter at all), but the wrapper then re-derived the argument list a second time, from the original unpeeled command, and passed *that* to the filter. So the filter was chosen from one command and handed another: every filter that reads its own flags saw `cd` as the program name and the directory as the first argument. That is 45 filters, among them grep and rg (which look up the search pattern to decide where to clip a long line), make (target), cargo, dotnet, maven, gradle, go, webpack, gh, kubectl, helm, ansible, and the git log/diff/status filters. The visible symptom on grep was that a long matching line shipped at full length on a `cd`-prefixed search while the identical bare search clipped it, because the pattern the clipper looked for was the directory name and was nowhere on the line. In a corpus of real sessions, 592 of 1,884 long-line grep results were `cd`-prefixed. The wrapper now derives the argument list once, through the same peeling helper filter selection uses, so the two cannot drift apart again. No reindex is needed. See [src/bash_runner.ts](src/bash_runner.ts), [src/tool_filters/dispatch.ts](src/tool_filters/dispatch.ts) and [tests/bash_runner.test.ts](tests/bash_runner.test.ts).

- **A short grep result containing one enormous matching line no longer ships that line whole.** Below 30 matching lines the grep/rg filter passed its output through verbatim, and nothing anywhere in the pipeline looked at an individual line: the whole-output line and byte caps only measure the result as a whole. So a twelve-line search whose ninth hit landed inside a minified bundle sent that 5,000-character line in full. Measured across 4,664 real session transcripts (32,720 grep/rg results, 42.8 MB), 2.89 MB sat beyond 1,000 characters per line, spread over 1,872 results. Lines longer than 1,000 characters are now clipped to a window **centered on the match**, not to their first 1,000 characters: a head trim would have thrown away the answer whenever the hit sat past the cut, which is exactly what happens in minified files. The `path:lineno:` field (or the bare `lineno:` grep prints for a single file) is always kept, and every removed run is marked with its exact character count. When the match cannot be located by a plain substring scan (a regex pattern, `-i`, `-v`, `-e`/`-f`, `-z`, rg's `-U` or `-S`), the line is left completely untouched rather than trimmed blind. A clip that would cost more in markers than it removes is also discarded. The existing filter accounting is reused unchanged: no new stat kind, and the same net-savings floor that already decides whether the filter's output is worth shipping still applies, measured on the bytes actually emitted. No reindex is needed. See [src/tool_filters/helpers.ts](src/tool_filters/helpers.ts), [src/tool_filters/shell_file.ts](src/tool_filters/shell_file.ts) and [tests/tool_filters_shell_file.test.ts](tests/tool_filters_shell_file.test.ts).

- **`token-goat refs` no longer claims it saved you the whole contents of every file a reference lives in.** The `symbol_read` saving for `refs` was measured against the on-disk size of every file that contained a match, added together. A `refs` call that found call sites in 40 files credited itself all 40 files read end to end. There is a 100KB-per-file ceiling on that kind of baseline, but it bounds each file and never their sum, so a multi-file result walked straight past it: on one real ledger `refs` reported an average of 466KB saved per call, and the `symbol_read` line item alone was 298MB over 640 calls. Nobody reads 40 whole files to find call sites; they run a search. The baseline is now the search that `refs` actually replaces (one `path:line: label` hit line per reference), which is a deliberate lower bound on what a real `grep -n` would have printed, since a grep line carries the whole source line and a textual grep also returns comments and unrelated same-named symbols. The reported number for `refs` drops sharply and by design; nothing about what `refs` prints changes, and only the `symbol_read` events produced by `refs` are affected. The same counter recorded by `read "file::symbol"`, where the alternative genuinely is reading one file whole, is untouched. Historical rows already in the stats database keep their old inflated numbers; they are a record of what was recorded at the time and are not rewritten. No reindex is needed. See [src/read_commands.ts](src/read_commands.ts) and [tests/refs_stat_baseline.test.ts](tests/refs_stat_baseline.test.ts).

- **Corrected a stale comment on the `map` saving.** The doc comment above `mapLookupBytesSaved` still described the baseline as "the on-disk size of every file the map surfaces" even though that measurement had already been replaced with a plain listing of the same paths. Comment only, no behavior change. No reindex is needed. See [src/baseline.ts](src/baseline.ts).

- **A subagent's read could make the parent's re-read of the same file wrongly say "unchanged."** Read-dedup state (has this agent already read this file?) has been keyed per agent since an earlier fix, salting the key with the subagent id when one is present so sibling agents don't conflate each other's reads. The snapshot store that powers the unchanged/diff messages was never given the same treatment: every snapshot save and lookup in [src/hooks_read.ts](src/hooks_read.ts) still used the plain, unsalted session id. Since every subagent spawned from one parent shares the parent's session id, a subagent reading a file after the parent overwrote the parent's saved snapshot with the subagent's own copy. The parent's next re-read then compared the live file against content it never actually saw: reporting "unchanged" for a file that had in fact changed, or computing a diff against the wrong starting point. Snapshot keys are now built the same way session state keys already are, through one shared `sessionStateKey()` helper (moved to [src/hook_registry.ts](src/hook_registry.ts) so both callers use the identical code path). A parent session that already has a snapshot saved under the old, unsalted key from before this fix will fall back once to the ordinary re-read handling for that one file, exactly as if no snapshot existed yet; it snapshots normally again on the next read. No reindex is needed.

- **`session-audit` can see its own history again after a deny message is reworded.** The table that classifies deny messages into kinds had an entry for the old `MEMORY.md` wording removed once the code stopped emitting it. That looked safe and was not: this table classifies a corpus of past sessions, and transcripts written before the rewording still contain the old text forever. Removing the entry made 21 real denies unclassifiable (`memory_md_reread_deny` fell from 51 events to 30, 41% of that kind's recorded history), with a passing test suite and no error anywhere, which would have quietly shrunk the denominator under any rate later derived for that kind. The entry is restored, and a test now fails if a superseded wording stops being recognized. No reindex is needed. See [src/session_audit.ts](src/session_audit.ts) and [tests/deny_outcomes.test.ts](tests/deny_outcomes.test.ts).

### Added

- **New off-by-default option to stop a subagent loading a big markdown file whole.** Across 4,664 real session transcripts, the single largest pool of Read bytes is a subagent's first, un-ranged read of a markdown file: those reads are 10.4% of all Reads but 38.5% of all Read result bytes, and only 12% of them are followed by an edit of the same file, so they are overwhelmingly reading to understand rather than reading to change something. Setting `subagent_markdown_first_read_deny = true` under `[hints]` (or the `TOKEN_GOAT_SUBAGENT_MARKDOWN_FIRST_READ_DENY` environment variable) blocks that read and answers with the file's heading tree plus the `token-goat section` command for each heading, the same answer the existing re-read block already gives. It only applies when every one of these holds: the read is in a subagent, it is that subagent's first read of the file, it asks for no line range, the file ends in `.md`/`.mdx`/`.markdown`, it is at least 30KB, and it has at least three headings. A read that already asks for a line range is left alone, and so is every read in a main session. **The option defaults to `false`, so nothing changes unless you turn it on.** The block is recorded at zero bytes and zero tokens on purpose: no block of this shape has ever run, so how often an agent works around one is unknown, and claiming a saving from borrowed numbers would be a saving the feature cannot back up. The stat exists so `token-goat session-audit` can count the blocks and report what agents actually did next. No reindex is needed. See [src/hooks_read.ts](src/hooks_read.ts), [src/config.ts](src/config.ts), [src/session_audit.ts](src/session_audit.ts) and [tests/subagent_markdown_first_read_deny.test.ts](tests/subagent_markdown_first_read_deny.test.ts).

- **Re-reading a memory file (`MEMORY.md`, or any `.md` file under a `memory/` directory) now checks whether it actually changed before denying the re-read.** This deny used to always answer with the same flat "already read this session" message, whether or not the file changed, even though the same unchanged/diff snapshot logic already used elsewhere in this file was sitting right there unused. Measured against this project's own session corpus, Edits made right after this specific deny error 8.9x more often than the corpus-wide baseline (the worst of any deny kind), which is the signature of a deny withholding information the agent then needed. Now, on a re-read, it checks the snapshot from the earlier read first: unchanged content gets a one-line "unchanged since last read" answer, a small change gets a fenced diff of just what changed, and a missing or unusable snapshot (including a truncated one) still falls back to the exact original deny message. No reindex is needed. See [src/hooks_read.ts](src/hooks_read.ts).

- **Re-reading an unchanged or lightly-edited large markdown file now gets a short answer instead of the full heading tree.** The heading-tree deny that fires on a re-read of a large markdown file (the highest-volume deny in the product, 842 occurrences in this project's own session corpus) used to return before the existing unchanged/diff snapshot logic ever ran, so a snapshot from the first read was never consulted for markdown files large enough to trip it. Now, on a re-read, it checks that snapshot first: unchanged content gets a one-line "unchanged since last read" answer, a small change gets a fenced diff of just what changed, and a missing or unusable snapshot (including a truncated one) still falls back to the full heading tree exactly as before. No reindex is needed. See [src/hooks_read.ts](src/hooks_read.ts).

- **The deny-outcome census in `session-audit` no longer counts a deny as "abandoned" just because it can't see how the agent actually responded.** Two blind spots meant the census was crediting itself work the agent had already routed around. First, the check for a substituted `token-goat` command only matched a command that started with `token-goat`/`tg`, so `cd somewhere && token-goat section file.ts::Heading` and `node dist/token-goat.mjs read file.ts::Foo` were both counted as no substitution at all; that check now also matches after a shell separator (`;`, `&`, `|`, `(`, or whitespace). Second, there was no way to see the single most common real response to a deny: reading the same file with a shell command instead (`sed`, `grep`, `cat`, `head`, `tail`, `awk`, `rg`, `less`, `nl`, `python`, or `node`). Every one of those fell through to "abandoned" before. There is now a `shell_read` outcome for it, which subdivides "abandoned" rather than sitting alongside it, so the outcome rates still sum to exactly 1.0 for every deny kind. A short basename (like `index.ts`) appearing only as an incidental substring of a longer, unrelated filename is not credited as a shell read; those ambiguous cases are counted separately in a new `shellReadAmbiguousCount` field instead of being silently guessed either way. There is also a new Edit-error canary: for each deny kind, the count of Edits to the exact denied path that errored (`is_error: true`) within the following 10 calls, alongside a corpus-wide Edit-error baseline (`editErrorBaseline`) so that count has a denominator to compare against. On this project's own session corpus, the two blind spots together moved the overall abandoned rate from 73.5% down to 40.3%, with most of that landing in the new `shell_read` and (for the unanchored command check) `substituted` buckets. No reindex is needed. See [src/session_audit.ts](src/session_audit.ts).

- **Fix the deny-outcome Edit-error canary denominator mismatch.** The per-kind `editErrorWithin10Count` was previously compared against `editErrorBaseline.rate` directly, but they have different denominators: the per-kind count is errors out of that kind's denies, while the baseline is errors out of corpus-wide edits. Added `editWithin10Count`: the number of denies where an Edit on the denied path occurred within 10 calls (regardless of error), making the ratio `editErrorWithin10Count / editWithin10Count` directly comparable to `editErrorBaseline.rate`. On this project's corpus: 32 errors out of 426 at-risk Edits on denied paths (7.51%) versus 398 errors out of 22,106 corpus-wide Edits (1.80%), revealing a 4.17x elevation in error rates for Edits on recently-denied paths, not a weak signal. Both `editWithin10Count` and `editErrorWithin10Count` now appear in text and JSON output. No reindex is needed. See [src/session_audit.ts](src/session_audit.ts).

- **`session-audit` now measures what actually happens after a Read is denied, instead of assuming the worst case.** Every deny (a re-read block, a large-file block, a stale-cache serve, and 20 other message shapes) was credited as a saving equal to the full withheld bytes, on the assumption that a denied read always turns into a costly retry. That assumption was never checked. A deny can also be a wash (the agent substitutes the surgical command it should have used) or a genuine win (the agent abandons a read it did not need), and nothing distinguished the three.

  `session-audit` now classifies every deny message into one of 24 kinds and, for each one, measures the tool calls that follow it in the same transcript: whether the next few calls were a plain re-read (a real retry), a `token-goat read`/`section`/`symbol`/etc. command against the same file (a substitution, not a retry), nothing at all before the transcript ended (unresolved), a later re-read that's correct by design because a compaction happened first, or none of the above (abandoned). Counts and rates for all five outcomes appear next to the existing "Read interception" section, and `--json` adds a `denyOutcomes` array with per-kind medians of withheld bytes, remaining calls, and the next API call's raw token usage. Nothing is converted to a billed-token estimate; the raw usage numbers are reported as-is. No reindex is needed. See [src/session_audit.ts](src/session_audit.ts).

- **Compact `token-goat --help` output under 4096 bytes.** The top-level help was 23,988 bytes: a 133-line guide that named every command with a full description, was run 138 times in a corpus, and cost ~60KB per session on average. It is now a 2,318-byte grouped command index organized by category (reads, analysis, file formats, indexing, session, skills, compression, config, data, utilities). All 148 command names still appear. The full original listing is still there when you want it: `token-goat help --full` prints it in one go, `token-goat <command> --help` prints one command's help, and `token-goat commands --grep <pattern>` searches. Keeping `--full` working needed care, because replacing the short help sets a property on the program object that hides the built-in formatter from everything else that asks for it, including `--full` itself; the original is now saved before that happens, and a test fails if `--full` ever returns less than the short index it is supposed to expand. No reindex is needed. See [src/cli.ts](src/cli.ts) and [tests/help_full_restores_long_form.test.ts](tests/help_full_restores_long_form.test.ts).

- **Skill notices now offer `skill-section` before `skill-body`.** When a skill is cached, too large, or has a compact slice available, the denial notice now offers the cheapest recall command (`skill-section`) before the more expensive alternatives (`skill-body --compact` and `skill-body`). No reindex is needed.

- **Top symbols list no longer includes test-file variables.** `token-goat map --compact` and agent briefings were reporting test-file local variables and short names (out, file, result, slice, find) as top project symbols, actively misleading. Now filters out files matching `*/tests/*`, `*/test/*`, `*/__tests__/*`, `*/spec/*` and `*.test.*`, `*.spec.*`, and excludes names shorter than 4 characters. Also changed ref counting from `COUNT(*)` to `COUNT(DISTINCT file_path)` to rank by number of files using a symbol rather than raw reference count. No reindex is needed.

- **Reading the same unchanged file twice through the shell no longer costs twice.** Reading a file with `cat`, `head`, `tail`, or `sed -n '1,40p'` went through the shell rather than the read tool, and the shell path had no memory: nothing was cached, nothing was compared against a previous run, and the same file read five times sent its full contents five times. In one recent session the same 40-line slice of a changelog was read six times, at roughly 6,500 tokens each.

  Now, when one of those reads runs again and comes back byte-for-byte identical to the earlier run, the repeated copy is replaced with a single line saying the file has not changed and giving the command to bring the contents back. Nothing is summarized or thrown away: the two versions are the same bytes, so what is dropped is a duplicate, and the full text stays available through `token-goat bash-output <id>`. A read of a file that did change is left completely alone, as is anything that is not a plain file read, because for a test run or a build "the same output as last time" is the answer rather than a repeat. The comparison is also limited to the conversation you are in: the stored copy outlives a session, but the first read in a new one is left whole, because the point is to drop a copy you already have rather than to hand you a pointer to text you have never seen. Measured on this project, one repeated read went from 4,031 bytes to 189.

  This replaces the output rather than advising against the read, which matters: the advice token-goat used to give about shell reads was followed 2.7% of the time, while the places where it acts on the content directly land above 95%. Savings show up in `token-goat stats` under `bash_compress:identical-reread`. No reindex is needed.

- **Reading part of a file you have already read costs nothing extra.** The collapse above only recognized the exact same command run again. The reads that actually repeat are not spelled the same: in one measured session the three most expensive shell calls were `sed -n '1,40p' CHANGELOG.md`, `head -40 CHANGELOG.md`, and `sed -n '1,30p' CHANGELOG.md`, roughly 6,600 tokens each. Three different commands, three different results, and the third showed nothing the first two had not.

  A read of a file is now checked against everything already served for that same file this session, not just against an identical command. When every line coming back was already shown, in order, as part of a wider read, the repeat is replaced with a line saying so and giving the command to bring the earlier output back. The check is on the text itself rather than on line numbers, which matters because line numbers stop being true the moment a file changes in a way token-goat did not see, such as a pull in another terminal.

  It only holds back a read that adds nothing. A read reaching past what was shown is left whole, since part of it is new. A match has to line up with whole lines at both ends, so a read that starts or stops in the middle of a line already shown is left alone rather than being answered with lines the model never saw as lines. Two files that happen to hold the same text are kept apart, because the recall command has to point at the file that was actually read. And the record is dropped whenever the text behind it stops being trustworthy: when the file is edited, and when the conversation is compacted and the earlier output is no longer in context. Savings show up in `token-goat stats` under `bash_compress:contained-reread`. No reindex is needed.

- **A file opened the ordinary way now counts as already read when the shell asks for it again.** The check above compares a shell read against everything already served for that same file, but only shell reads were ever written into that record. A file first opened with the read tool was invisible to it, so `sed -n '1,40p' README.md` run after reading README.md came back in full, and the half of that check meant to catch this never fired once in a month of real sessions. Measured on this project's own sessions, a third of the shell reads that name a line range ask for lines the conversation is already holding.

  A finished read now records the lines it actually handed over, so a later shell read of those same lines is recognized and replaced with the same one-line pointer. What gets recorded is the file's own text rather than the read tool's numbered display, because the plain text is what `sed` and `cat` will print and what the comparison is made against. A read that asked for part of a file records only that part, so a later read reaching past it is left whole rather than being answered with lines nobody was shown. A read that came back truncated records nothing at all: it delivered less than it asked for, and there is no way from here to tell where it stopped. Savings continue to show up in `token-goat stats` under `bash_compress:contained-reread`. No reindex is needed. See [src/hooks_read.ts](src/hooks_read.ts).

- **A file is no longer sent again when the exact lines are already in the conversation.** Everything token-goat did about repeated reads counted them: how many times a file had been opened, how large it was, how recently it was touched. Counting is a guess, and because it is a guess there is a safety valve, which leaves the four most recently read files alone so a read that is genuinely needed is never blocked on one. That valve covers the case where the answer is most obvious: a file read a moment ago is a file whose contents are certainly still in the conversation. Over a month of real sessions, 830 reads returned a line range that had already been handed over, and sitting inside that window was the main reason nothing happened.

  When the lines can be checked rather than guessed at, they are. Before a repeated read goes through, the text it would return is compared against the text already given out for that same file this session. If every line matches, whole line for whole line, the read is answered with a line saying so and the command to bring the earlier copy back, instead of the file. Counting still decides everything else; this only takes over where there is proof.

  The comparison is on the text, never on line numbers, so it goes the safe way in every case that matters. A file changed since it was last read no longer matches, and the read goes through. A read asking for more than was given before carries lines nobody has seen, and goes through. A read of something never delivered goes through. Turning re-read denial off turns this off too, because a setting that asks for hints instead of blocks is not overridden by having better evidence. Savings show up in `token-goat stats` under `read_served_deny`. No reindex is needed. See [src/hooks_read.ts](src/hooks_read.ts).

- **A read that asks for more than you already have now sends back only the part you do not.** Everything above is all-or-nothing: a read is replaced with a pointer when every single line of it was already delivered, and left completely alone otherwise. That leaves out the shape most repeated reads actually take. Opening a file, then opening it again to see further down, asks for the lines you just read plus some new ones, and because part of it is new the whole thing comes back, first lines included.

  A finished read is now compared against what has already been handed over for that same file in this conversation, line by line. Any stretch that was shown before, in the same order, is replaced with one line naming the line numbers it stands in for and the command to bring them back. Everything else comes through exactly as it arrived, with its own line numbers and its own spacing, unchanged byte for byte, so a later reference to "line 47" still points at line 47. Reading a 60-line file whose first 40 lines had already been read returned 1,924 bytes instead of 5,321.

  Its caution is in what it declines to do. A stretch is only held back when dropping it saves more than the line replacing it costs, so five short lines are left alone rather than swapped for a longer notice, and the rewrite as a whole still has to clear the same minimum saving as every other rewrite before it is used at all. A result holding anything the redactor would strip is passed through whole, because handing back a redacted copy of your own file would show you less than a plain read does. A truncated result is left alone, since there is no telling what it left out. A file changed on disk since it was served no longer matches and comes through in full. And where this fires, the advice token-goat would otherwise have given about the same read is not shown, so you are never charged for both.

  Savings show up in `token-goat stats` under `read:served_elide`. Set `elide_served_lines = false` under `[hints]` to turn it off. No reindex is needed. See [src/hooks_read.ts](src/hooks_read.ts).

- **Color codes in shell output no longer cost anything.** A command run with color on sends the escape sequences that paint a terminal along with its text. There is no terminal on the other end of a tool call, so those bytes arrive as tokens and say nothing. They are not a rounding error either: on a real `git diff` of this project they were 13.2% of the output, and `token-goat`'s own colored output is over half escape bytes by weight.

  Shell output that nothing else compressed now has its escape sequences removed. This is the one change on that path that holds nothing back. What comes through is byte-for-byte the same output with color turned off, so there is no summary, no marker, and no recall command, because there is nothing to recall: a marker would only spend bytes announcing that nothing was lost.

  It runs on commands that failed, too. The compressing paths deliberately leave a failed command alone so its diagnostics arrive whole, and here removing color is what keeps a failed build whole rather than shortening it. It stays out of the way otherwise: output with no escapes is untouched, and output whose escapes are too few to be worth a rewrite is left as it is, so a single colored word does not trigger one. Turn it off with `disabled_filters = ["ansi"]` under `[bash_compress]`, or with the existing `TOKEN_GOAT_BASH_COMPRESS=0`. Savings show up in `token-goat stats` under `bash_compress:ansi`. No reindex is needed. See [src/hooks_bash.ts](src/hooks_bash.ts).

- **The index now catches up on what changed while nothing was watching.** Every way token-goat noticed a file had changed ran from a hook: the edit hook queues what the agent edits, the shell hook queues what a branch switch or an in-place rewrite touches, and a command naming a file reparses it on the spot. Between them, a change made during a session is covered. Nothing covered a change made outside one. A pull in another terminal, a save from an editor, a code generator run from a different window: the file on disk moves on and the stored copy does not, and the commands most likely to be asked first are exactly the ones that never name a file, so none of them triggers the per-file repair. `semantic`, `symbol` by name, `find`, `refs`, `callers`, `arch` and `dead` all answer from whatever was stored, and a stale answer looks the same as a correct one.

  Starting a session now sweeps the project once and queues anything whose content no longer matches what was stored, so the repair happens before the first question rather than after a wrong answer. It compares the two things that have to agree rather than trying to list the ways they can disagree, so a cause nobody thought of is covered by the same code. The sweep reads a timestamp per file and nothing else in the ordinary case, and only reads a file's contents when its timestamp moved, so the steady-state cost on a session start is one filesystem call per tracked file. A moved timestamp is treated as a suspicion and confirmed by content, never taken as proof: switching branches rewrites every timestamp in the repository while leaving most files identical, and a sweep that believed timestamps would queue the whole project every time you changed branch. It is bounded by a time budget, it never fails a session start, and it says nothing at all when the stored copy is already correct. When the budget cuts it short it says so and reports no deletions at all, because a file it never reached looks exactly like one that was deleted, and guessing there would queue live files for removal. It holds back the same way in a folder git cannot list at all, which happens when the folder is not a repository, when git is missing, and when git simply fails: an empty list of files there is not the same thing as an empty project, and reading it as one would report every stored file as deleted and drop the whole index for that folder. It says which of the two it is instead of picking. **Files it finds are queued for reindexing, which is the point**; nothing else needs a reindex. Set `TOKEN_GOAT_RECONCILE=0` to switch the sweep off, or `TOKEN_GOAT_RECONCILE_BUDGET_MS` to change its budget. The same sweep is available as `token-goat reconcile`, with `--dry-run` to see the drift without queueing it. See [src/reconcile.ts](src/reconcile.ts) and [src/hooks_session_start.ts](src/hooks_session_start.ts).

- **`token-goat affected` names the test files a change can reach.** Given a list of changed files it walks the project's import graph backwards, so a test that imports a helper that imports the changed file is reported alongside a test that imports it directly. The intended use is narrowing a run to the tests a change can actually break: `git diff --name-only | token-goat affected --stdin --quiet` prints bare paths ready to hand to a test runner.

  It answers a different question from `test-for`, and neither replaces the other: `test-for` asks which tests mention a file's symbols by name, one step, from the stored symbols; this asks which tests reach a file through imports, however many steps away. A test that goes through a helper mentions none of the changed file's names and is invisible to the first; a test that mentions a same-named symbol defined somewhere else is visible to the first and not here. Because a short list of affected tests looks exactly like a complete one, and acting on a short one means shipping a change believing it was covered, every way this can return less than everything says so: a path that is not a tracked file is named rather than dropped, and a depth limit that actually cut the walk short is reported with how many files were left unexplored. Both of those still print under `--quiet`, on the error stream, so what gets piped into a test runner stays bare paths. `--filter` takes a regular expression deciding what counts as a test, and an invalid one is refused rather than quietly matched as plain text, because a typo silently selecting a different set of tests is the exact failure this command exists to prevent. No reindex is needed. See [src/affected.ts](src/affected.ts).

- **`token-goat arch --modules` shows what the project is actually made of.** `arch` already answers three questions about single files: which are imported most, which nothing imports, and which import each other in a circle. None of them says which files form a group that mostly talks to itself, or where one group reaches across into another, and that is the question worth asking before a refactor. It is a property of the whole graph, so no per-file number produces it.

  The new section groups the files by who imports whom, using the import graph `arch` already builds, and names each group by its most connected member rather than by a shared folder: a group normally holds a source file and the test that imports it, those live in different folders, and naming by the shared folder gave every group on this project the same empty name. Each group says whether it is one folder or spread across several, which is the interesting half: a group that matches a folder is the layout you already have, and one that does not is the part worth looking at. Below the groups it lists which group imports which, and how many times, with the direction kept.

  It also prints how strong the grouping is, because the method returns groups for any graph at all, including one with no real structure, so a result that looks like a finding is the default rather than the exception. Below a threshold the output says the grouping is weak and should be read as a hint, instead of presenting it as structure. The grouping is reproducible: the order files are visited and the way ties are settled are both fixed, so the same project gives the same answer on every run and on every machine. Files that neither import nor are imported are reported as a count rather than becoming a group each. Everything the `--top` limit leaves out is named, in both the group list and the cross-group list. Off unless asked for, so plain `arch` prints exactly what it printed before and its `--json` payload gains no fields; `--modules --json` adds the full member list of each group. No reindex is needed. See [src/modules.ts](src/modules.ts).

- **The MCP tool surface can be trimmed to the tools you actually use.** Every tool a server offers is described to the model on every request for the length of the session: its name, its summary, and the full shape of its inputs. Measured on this server's own listing, all eighteen come to roughly sixteen thousand bytes, about four thousand tokens, and the input shapes account for more of that than the summaries do. A setup calling two of them pays for all eighteen, every message.

  `TOKEN_GOAT_MCP_TOOLS` takes a comma-separated list of tool names and registers only those. A name that matches nothing can only fail to select a tool, never invent one, so a typo makes the surface smaller rather than larger, and because a smaller list is indistinguishable from a correctly filtered one the server prints any unmatched name to its error stream at startup. An empty value is treated as unset rather than as a request for a server with no tools. The summaries themselves are deliberately left alone: they are what steers a model to the right tool, and a surface that is cheap and unusable costs more than one that is expensive and right. No reindex is needed. See [src/mcp_server.ts](src/mcp_server.ts).

It also left out the part that decides when it fires, which is that the check is keyed on the page address and the question together, because a fetch answers the question you asked and handing back an answer written for a different one would be wrong. ### Changed

- **Indexing no longer takes most of the machine while it runs.** Building embeddings runs a small neural model, and the runtime that executes it, ONNX Runtime, decides for itself how many threads to use when nobody tells it otherwise: it takes the whole host. Measured here on a 26-core machine, creating that session took the process from 13 operating-system threads to 30, and every single embedding call then spread across all of them. Two indexing paths did this: the background worker, which is invisible because it runs detached with its output discarded, and the `token-goat index` command. Neither asked for fewer threads, and neither asked the operating system to schedule it behind whatever the user was actually doing. On a large index that is felt as the whole computer stalling for as long as the walk lasts, with nothing on screen to explain it.

  Both are now fixed, with two settings that work independently. `worker.embed_threads` (default 4, range 1 to 16, `TOKEN_GOAT_EMBED_THREADS`) caps how wide one embedding call can spread; the same measurement showed a session created with an explicit count adds no threads at all. `worker.priority` (default `below_normal`, also `low` or `normal`, `TOKEN_GOAT_WORKER_PRIORITY`) is what both indexing paths now ask the operating system for, which costs nothing on an idle machine because the scheduler only steps a process down when something else wants the processor. Nothing above `normal` can be set, so a checked-in project file cannot put a background indexer ahead of your own work; an unrecognised value falls back to the default rather than to the system default, because a typo there would silently restore the old behaviour. Where the platform refuses the change, which some hardened Linux setups and sandboxes do, indexing continues exactly as before rather than failing.

  Indexing takes longer in exchange, and on a machine that is otherwise idle it takes longer than it used to. Indexing this project's own `src` through the built binary took 210 seconds at the new default of 4 threads and 384 seconds at 2, one run each on one machine, so treat those as the size of the effect rather than precise figures. Four is where it settled because of what a foreground responsiveness probe found on a 26-core machine: with the priority set below normal, 2, 4 and 6 threads are all indistinguishable from an idle machine, and they stay indistinguishable when the indexer and the probe are confined to the same 4 processor cores, and still when 4 threads are confined to 2 cores, which is more threads than cores. The same probe reads a 10% drop at 16 threads, and a 69% drop with a 292 millisecond stall at 4 threads on 2 cores, once the priority is normal instead. So it is the priority, not the thread count, that keeps the rest of the machine usable, and the cap is what remains where the platform refuses to change priority at all. Existing embeddings are unaffected and **no reindex is needed**: the model output was compared at the old and new thread counts and all 4224 values were bit-identical, maximum difference zero, so vectors written before and after this change are interchangeable. See [src/embed_model.ts](src/embed_model.ts), [src/process_priority.ts](src/process_priority.ts), [src/worker.ts](src/worker.ts) and [src/cli.ts](src/cli.ts).

- **A structural check now stops the thread cap being dropped by a later edit.** Nothing about a bare session call fails: indexing works perfectly, it just takes the machine, so no functional test can see it. The new guard reads every session-creation call in the source, requires each to pass a thread count that comes from configuration rather than a hardcoded number, and separately asserts that it found a call at all, so the check cannot quietly pass by finding nothing after a rename. All three of those were confirmed by breaking the code three ways and watching the matching test, and only the matching test, go red. See [tests/guards/embed_session_thread_cap.test.ts](tests/guards/embed_session_thread_cap.test.ts).

## [2.8.5] - 2026-08-29

### Security

- **Third-party text is now always marked as untrusted, instead of only when it matched an injection pattern.** A fetched page, a search result, an MCP server's reply, recalled command output, a PDF or Word or Excel or PowerPoint body, a pull-request diff, a Google Doc section, and a recall listing are all somebody else's writing. Until now each of those was wrapped in an untrusted-content fence only if the text matched one of eight deliberately narrow attack phrasings, which meant anyone wording the same instruction differently got an unmarked channel straight into the model, and a miss was silent. All of them are now fenced for where the text came from. The scan still runs and is still counted: it decides whether the notice names the patterns it found, not whether the fence appears. This is the rule already applied to image text in 2.8.4 and to file bytes spliced into a denial message, now applied everywhere. The decision lives in one new place, [src/untrusted_fence.ts](src/untrusted_fence.ts), rather than being restated at each site, because the eight sites that restated it all got it wrong the same way. `injection.enabled = false` still switches the whole thing off in one line, and now covers the image-text path too, which used to fence regardless of the setting. See also [src/cli.ts](src/cli.ts), [src/read_commands.ts](src/read_commands.ts), [src/cli_recall.ts](src/cli_recall.ts), [src/hooks_fetch.ts](src/hooks_fetch.ts), [src/hooks_mcp.ts](src/hooks_mcp.ts) and [src/hooks_websearch.ts](src/hooks_websearch.ts).

  Two things to expect. Output that used to arrive bare now carries a two-line wrapper, measured at 124 to 125 bytes on real `docx-text`, `xlsx-head` and `bash-output` runs, rising to about 195 when the notice names a matched pattern, so short recalls are slightly larger; the wrapper is added once around a printed block rather than once per item, so a listing of forty snippets pays for it once. And `--json` output is the one exception: a fence wrapped around JSON is no longer JSON, so those envelopes still fence individual fields only on a pattern match. The printed form of the same command is always fenced. No reindex is needed.

- **The structural check that was supposed to catch this could not see it.** The existing guard tested that a function which reads third-party content can *reach* a fence call, which stayed true the whole time the fence sat behind an `if (matches.length === 0) return text`. It now checks the thing that matters: that no fence can be skipped by a zero-match early return, with a named exception list for the `--json` field cases and a check that the exception list has no stale entries. Mutating a fixed site back to the conditional shape leaves the old check green and turns the new one red, naming the function. Thirteen document-extraction entry points were added to the guard's list of sources at the same time. See [tests/guards/third_party_content_reaches_fence.test.ts](tests/guards/third_party_content_reaches_fence.test.ts).

## [2.8.4] - 2026-08-28

### Security

- **Text read out of an image is now always marked as untrusted, instead of only when it matched an injection pattern.** OCR is the one extraction path where the content is authored in pixels: nobody, not the user and not any scanner reading the file, can see what an image says without decoding it, so the model is the first reader of that text. Two things were wrong. The image-shrink path, which OCRs automatically when a read hits a text-heavy image and puts the result straight into context, had no marking of any kind: a user who asked to read a screenshot got its text injected without ever requesting a decode. The `image-text` command did mark its output, but only after a match against a short list of injection phrasings, so anyone wording the same instruction differently got an unmarked channel, and a miss was silent. Both paths now wrap the recovered text unconditionally, in their own `untrusted-image-text` fence, on the same reasoning already applied to file bytes elsewhere in token-goat: the text is marked for where it came from, not because a heuristic recognized it. Pattern scanning still runs and is still counted, it just no longer decides whether the marking appears. See [src/injection_scan.ts](src/injection_scan.ts), [src/image_ocr.ts](src/image_ocr.ts) and [src/cli.ts](src/cli.ts).

- **The OCR language model is now fetched from a pinned source and checked before it is used.** OCR is optional and off unless `tesseract.js` is installed, but when it runs it needs a 5 MB English language model that is not part of any package: `tesseract.js` downloads it from a CDN on first use with no checksum, signature, or size check anywhere in its code. The default URL made that worse than it looks. An npm CDN path resolves to the newest publish unless it names a version, and the default names none, so the URL silently followed whatever was published latest, with no lockfile entry that would ever notice the change. Token-goat now requests the model from an explicitly versioned URL and records the SHA-256 of the exact artifact that URL serves. A cached model is verified before it is handed to the parser; one that fails is deleted, refused, and stays refused for the rest of the process, and `token-goat image-text` says the model failed its checksum rather than blaming the image. The next run starts from a clean cache and downloads again from the pinned source, so a corrupted cache repairs itself with no user action. See [src/image_ocr.ts](src/image_ocr.ts).

- **New [socket.yml](socket.yml) recording which supply-chain alerts are noise and which are known.** The Socket scan of 2.8.3 passed with 729 alerts, of which 724 were a licence-shape notice that fires on any package offering a choice of permissive licences. Those are now suppressed so the report is readable. The five remaining alerts are documented individually instead: three are development-only and reach no user of the published package, and two arrive under the optional OCR dependency. The alert class itself is deliberately left enabled, because turning it off would equally hide a genuinely malicious payload in some future dependency. The file also records the gap no package scanner can see, a binary downloaded at runtime rather than shipped, and names the checksum work above as its owner.

### Added

- **Image shrinking now works on Copilot CLI and OpenClaw.** Both bridges lacked the context channel the shrink payload rides on Claude Code, so a large image read reached the model at full size there. They now use the same delivery the opencode and pi bridges already proved: the shrunk image's data URL is decoded to a temp file and the read call's path argument is rewritten to point at the shrunk copy, over each harness's own argument-rewrite channel: `modifiedArgs` on Copilot's `preToolUse` (carrying the full original arguments with only the path swapped, because Copilot replaces the argument object wholesale) and rewritten `params` on OpenClaw's `before_tool_call`. The decoder is now one shared block ([src/bridges/shrink_block.ts](src/bridges/shrink_block.ts)) instead of per-bridge copies, and it sweeps its own stale temp copies (prefix-checked, age-gated) on every materialization, on every bridge that uses it. - **A once-per-session advisory when a subagent spawn runs as unrestricted general-purpose while tools-restricted agent definitions exist.** Corpus measurement across 5,988 subagent lanes showed the causal lever on spawn-prefix cost is the agent definition's `tools:` allowlist, not its type: an agent without one inherits every tool and MCP schema into its lane's system prompt (median net prefix ~92,500 tokens for general-purpose, versus ~35,000 for the same agent after its definition gained a `tools:` line). The subagent-lane rollup reads each lane transcript's first API response, whose input total is the spawn prefix (system prompt, tool and MCP manifests, inherited instruction files, and the task brief), reports mean, median and p90 prefix size, calls per lane, and mean task-brief bytes, and models the prefix's billed carriage with the same cache-write-then-re-read model as the attachment census. The Bash census classifies every Bash tool result: carrying a token-goat marker (a filter or recall hint demonstrably fired), too small to be worth compressing, or untouched: the untouched pool is sized in bytes, estimated tokens and modeled billed cost, and bucketed by bare command head (the binary name only, never the command line), which names the shapes any future filter work should aim at. The annotation is now capped at 140 characters, cut at a word boundary with a visible ellipsis; short summaries render byte-identically, and the full doc text is one `token-goat read "file::symbol"` away. A census of 13,614 real token-goat invocations across local session transcripts ranked outline third by total output bytes, and this was the only avoidable share: counts, ranges, truncation notices and filter explanations are all kept. `--json` output is unchanged and still carries the full docstring. - **The cat and awk read hints now fire on the respelled reads a corpus census found them missing.** The same census method as the sed fix below, run over 8,179 real `cat`-headed and 916 real `awk`-headed commands from local session transcripts. Four clusters were the same read wearing different clothing and got no hint at all: a `cat file 2>&1` or `cat file 2>/dev/null` suffix (144 commands; the `2>/dev/null` spelling tolerates a missing file, so it gets guidance instead of a deny), the piped partial-read spellings `cat file | head -N` and `cat file | tail -N` (310 commands, now treated exactly like `head -N file` / `tail -N file`, including the already-surgical N<=10 exemption and the line-range ledger), `cat file | sed -n 'N,Mp'` (35 commands, rewritten into the direct sed form so the same range validation and overlap dedup apply), and an awk `NR` range whose action block prints each whole line at most prefixed with its line number, such as `{print NR": "$0}` or `{printf "%d|%s\n", NR, $0}` (91 commands; awk also now accepts a `2>&1` suffix like sed does). Measured on the same corpus, cat-headed read-hint admission rose from 15.1% to 21.1% and awk-headed from 10.3% to 23.7%; the large cat remainder is writes and heredocs, which are not reads. See [src/hooks_bash.ts](src/hooks_bash.ts).

- **The sed line-range read hint now fires on the compound and piped spellings that dominate real traffic.** A census of 19,380 real `sed` commands across 8,545 local session transcripts found the hint's admission pattern matched only 66.8% of them: it required exactly one quoted `sed -n 'N,Mp' file` command and nothing else. ### Fixed

- **The compaction record printed a token figure on a different scale from every other token figure in `token-goat stats`.** Its detail line reports the size of a compaction summary, and it derived that from the estimator token-goat uses to guard buffer limits, which divides by three because guessing high is the safe direction for a guard. Beside it on the same line, the byte figure came from a byte count while the token figure came from a UTF-16 string length, so the two disagreed on non-ASCII text as well as on scale. Nothing was miscredited: this record books a zero saving and no total moved. But a reader comparing it to the token counts elsewhere in the same command was comparing two different units. It now uses the one conversion every saving uses. A test additionally keeps the guard estimator out of any file that records statistics at all, which closes the gap the previous scans left: they checked single lines, so a figure computed on one line and recorded on the next passed them. See [src/hooks_compact.ts](src/hooks_compact.ts).

- **Zig declarations carrying `export`, `extern` or `threadlocal` were dropped from the index.** Loop 61 taught the Zig extractor about the `pub` keyword, but `pub` is only the first of the prefixes a top-level Zig declaration can carry. The Zig grammar (the comment above `expectTopLevelDecl` in `lib/std/zig/Parse.zig` in [the Zig compiler](https://github.com/ziglang/zig/blob/master/lib/std/zig/Parse.zig)) allows `pub`, then at most one of `export`, `extern` with an optional calling-convention string, `inline` or `noinline`, then `threadlocal` for variables. Every one of the four patterns in the extractor accepted a bare optional `pub` and nothing else, so `export const build_id = 7;`, `threadlocal var scratch: [64]u8 = undefined;`, `pub threadlocal var current_task = null;` and `extern "c" var environ;` all produced no symbol at all, and a prefixed container such as `pub export const Wrapper = struct {...}` took its methods down with it, because no scope was opened for a container the pattern never saw. The four patterns are now built from two shared prefix fragments, one for variables and one for functions, so they stay consistent with each other: `inline` and `noinline` are accepted on functions only and `threadlocal` on variables only, matching the grammar rather than widening every pattern to everything. Like every change to what token-goat extracts, this reparses already-indexed files once on upgrade: the parse-freshness entry below explains what that costs. See [src/languages/zig.ts](src/languages/zig.ts).

- **Only the first name of a multi-name Lua `local` was indexed.** A Lua `local` statement binds a whole list of names: the Lua 5.4 reference manual, section 3.3.7 in [the Lua manual](https://www.lua.org/manual/5.4/manual.html#3.3.7), gives it as `local attnamelist ['=' explist]` with `attnamelist ::= Name attrib {',' Name attrib}`. The extractor's pattern captured one name and stopped, so in `local ok, err = pcall(dofile, "cfg.lua")` only `ok` was stored and `err` was never indexed, and the common module header `local sqrt, floor, ceil = math.sqrt, math.floor, math.ceil` contributed one symbol instead of three. Nothing failed: `token-goat symbol err` simply reported no such symbol. The pattern now reads the full name list, and each name becomes its own symbol on the declaration's line. Lua 5.4 attributes are handled too, so `local limit <const> = 10` indexes `limit` and does not mistake `const` for a binding. Like every change to what token-goat extracts, this reparses already-indexed files once on upgrade: the parse-freshness entry below explains what that costs. See [src/languages/lua.ts](src/languages/lua.ts).

- **Public Zig constants and variables were dropped from the index entirely.** The Zig extractor recognised a top-level declaration only when the line began with `const` or `var`, with no allowance for the `pub` keyword that marks it public, even though the neighbouring patterns for container types and functions both already accepted it. So `pub const max_len = 4096;` and `pub var counter: u32 = 0;` matched nothing and were never stored, while a `pub const Point = struct {...}` two lines away resolved normally. That hit the most looked-up part of a Zig codebase hardest: a root module is largely public re-exports of the form `pub const io = @import("io.zig");`, and every one of them was invisible to `token-goat symbol`, `read`, `outline` and `skeleton`. There was no error, just a shorter answer than the file deserved. Both patterns now accept the optional `pub` prefix, matching the container and function patterns beside them. Like every change to what token-goat extracts, this reparses already-indexed files once on upgrade: the parse-freshness entry below explains what that costs. See [src/languages/zig.ts](src/languages/zig.ts).

- **A parser change now reindexes files whose content never moved. Upgrading to this release reparses every already-indexed file once.** Parse freshness was keyed on file content alone, so the index could only answer "have these bytes changed since we parsed them". It could not answer the other half: has what token-goat extracts from those bytes changed. When an extractor was fixed or a language adapter gained a case, every already-indexed file kept the symbols an older parser gave it, for as long as nobody happened to edit it, and `token-goat index` reported those files as skipped rather than stale. Measured on a real index against a clean one built by the same binary, 37 of 237 source files disagreed, 180 surplus rows in all: symbols that no longer existed still answered `symbol` and `read` lookups. Each file now also records a fingerprint of the extraction logic that produced its rows, and both freshness checks (the background worker and the `index` command) treat a mismatch as a change. **What this means on upgrade:** the fingerprint in this release differs from anything recorded before it, so the first `token-goat index` run reparses every tracked file instead of skipping the unchanged ones. On a large index that run takes noticeably longer than usual, once; runs after it skip as before. The background worker does the same thing gradually, reparsing each file the first time it is touched. Nothing needs to be deleted or rebuilt by hand, and the `--force` flag is no longer the only way to recover from this. The same will happen on any future release that changes extraction, and the changelog will say so. See [src/parser.ts](src/parser.ts), [src/worker.ts](src/worker.ts) and [src/db.ts](src/db.ts).

- **`token-goat scope` now really does list the innermost symbol first.** It sorts by which symbol starts latest, and when two start on the same line that told it nothing, so it fell back to whatever order the database happened to return: the widest one. Asking about a line where an object and its first method both begin listed the object above the method inside it, the exact reverse of what the command promises. Symbols that start on the same line are now ordered by which ends first, and two that begin and end together are ordered by name so repeated runs agree. See [src/graph_commands.ts](src/graph_commands.ts).

- **Hidden secrets in compressed shell output are now counted.** When token-goat replaces a tool's result with a shorter version, that replacement is the only copy the model reads, so any secret hidden in it is what protected that copy. The compound-command compressor was hiding them and reporting nothing: the only other place that counts them is the on-disk cache, which receives text that was already cleaned and so has nothing left to count. `token-goat stats` now shows those hidden values. Five places built this kind of replacement by hand, each with its own copy of the counting beside it, and three had drifted apart. They now all go through one function, and a test fails if a sixth is added by hand. See [src/hooks_common.ts](src/hooks_common.ts).

- **Compressed shell output no longer counts its saved tokens on a different scale from every other saving.** Turning saved bytes into saved tokens needs an assumed ratio, and this project uses four bytes per token. One path did not: the generic shell-output compressor reached for a helper built for a completely different job, keeping a buffer from overflowing, which divides by three because guessing high is the safe direction when the risk is running out of room. Crediting a saving is the opposite situation, where guessing high claims work that was never done, so that path was booking about a third more than its siblings inside a figure that adds them all together. On one real database it was 469,422 tokens across 520 events. There is now a single named conversion for savings, the overflow helper says on its face that it must not be used for one, and a test fails if any recorded saving reaches for it again. The test that covered this path had been restating the old formula rather than stating the expected one, which is why nothing failed. See [src/stats.ts](src/stats.ts) and [src/hooks_bash.ts](src/hooks_bash.ts).


- **Collapsing the echoed plan after you approve one is now counted, instead of saving bytes in silence.** When a plan is approved, the tool result repeats the whole plan back even though it is already on disk, and token-goat replaces that repeat with a one-line pointer. It has been doing so for several releases without recording anything, so a real mechanism was missing from `token-goat stats` and there was no way to check whether it was clearing the net-benefit floor that admits it. It now records under a `plan_echo_collapse` entry alongside the other rewrites of tool output. The handler also emits through the shared helper the other rewriting handlers use, which settles a question its own comment had left open: counting hidden secrets there used to mean either over-counting ones the collapse had already dropped, or writing a second pass over the emitted text, and the shared helper already does exactly that second pass. Measured on a real approval: 508 bytes in, 155 out, 353 recorded. See [src/hooks_exitplanmode.ts](src/hooks_exitplanmode.ts).


- **The number of secrets token-goat hid is no longer added to the count of tokens it saved.** When a secret is found in text on its way to the model, token-goat replaces it and records how many replacements it made. That number had nowhere else to go, so it was written into the same column the token savings live in, and the headline "Tokens saved" figure quietly added it. The amount is tiny, but a count of hidden secrets is not a quantity of tokens, and the one number this project asks to be taken at face value should not contain anything measured in something else. Half of this was already understood: the same kind is deliberately kept out of the savings breakdown, on the grounds that hiding a secret is not the same as saving a read, and that reasoning simply never reached the addition. Redaction counts now have their own place in the output and contribute nothing to any total, day, source, command or harness figure. `token-goat stats` prints them on their own line, labelled as a count, and only when something was actually hidden. See [src/stats.ts](src/stats.ts).

- **A new field in the stats summary no longer goes missing from `token-goat stats --json`.** The JSON output is assembled field by field on purpose, so that renaming something internally cannot silently rename it for anyone parsing the output, but that also means a newly added field is absent until someone remembers to list it. The redaction count above was added, unit tested, type checked and passed the whole suite while still being missing from the JSON, and only running the built command showed it. The assembly is now one named function with a test that compares it against the summary in both directions, so a missing field and a stale leftover both fail. See [src/cli_stats.ts](src/cli_stats.ts).


- **Saved tokens from image shrinking are now counted the way an image is actually billed, in visual tokens rather than in bytes.** Every image row in `token-goat stats` divided the bytes it removed by four, which is the rule of thumb this codebase uses for text and is simply the wrong unit for pixels: a model is charged for an image as a grid of 28 by 28 pixel patches, so what an image costs follows from its dimensions and not at all from how many bytes its encoding happens to take. The gap was not small. A single browser screenshot booked close to three million saved tokens where the true figure was under two thousand. All four image branches now price both sides of the trade the way the API does, including the part that matters most: the API downsizes an oversized image itself before charging for it, so on a standard-resolution model a 4K screenshot and a 1080p screenshot cost exactly the same, and shrinking the first one saves real bytes on the wire but not one token on the bill. That case now reports zero instead of a large invented number. A new `image_shrink.vision_tier` setting (`standard` or `high`, or the `TOKEN_GOAT_VISION_TIER` environment variable) says which resolution tier the model reading the images is on, since the two tiers bill the same large image up to three times apart. It defaults to `standard`, the lower of the two, so the reported figure can never claim a saving that was not there. The expected costs are pinned in tests against Anthropic's own published table rather than against this code's arithmetic. See [src/image_shrink.ts](src/image_shrink.ts), [src/hooks_browser_image.ts](src/hooks_browser_image.ts) and [src/config.ts](src/config.ts).


- **The saving credited when OCR replaces an image was measured against the wrong thing.** The image-shrink path credits itself with the difference between the shrunk image it did not send and the text it sent instead, but it measured only the recognized text, not the summary line and untrusted-content marker that ship with it. The row is now priced on the payload actually emitted. See [src/image_shrink.ts](src/image_shrink.ts).

- **The OCR language model was being downloaded again on every single call.** Token-goat told `tesseract.js` to cache the model under its own home directory, but nothing ever created that directory, and a failed cache write is silent there: OCR still returned text, so nothing looked wrong. Every `token-goat image-text` call, and every OCR pass inside image shrinking, re-fetched about 2.9 MB. The directory is now created before the engine starts, so the model is downloaded once and reused. See [src/image_ocr.ts](src/image_ocr.ts).

- **Indented keys in a `.env` file are indexed again.** The dotenv extractor skipped every line starting with a space or a tab, so an assignment written with any leading indentation produced no symbol at all and could not be found by `symbol`, `outline` or `section`. dotenv's own parser treats leading blanks as part of a legal assignment, so token-goat now does the same: blanks are stripped, the comment test is applied to what is left, and the multi-line quoted value tracking is unchanged, so a continuation line that looks like its own assignment is still not mistaken for a key. The live section reader was carrying the identical gap and is fixed alongside it, so a key found by the indexer is also reachable by name through `section`. See [src/languages/ini_idx.ts](src/languages/ini_idx.ts) and [src/section_reader.ts](src/section_reader.ts).

- **Salesforce metadata with a space before an end tag bracket no longer swallows the rest of the file.** XML allows whitespace inside a closing tag, as in `</fullName >`, but four of the extractor's patterns required the bracket to follow the tag name immediately. A single such tag meant the element never closed where it should, and the search ran on to the next element's closing tag: an object's name came back as a block of raw XML rather than the object name, and two neighbouring flow elements collapsed into one, losing the second element's symbol and stretching the first one's line span over it. The end tag patterns in the general text reader, the direct-child reader, the block scanner and the flow element scanner now all allow that whitespace, and the direct-child depth walk counts tags whose names use the leading underscore, colon, dot or hyphen that XML permits, instead of skipping them and miscounting the nesting. See [src/languages/salesforce_metadata.ts](src/languages/salesforce_metadata.ts).

- **pi sessions now receive rewritten tool output instead of the raw result.** The pi extension called token-goat's post-tool hook for its side effects and threw the response away, so every rewrite that hook produces (output compression, secret redaction, injection fencing) was computed, cached, counted as a saving, and never reached the model. pi's own published package settles the question the bridge had left open: its extension types say a tool-result handler can modify the result, and its shipped runtime copies a returned `content` onto the tool result. The bridge now returns the rewrite. It replaces only the text blocks and leaves image blocks in place, because pi overwrites the content list wholesale, and it returns nothing else, because pi keeps the fields a handler does not supply. OpenClaw's matching hook was checked the same way and genuinely cannot do this: its own hook documentation classes `after_tool_call` as observe-only and says return values are ignored, so nothing changed there. See [src/bridges/pi.ts](src/bridges/pi.ts) and [docs/hook-channel-matrix.md](docs/hook-channel-matrix.md).

So result measurement, caching, secret redaction, injection fencing and output compression all ran against nothing on Gemini: no error, no wrong statistic, just silence. This is the same gap fixed on Qwen Code, which inherited the shape from Gemini as a fork of it, and the same fix: `output` is added alongside the original keys, never renaming them, and a result that is not a plain string is left untouched rather than coerced. Qwen's `PostToolUse` payload also carries its result as `{llmContent, returnDisplay}`, and neither key was in the lists every post handler reads, so result measurement and compression saw an empty string. The plugin's own response-contract comment listed four of the five producer shapes, and the missing one shipped dead: the same silent-whitelist failure previously found in the Copilot shim's payload builder. The rewritten text now replaces the tool result through the same output mutation the hint append already used. On a real machine those unmentioned skills were the biggest context spenders (a 156 KB skill among them). Worse, a cached skill whose source file was later deleted or renamed crashed the whole command with a raw ENOENT, because the cached path is returned without an existence check. The summary now names a `no marker` and an `unresolvable` bucket whenever they are non-empty, points at `token-goat skill-size` for per-skill marker recommendations, and a vanished source is counted as unresolvable instead of aborting the pass. - **`token-goat session-audit` now scans subagent and workflow transcripts, which carried most of the billing it claimed to cover.** The corpus walk stopped two directory levels down, but modern Claude Code stores each session's subagent transcripts deeper, under `<project>/<session>/subagents/`. On one real corpus that walk missed 6,022 of 11,555 transcripts, holding 65% of all API calls and 57% of all cache-read tokens, while the report still presented itself as corpus-wide. The walk now recurses the whole tree, so the measured ledger covers every transcript. Overlap between the shallow and deep sets is negligible (89 of 302,968 API responses), so recursing does not double-count. See [src/session_audit.ts](src/session_audit.ts).

- **Background task polls are deduplicated again: the poll delta reads the output where Claude Code actually puts it.** A `TaskOutput` result arrives as `{retrieval_status, task: {task_id, status, output, ...}}`, with the accumulated text one level down at `task.output`. The hook looked only at the top level, found nothing, and fell back to serialising the whole envelope as JSON. That broke both of its jobs at once: a longer poll is not a prefix of the previous poll's serialised envelope, so the delta was never taken and the full output was re-sent on every poll, and a JSON string escapes its newlines, so the repeated-line collapse saw one single line and never fired. The hook now reads `task.output` directly and falls back to the shared extractor for any other envelope. Replaying the shapes of 170 recorded polls through the built binary: 0 were shortened before, 2 are now, both of them repeat polls of long-running tasks that had accumulated 20,000 bytes of already-seen output. The field lookup stopped at the first key present as a string, empty or not, so it returned an empty string and every post-Bash path that needs the output did nothing. An empty field is now skipped in favour of a later one, and `stderr` is consulted last of all, after every other name, so a populated `stdout` always still wins. See [src/hooks_common.ts](src/hooks_common.ts).

- **Post-tool-use work that needs a command's output or a fetched page now actually gets it on Claude Code.** Claude Code sends a Bash result as `{stdout, stderr, interrupted, isImage, noOutputExpected}` and a WebFetch result as `{result, url, code, codeText, bytes, durationMs}`. On a small `Cargo.toml` holding five such keys, `token-goat outline` listed 6 symbols and omitted every one of them, and `read "Cargo.toml::serde.workspace"` answered "not found" for a line plainly present in the file; the same file now lists 11. See [src/languages/sfc_idx.ts](src/languages/sfc_idx.ts).

On a `Cargo.toml` whose fourth line was such a comment, `token-goat outline` listed only the first table, `section "Cargo.toml::dependencies"` answered "not found" for a table plainly present, and nothing said why. An unclosed `'''` or `"""` inside a comment did the same through the other tracker. See [src/parser.ts](src/parser.ts) and [src/section_reader.ts](src/section_reader.ts).

Two-part names keep their schema prefix exactly as before. See [src/languages/sql_idx.ts](src/languages/sql_idx.ts).

A backtick-quoted name is how every infix operator is defined (`` `%+%` <- function(a, b) ``, the same form magrittr's own `%>%` uses) and how every S3 method on an operator or extractor generic is defined (`` `[.myclass` <- ``, `` `+.difftime` <- ``). When a concurrent reader blocked the checkpoint, the command printed `1345.3 MB -> 2494.4 MB (freed -1149.0 MB)` for a run that had in fact taken the database from 1310 MB to 1177 MB. A negative saving is worse than no saving reported, because it reads as the command having made things worse. The figures now fall back to the main database file, the only pair comparable across a run whose checkpoint could not finish, and the existing note says where the rest of the space went. A run whose checkpoint succeeded still counts the WAL it reclaimed. A run that genuinely grew the index -- the first run against a path with no database yet, where every byte is growth and there was never anything to reclaim -- now says it grew rather than reporting a saving with a minus sign. See [src/index_reclaim.ts](src/index_reclaim.ts).

- **`token-goat doctor` could print a tool-name warning that contradicted itself and would never clear.** The check that watches for a bridge forgetting to rename an inbound tool warns when a name differs from a handled one by case or separators alone. A real database held a row whose near miss was its own name, so the warning read `claudecode sent "Bash" where "Bash" is handled` -- a sentence with nothing in it to act on, and nothing a working harness could do to make it go away. The skill-body cache in `src/skill_cache.ts` was a second, undocumented gap: `storeOutput` (called on every skill load) and `storeCompact` (called when a compact slice is generated) wrote the raw body straight to a `.txt` file with no redaction step. Both now call the same `redactSecrets` pass everything else uses, with the same fail-safe behavior: if the redaction pass itself throws, nothing is written rather than falling back to the raw body. `storeCompact`'s `source_sha` marker comment is added after redaction runs, so a content hash is never itself a redaction target. See [src/skill_cache.ts](src/skill_cache.ts) and [CLAUDE.arch.md](CLAUDE.arch.md).

- **`recall`, `pr-slice`, and `gdrive-sections` emitted third-party-authored text with no scan and no fence at all.** Every other recall path (`bash-output`, `web-output`, `mcp-output`, WebFetch, WebSearch, an MCP tool result) is scanned for injected instructions and fenced when it matches, but these three commands never called the check. `recall` searches the same three cache stores those three recall commands read, and its no-query browse mode is the sharpest case: with an empty query it returns the first 160 raw characters of every recent entry with no match required at all. `pr-slice` prints a GitHub pull request's title, description, review comments, and diff, all written by whoever opened the PR or left the comment. `gdrive-sections` prints a Google Doc's text, editable by anyone with access to the shared file. All three now scan and fence: `recall`'s snippets under `<untrusted-web-content>` for a web-cache hit or `<untrusted-tool-output>` for a bash/mcp-cache hit, matching the tag each hit's own recall command already uses; `gdrive-sections` under `<untrusted-web-content>`, the same tag WebFetch uses, since a Google Doc is fetched over HTTP the same way a page is; and `pr-slice` under a new `<untrusted-github-content>` tag, since PR content is neither a page token-goat fetched itself nor a cached copy of a prior tool call. `recall --json` and `pr-slice --json` fence only the specific string field that carries the risky text (`snippet`, `diff`, a comment's `body`, a description's `title`/`body`), so a script parsing either command's JSON output still sees the same field at the same key, never a corrupted envelope. A structural guard test now checks every function in the source tree, not a maintained list of command names, so a future command that reads through one of these same content sources and never reaches the fence fails on its own. See [src/cli_recall.ts](src/cli_recall.ts), [src/cli.ts](src/cli.ts), [src/read_commands.ts](src/read_commands.ts), [src/injection_scan.ts](src/injection_scan.ts), and [CLAUDE.arch.md](CLAUDE.arch.md).

- **WebSearch results reached the model with no scan for injected instructions and no fence around them.** Every other source of third-party text token-goat handles goes through this check first: a WebFetch page, an MCP tool result, cached output recalled later. WebSearch results were the one live surface that skipped it entirely, because the handler only cached the result and passed it through untouched. The post-search hook now scans every result the same way [`postFetchHandler`](src/hooks_fetch.ts) does for WebFetch, and wraps a result that matches in the same `<untrusted-web-content>` fence used for fetched pages, before any of the handler's own caching guards can return early with the result already attached — including the guard for an in-band error response, which is exactly the ordering mistake a past MCP fix already closed for `mcp__*` tools. See [src/hooks_websearch.ts](src/hooks_websearch.ts).

- **`pdf-extract`, `pdf-locate`, `pdf-outline`, `docx-text`, `docx-outline`, `pptx-outline`, `pptx-slide`, `pptx-notes`, `pptx-text`, `xlsx-sheets`, `xlsx-head`, `xlsx-range`, and `xlsx-query` printed extracted document text with no scan and no fence at all.** A path named on the command line is not the same thing as content authored by whoever ran the command: an emailed invoice, a downloaded report, a contract someone else drafted are all third-party text that happens to live in a local file, no different from a fetched web page or an MCP result. Every command in this family now scans its extracted text and wraps a match under a new `<untrusted-file-content>` fence: `pdf-extract` and `docx-text` route through the same `_applyFiltersAndPrint(..., true, ...)` plumbing `bash-output`/`web-output`/`mcp-output` already use, and the outline/list-shaped commands (bookmark titles, headings, slide titles, sheet names) fence each individual text field so a `--json` caller still gets a valid, parseable payload with only the risky field wrapped, not a corrupted envelope. See [src/cli.ts](src/cli.ts), [src/injection_scan.ts](src/injection_scan.ts), and [CLAUDE.arch.md](CLAUDE.arch.md).

- **A WebFetch or WebSearch result could carry a credential that reached the model unredacted.** Every other cache token-goat writes to disk (bash-output, web-output, mcp-output) redacts a secret before it's persisted, and the MCP live-rewrite path already redacts inside its compression branch — but neither `postWebSearchHandler` nor `postFetchHandler` had any redaction on the copy they hand back to the model this turn, only the injection-fence check, which a bare credential with no attack phrasing never trips. Both now redact secrets on the same live path the fence protects, computed once ahead of every early-return guard so no caching shortcut can skip it, matching the ordering discipline already enforced for the injection scan itself. See [src/hooks_websearch.ts](src/hooks_websearch.ts) and [src/hooks_fetch.ts](src/hooks_fetch.ts).

- **An MCP result could still carry a credential unredacted, on every return path except the two the earlier WebFetch/WebSearch fix didn't touch.** `postMcpHandler`'s compression branch already redacted, and its fenced-injection branch redacted too, but the small `passOrFence` helper both of them sit next to only redacted when an injection match had already fired — leaving no session id, an in-band MCP error response, a dedup cache hit, and the terminal "compression did not fire or did not pay off" return all shipping an MCP result's bare credential straight through, the same gap the WebFetch/WebSearch fix above closed on the other two live paths. Secrets are now redacted once, up front, alongside the injection scan and ahead of every one of those early returns, and `passOrFence` is now three-way: fence when there's an injection match, rewrite with the redacted text when there isn't but a secret was found, otherwise pass through unchanged. See [src/hooks_mcp.ts](src/hooks_mcp.ts).

- **`image-meta` decoded a file with no pixel cap at all, the one call site in `image_shrink.ts` that didn't thread the configured decompression-bomb bound.** Every other decode call in the file passes `cfg.max_image_pixels` (0 meaning "no cap") into sharp's own `limitInputPixels` guard; `probeImageMeta`, which backs `token-goat image-meta`, hardcoded `limitInputPixels: false` instead, so a decompression-bomb image had nothing bounding its decode. It now loads and threads the same config value as its siblings. A cap rejection surfaces as the same `ImageDecodeError` an ordinary corrupt/undecodable image already throws, rather than the "sharp unavailable" `null` — the two failure modes ("sharp isn't installed" vs. "sharp is installed and declined to decode this") need to stay distinguishable to the caller, and folding a cap rejection into the null case would have told a user to install a dependency they already have. See [src/image_shrink.ts](src/image_shrink.ts).

- **An Azure storage account key survived `redactSecrets` untouched.** A connection string like `DefaultEndpointsProtocol=https;AccountName=goat;AccountKey=<88-char base64>==;EndpointSuffix=core.windows.net` grants full read/write access to the account, but nothing in the generic `password|passwd|secret|api[_-]?key|access[_-]?token|refresh[_-]?token|id[_-]?token` keyword pattern matches "AccountKey", so the key passed through every cache and every live rewrite in plaintext. A new pattern anchors on the literal `AccountKey=` field name — an unanchored base64-shape pattern was deliberately rejected, since this module's own header already warns that a bare high-entropy-blob heuristic mangles ordinary hashes, digests, and ids. The value class is base64 proper (letters, digits, `+`, `/`, trailing `=` padding), none of which include `;`, so the match terminates on its own at the `;` that starts the next field, leaving `EndpointSuffix=core.windows.net` fully readable — no lookahead trick needed the way the generic pattern's own separator characters require, because `;` is never valid base64. See [src/secret_redact.ts](src/secret_redact.ts).

- **The Azure key pattern matched only the tightest possible spelling of the field.** Anchoring on a literal `AccountKey=` caught the canonical connection string and nothing else: `{"AccountKey": "..."}` (the shape a logged api response or MCP result actually arrives in), a hand-aligned `AccountKey = ...` in an appsettings file, the lowercase and YAML-colon forms, and Service Bus / Event Hubs / Relay connection strings, which spell the identical credential `SharedAccessKey` and hand over the same authority over a namespace. Each of those printed the key in full. The pattern now accepts both field names and writes its separator the way [`auth_bearer_token`](src/secret_redact.ts) already writes its own -- optional quotes on either side, and a bounded gap rather than exactly one space -- which are the two variants that module records having already been caught out by once. `SharedAccessKeyName`, a plain identifier that sits immediately before the secret in every Service Bus string, still reads through untouched. See [src/secret_redact.ts](src/secret_redact.ts).

- **`image-text` printed OCR text lifted out of an image with no scan and no fence.** The thirteen document-extraction commands were fenced on the argument that naming a local path is not the same as authoring its content. OCR is the same argument one step further: the attacker controls the pixels, so text placed in a screenshot, a scanned document or a photographed sign is read verbatim into the model context, and an image carries no format-level hint that its text came from somewhere else. Both emit paths now scan and wrap a match in the same `<untrusted-file-content>` fence the document commands use. The `--json` path fences only the `text` field, so the envelope stays parseable, and it matters more there than in the plain-text renderer: `--json` returns the OCR text even when confidence is below the usefulness threshold, which is exactly the case the plain renderer withholds as noise. See [src/cli.ts](src/cli.ts).

### Documentation

- **The README's image section never said what actually drives vision-model token cost.** It claimed a flat 60-90% cut in vision tokens without explaining why, so a reader couldn't tell why a small, heavily compressed screenshot still costs the model plenty. Vision models bill by pixel dimensions, not file size, and the README now says so, with the per-vendor patch and tile formulas that back it up. It also explains why token-goat shrinks an image on either of two independent checks (file size at or above 512 KB, or longest edge past 1568 pixels): the byte check is a cheap pre-filter, and the dimension check catches the case the byte check alone misses, a small file that still decodes to a huge image. See [README.md](README.md).

- **The old 60-90% savings claim was measured against a bill the model never sends.** Claude downscales an oversized image on its own before billing and caps the cost, so the saving from shrinking an image first is the difference against that cap, not against the full original. The README now gives the real figures from Anthropic's [published per-tier table](https://platform.claude.com/docs/en/build-with-claude/vision#evaluate-image-size): a 3840x2160 screenshot bills at 4784 visual tokens on Claude 4.7 and later and 1560 on earlier models, against 1792 tokens once resized to a 1568px long edge. That is a 63% cut on the newer models and no cut at all on the older ones. The README also now names the two cases where shrinking is not about cost: screenshots handed back to the computer-use and browser-use toolsets are rejected rather than downscaled when they are too large, and a request carrying more than 20 images has a tighter per-image dimension limit applied to all of them.

### Fixed

- **A Dart `'''` string containing a lone quote dropped every later method in the class from the index.** The brace walk that decides where a symbol ends was fixed for this case already, but the Dart extractor runs its own separate line-by-line brace count first, on a copy of the line with string contents blanked out. That blanking step only knew one-character quotes. Given `var s = '''a ' } b''';` it opened and closed a string on each quote in turn, so it was outside any string over the middle of the literal and counted the `}` there as a real closing brace. That drove its depth one level too shallow, and every method after that line was never recorded at all: `token-goat symbol n` found nothing, with nothing to signal the method existed. The blanking step now takes a per-language option, and Dart turns it on for both `'''` and `"""`. Every other language that uses it passes no option and behaves exactly as before. See [src/languages/common.ts](src/languages/common.ts) and [src/languages/dart.ts](src/languages/dart.ts).

- **A Dart `'''` string containing a lone quote ended the enclosing method on the next brace.** Dart writes a triple-quoted string with either `"""` or `'''`, but the brace walk only knew the double-quoted spelling. Given `'''a ' } b'''` it paired the quotes off differently, so the `}` between them was read as real code and closed the method: a five-line method came back as two, and its class as one. Both spellings are now recognized for Dart. Kotlin, Scala and Swift, which have only the double-quoted spelling, are unchanged. See [src/languages/common.ts](src/languages/common.ts) and [src/parser.ts](src/parser.ts).

- **A C# raw string literal collapsed the method and class around it to their signature lines.** C# 11 raw strings open on a run of three or more `"` and close on the next run at least as long, and take no escape sequences, so `"""C:\Users\"""` is a perfectly ordinary path. The brace walk read those as three separate quotes, and the trailing backslash then looked like it escaped the closing one, leaving the walk inside a string for the rest of the file. A ten-line class came back as one line. The walk now measures the opening run and jumps past the first run at least as long, so a four-quote literal closes on four rather than on a `"""` in its own text. Kotlin, Scala, Swift and Dart keep their fixed three-quote handling, which is what those languages specify. See [src/languages/common.ts](src/languages/common.ts) and [src/parser.ts](src/parser.ts).

- **A backtick-escaped quote in a PowerShell string ended the enclosing function early.** The brace walk was told that a backslash escapes nothing in PowerShell, which is correct, but nothing was put in its place: PowerShell's real escape character is a backtick. So `"a`` " } still text"` was read as a string that closed at the escaped quote, and the brace after it was counted as the function's closing brace. The backtick is now honored, inside double-quoted strings only, since in a single-quoted PowerShell string it is an ordinary character. A trailing backslash in a path literal such as `"C:\temp\"` still ends the string where it looks like it does, and languages that really do use backslash escapes are unchanged. See [src/languages/common.ts](src/languages/common.ts) and [src/parser.ts](src/parser.ts).

- **A `#` comment in PHP ended the enclosing function at whatever brace it contained.** PHP accepts both `//` and `#` for a line comment, but the brace walk was told about `//` only, so `# }` was read as real code and the function's span stopped on that brace: a five-line function came back as two. Both spellings are now recognized. `#[Attr]` is exempt, because in PHP 8 that is an attribute rather than a comment, and reading it as one loses an opening brace that shares the line, as in `function f(#[SensitiveParameter] string $p) {`. PowerShell, whose `#` comments have no such exception, is unchanged. See [src/languages/common.ts](src/languages/common.ts) and [src/parser.ts](src/parser.ts).

- **A Zig multi-line string containing a closing brace ended the enclosing function early.** Zig writes a multi-line string as a `\\` at the start of each line: the rest of the line is literal text, with no closing delimiter and no escape sequences. The brace walk read those lines as ordinary code, so a `}` anywhere in the text was counted as a real closing brace and the function's span stopped at it. A seven-line function holding a two-line string came back as three lines. Those lines are now skipped as text, up to the newline and no further, so the code after the string is still scanned normally. See [src/languages/common.ts](src/languages/common.ts) and [src/parser.ts](src/parser.ts).

- **An ordinary division in Zig collapsed the surrounding function to its signature line.** The shared brace walk guessed each language's block-comment delimiters from its line-comment prefix: anything spelling line comments `//` was assumed to spell block comments `/* */`. Zig spells line comments `//` and has no block comment at all, so `return a/*b;` — divide `a` by `b`, dereferencing a pointer — looked like the start of a comment that never closed. The walk gave up, and `token-goat read "div.zig::f"` returned the signature instead of the body. Each language now states its block-comment delimiters instead of having them inferred, and Zig states that it has none. Languages that really do have `/* */`, such as PHP and C#, are unchanged. See [src/languages/common.ts](src/languages/common.ts) and [src/parser.ts](src/parser.ts).

- **A triple-quoted string in Kotlin, Scala, Swift or Dart cut every symbol around it back to its signature line.** All four languages have a `"""..."""` literal that runs to the next `"""`, and in Kotlin and Scala it takes no escape sequences at all. The shared brace walk that gives these symbols their real body read those three quotes as three ordinary string delimiters, so two very common literals derailed it: a lone `"` in the text, as in `"""5" wide"""`, flipped its idea of which characters were code, and a trailing backslash, as in `"""C:\Users\"""`, was read as escaping the closing quote and left the walk inside a string for the rest of the file. Either way the walk never found the closing brace, and the enclosing function and class fell back to their one-line signature: `token-goat read "Paths.kt::root"` returned `fun root(): String` and nothing else, so the caller had to read the whole file. The walk now jumps straight from `"""` to its closer for these four languages. Languages where three adjacent quotes mean something else, such as PowerShell doubling a quote to escape it, are untouched. See [src/languages/common.ts](src/languages/common.ts) and [src/parser.ts](src/parser.ts).

- **A nested block comment in Swift, Kotlin, Scala or Dart cut the enclosing symbol's body short.** All four languages specify block comments that nest, so `/* outer /* inner */ still outer */` is one comment from the first opener to the last closer. The shared brace walk ended it at the first `*/` it found, so everything after the inner closer was read as live code -- and a `}` sitting in that still-commented text decremented the real brace depth and closed the symbol early. A Swift `func` whose body opened with such a comment reported a span of lines 1-2 instead of 1-4, so `token-goat read "a.swift::first"` returned the signature and the comment while silently dropping the `return`, which is the worst shape for this failure: the output looks like a complete answer. The walk now counts opener depth for these four languages, and both halves of it -- the search for the opening brace and the search for its match -- share one skip routine so they cannot disagree about where a comment ends. C#, PHP, Zig and PowerShell do not nest block comments and keep the previous first-closer behavior exactly. See [src/languages/common.ts](src/languages/common.ts) and [src/parser.ts](src/parser.ts).

- **A Windows path in a C# or PowerShell file collapsed every symbol around it to a one-line span.** A string ending in a backslash is completely ordinary in both languages -- `@"C:\temp\"` in C#, `"C:\temp\"` in PowerShell -- but the shared brace walk that gives these symbols their real body treated a backslash as escaping the next character everywhere, so that final backslash "escaped" the closing quote. The string was then read as still open, every brace after it was swallowed, and the walk reached end of file without ever closing the block. The enclosing method, class and namespace all fell back to their one-line signature, so `token-goat read "Paths.cs::First"` returned `public string First()` and nothing else, and the caller had no option left but to read the whole file. The walk now takes the escape model from the language: PowerShell escapes with a backtick, so a backslash is just a character there; C# keeps backslash escapes for ordinary literals but recognizes a verbatim string (`@"..."`, `$@"..."`, `@$"..."`), inside which a backslash is literal and a doubled `""` is the escaped quote. Every other adapter keeps the previous behavior unchanged. See [src/languages/common.ts](src/languages/common.ts) and [src/parser.ts](src/parser.ts).

- **The two poll handlers replaced a large tool result with a tiny one and recorded the saving as zero.** `BashOutput` and `TaskOutput` are among the loudest tools in a long agent run: each poll re-sends everything the process has printed so far, so token-goat replaces the result with just the new suffix, a de-duplicated body, or a short "unchanged since last poll" notice. Those are real token savings, and none of the five branches recorded a single byte, so `token-goat stats` reported nothing for the two paths that fire most often. All five now record. The saving is computed inside the shared emit helper from the string actually returned, never from a number the caller worked out separately, so a recorded figure cannot disagree with what the model received; only a positive delta is stored, since one negative entry would corrupt every total that sums it. The baseline is the raw tool result rather than the redacted copy the handler diffs against, because a pass hands the model the harness's own untouched output; billing against the redacted copy over-reports, since a placeholder is often longer than the secret it replaces and the handler would be credited for bytes the redaction added. See [src/hooks_common.ts](src/hooks_common.ts), [src/hooks_bashoutput.ts](src/hooks_bashoutput.ts), and [src/hooks_taskoutput.ts](src/hooks_taskoutput.ts).

- **New guard: a stat kind that nobody registered is now a test failure instead of a silent misfiling.** `kindToSource` maps each stat kind to the source it is reported under, and its fallback for an unrecognized kind is to return `other` -- no error, no warning, the numbers just land in the wrong bucket and the by-source breakdown quietly understates whichever subsystem earned them. This has gone wrong repeatedly, always the same way: someone adds a kind and forgets the table. A guard now walks `src/` for every stat kind visible at a call site and fails naming the file and line if one does not resolve. It found three on its first run -- the fail-soft diagnostic counters in the edit hook -- which genuinely belong under `other` and are now listed there deliberately rather than arriving by fallback. The scan reads each file as a whole rather than line by line, so a call split across several lines is still seen, and it accepts either quote style; the three call shapes that a simpler scan misses are pinned individually, so losing one again fails by name instead of hiding behind the fifty ordinary single-line sites. See [src/stats.ts](src/stats.ts) and [tests/guards/every_recorded_stat_kind_is_registered.test.ts](tests/guards/every_recorded_stat_kind_is_registered.test.ts).

- **The `hint-stats` TOTAL line subtracted two figures that were never measuring the same thing.** It printed `saved`, `spent` and a `net` that was `saved` minus `spent`. `saved` is an all-time total across every kind of hint token-goat has ever recorded — tens of thousands of events. `spent` only sums the much smaller ledger that tracks individual hint emissions, which for most installs holds a few dozen rows. Because the two figures come from different, unrelated counts, the subtraction between them was not a real net benefit; on one real store it read "net=4861733142" from a ledger of only 71 rows, which looks like hints saved gigabytes when nothing of the sort was measured. The `net` figure is gone. `saved` and `spent` now print side by side, each labeled with what it actually counts, so the line states what was measured instead of implying a benefit nothing measured. See [src/hint_stats.ts](src/hint_stats.ts) and [src/cli_hint_stats.ts](src/cli_hint_stats.ts).

- **Two of the savings figures were counting something nobody would ever actually do.** `sqlite-query` credited itself with saving the entire on-disk size of the SQLite database file it queried, as if the alternative were pasting a whole binary database into the model — that never happens and no tool even offers it; on one real install this one line item alone accounted for 40% of all reported savings. `map` had the same problem: it credited the full on-disk content size of every file it surfaced, as if the alternative were reading each of those files in full, which nobody does either. `sqlite-query` now measures against the same query's own untruncated output, so a saving is only recorded when `--head` genuinely cuts rows out of what was returned. `map` now measures against a plain listing of the same file paths, the more realistic alternative to running `map` at all. Neither command's savings can be inflated by the size of files or databases nobody actually reads whole. See [src/read_commands.ts](src/read_commands.ts) and [src/baseline.ts](src/baseline.ts).

- **A file blocked on its third read within one session was credited for the same saving twice.** When a source file was read enough times in a row to trigger the hard block, the block's size was recorded once under its own tally and then a second time under the general hint tally — and both of those tallies roll up into the same total that `hint-stats` reports, so one blocked read counted as two. On one real install this doubled 6.3MB of genuine savings into 6.3MB of phantom savings on top. The general hint tally now records this event at zero bytes, since the file's own tally already carries the real number; the event itself still shows up, just without booking its bytes twice. See [src/hooks_read.ts](src/hooks_read.ts).

- **Blocking a repeat skill load in the same session recorded zero bytes saved, even though the skill's body genuinely never reached the model.** A skill loaded a second time in one session is denied with a pointer to the cached, cheaper recall command instead — the same shape as a blocked repeat file read, which does credit its real size. This one didn't: it always recorded the saving as zero, silently understating real savings. It now credits the cached skill body's actual byte size, capped the same way a blocked re-read already is, so it doesn't claim more than a real re-load of that size would ever have cost. See [src/hooks_skill.ts](src/hooks_skill.ts) and [src/skill_cache.ts](src/skill_cache.ts).

- **A command that started with `cd DIR &&` (or `cd DIR ;`) never got its output compressed at all.** Bash output compression picks a filter by looking at the first word of the command — `ls`, `npm`, `pytest`, and so on. A leading `cd DIR &&`/`cd DIR ;` pushed the real command one or more words to the right, so nothing recognized it and the command streamed raw. Measured on an identical 400-file directory, `cd DIR && ls -la` produced 32.7x more output than plain `ls -la` — the `ls` filter simply never fired. A leading `cd DIR &&`/`cd DIR ;` is now peeled off before filter selection, and the working directory used for that selection (which matters for resolving `npm test`-style scripts to the right `package.json`) shifts to match. What actually runs in the shell is unchanged; this only affects which filter is chosen. A `cd` inside a subshell, like `(cd DIR && cmd)`, is a different shape and still isn't recognized — pipes were never affected by this bug and still work as before. See [src/tool_filters/dispatch.ts](src/tool_filters/dispatch.ts).

- **`mcp-audit` printed a confident "Total cost: 0 tok" even when it had no idea what MCP servers were active.** The command only ever read one file, `.mcp.json` in the project root, and when that file didn't exist it reported zero cost — indistinguishable from "checked, and there truly is none." On a real project with four live MCP servers and no `.mcp.json`, the report read as a clean bill of health when the honest answer was "unmeasured." The command now also reads this project's entry out of Claude Code's own `~/.claude.json` (checking both the backslash and forward-slash forms of the path, and both drive-letter cases, since Claude Code can key a project under any of them depending on how it was launched), and when neither source is readable it says so plainly — "Total cost: unknown" instead of a bare zero — rather than reporting an absence of data as a measurement. Every report also now notes that plugin-provided MCP servers have no on-disk config at all, so a live session can still have MCP servers this audit cannot see or price. See [src/cli_mcp_audit.ts](src/cli_mcp_audit.ts).
