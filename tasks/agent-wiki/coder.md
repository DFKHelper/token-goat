# Coder agent notes — token-goat

## Any edit to src/parser.ts (or src/languages/*) bumps PARSER_FINGERPRINT even for non-extraction changes, and the CHANGELOG needs a matching "upgrading reindexes" line (2026-09-08)
`scripts/parser-fingerprint.mjs::extractionSources` hashes the full text of `src/parser.ts` plus every file under `src/languages/`, not just the extraction logic inside them. Adding two pure diagnostic accessors (`treeSitterCoreAvailable`/`treeSitterCoreLoadError`/`setTreeSitterCoreForTesting`) to `src/parser.ts` for a `doctor` check made `tests/parser_fingerprint_gate.test.ts` fail even though no parsed output changed, because the gate hashes the whole file, not a semantic diff. Fix: run `npm run parser:fingerprint` to regenerate `src/parser_fingerprint.ts`, and add a CHANGELOG line ending "Upgrading reindexes: the parser fingerprint changed, so every file is reparsed once on the next worker drain." (exact phrasing already used at CHANGELOG.md, see the `[2.9.6]` entries) -- the gate's own failure message names this remedy verbatim. Anything needing a test-only override for an optional native dependency that `parser.ts` also loads (mirroring `ts_refs.ts`'s `setTsModuleForTesting` pattern) unavoidably touches this file and pays the fingerprint bump; there is no way around it short of moving the loader out of `parser.ts` entirely, which is a bigger change than the diagnostic itself.

## storeBashOutput always redacts on write; a fold comparing LIVE output against a stored body must guard the live side too (2026-09-08)
`bash_output_cache.ts::storeBashOutputSync` unconditionally runs `redactSecrets` before writing `entry.output`. Any function that later diffs/matches a fresh command's raw `output` against a previously-stored body (e.g. a served-lines elision) will see a REDACTED prior body next to a LIVE current one. A row containing a secret in the live output will never match the corresponding (redacted) row in the prior body, so it survives as an "unmatched" row and gets copied verbatim into a composed rewrite — a real leak the `rewritten_output_never_carries_a_secret.test.ts` guard catches. Fix: check `redactSecrets(output).count > 0` on the CURRENT output before ever composing a rewrite from it (mirrors the existing `foldShellReadBodies`/`foldShellReadStructure` pattern in `hooks_bash.ts`), and decline entirely rather than partially. Evidence: `maybeElideServedGenericOutput` in `src/hooks_bash.ts`, reproduced with a two-different-commands fixture (same-command fixtures can hide this because of the next entry).

## An identical rerun of the same command is a finding, not redundancy — don't let a new fold silently re-collapse it (2026-09-08)
`bash_identical_read_collapse.test.ts` pins that `maybeCollapseIdenticalRead` must NOT collapse two identical runs of a non-file-read command (e.g. `npm test` printing the same thing twice means the suite is still green; replacing that with a pointer deletes the answer). Any NEW cross-command elision mechanism keyed on a session-wide store (not per-file) will independently rediscover this exact pair and re-introduce the same collapse through a different door unless it explicitly excludes priors recorded under the SAME command (`getBashOutput(id)?.command !== cmd` filter before matching). This is easy to miss because the existing test's own repro happens to be a same-command rerun, so mutating away an unrelated guard (e.g. the redaction check above) can look "safe" against that one fixture purely because this filter already empties `priorIds` first — write a genuinely cross-command fixture to test each guard in isolation.

## `python3 -c "...open(path,'w')..."` on Windows silently converts the whole file to CRLF (2026-09-08)
Used a `python3 -c` one-liner to patch a single line in `src/hooks_bash.ts` via `open(path, 'r').read()` / `open(path, 'w').write(...)` (text mode, no explicit `newline=''`). Python's text-mode write on Windows translates every `\n` to `\r\n`, so a file that was pure LF came out entirely CRLF (3,358 conversions), caught only by `git diff`'s "CRLF will be replaced by LF" warning — `git diff --stat` alone still showed a small, plausible line count and did not flag it. Fix: re-read as bytes and `.replace(b'\r\n', b'\n')`, or just use the Edit tool for single-line changes instead of a Python rewrite (the earlier README rule against Python writes to `src/` is a stricter version of this same trap). Check `git diff` output for the CRLF warning after ANY out-of-band (non-Edit-tool) file rewrite on Windows.

## Retyping a `\u0000`-style escape from a token-goat-rendered source view can land a raw NUL byte instead of the escape text (2026-09-08)
Moving `GENERIC_SERVED_OUTPUT_KEY = '\u0000<bash-generic-served>'` from `hooks_bash.ts` to `session.ts`, an `Edit` `new_string` composed after viewing the constant via a `token-goat read` command landed a literal 0x00 byte in the new file instead of the six-character escape sequence `\`, `u`, `0`, `0`, `0`, `0` -- `grep`/`cat -n` then reported the file as binary. The tool's rendering of the real NUL character in the surrounding terminal output is visually indistinguishable from a space, so copying that visual slice into a new edit reproduces the raw byte, not the source text. Fixed with a small Node script that finds the raw `0x00` and replaces it with the literal ASCII string `\u0000` via `Buffer.from('\\u0000')` (double backslash in JS source to emit one literal backslash). Verify with a byte-level dump (`[...buf.slice(a,b)].map(b=>b.toString(16))`) after touching any line containing a control-character escape, rather than trusting `grep`/`cat -n`, both of which print a real NUL as blank/whitespace.

## A doubled-delimiter escape (`""` in F#/.NET verbatim strings, likely similar shapes elsewhere) is NOT independently mutation-discriminating against a naive "close on first delimiter" masker (2026-09-12)
Writing `fsharp.ts::endOfFSharpVerbatimString` (the `@"...""..."` `""`-escapes-a-literal-`"` rule), the obvious fixture -- one embedded `""` pair inside an otherwise-normal string, followed by a trailing real closer with nothing else between -- passed unchanged under a mutation that deleted the doubled-quote check entirely. Root cause: the two quote characters of a `""` pair are strictly adjacent, so a masker that (wrongly) closes the string at the first of the pair has its very next character be the second of the pair; the outer per-character masking loop then reopens a NEW string scan right there, which runs forward to the same real closer the correct implementation would have found directly. The two wrong sub-spans compose back to the exact same net masked range whenever there is nothing else (no stray quote, no odd count) between the pair and the real closer -- this is structural, not a fixture-quality accident, and will recur for any language whose "escape a delimiter by doubling it" rule you fixture the same way (SQL `''`, CSV `""`, Pascal string literals, etc.). Detected via this repo's own "mutate once, expect red" discipline -- the mutation went green, which is the signal to distrust the fixture, exactly as `ocaml_idx.test.ts`'s own precedent describes for its char-literal-with-equals tests. Fix used here: keep the doubled-delimiter fixture as an explicitly-labeled correctness/regression pin (not a mutation-discriminating test), and add a SEPARATE fixture for the actual discriminating case -- an escape character (backslash, in F#'s case) sitting directly adjacent to the real closer, which a naive "backslash escapes the next char" masker consumes together with that closer and then runs off looking for a wrong one (`@"C:\"` followed by a next-line definition it should not swallow). Check for this shape before trusting any "doubled/repeated delimiter" test as its own proof: does the wrong-close-then-reopen algebra actually change the net masked range for this exact fixture, or only cancel out?

## For a per-line single-match extractor (`ini_idx.ts`-style: one `BINDING_RE.exec()` per line), a mutation-discriminating fixture for masking bugs must put the fake definition on its OWN physical line (2026-09-12)
Writing `nix.ts::extractNix`'s mode-stack masker, a brace-depth-tracking test for `${ { a = 1; } }`-style nested interpolation (a `}` closing a nested record literal must decrement depth, not pop the whole interpolation frame) initially used a SINGLE-LINE fixture: `'quoted = "value: ${ { a = 1; } "fakeCloseTrap = 1;" }";'`. Mutating the `}` handler to always pop regardless of depth stayed GREEN -- not because the masking was actually still correct, but because `classifyLine`'s single `BINDING_RE.exec()` per line only ever extracts the FIRST match on a raw line, so `fakeCloseTrap` becoming live top-level code (due to the mutation) shared a line with `quoted` and was structurally invisible to the extractor regardless of the mutation's effect on masking. This generalizes the doubled-delimiter entry above: even a genuinely-different-net-masked-range mutation can fail to flip a test if the extractor's own per-line/per-match granularity discards the evidence before it reaches an assertion. Diagnosed by a temporary debug test (`console.log(extractNix(...))`, created and deleted) comparing correct vs. mutated output directly rather than trusting the assertion. Fix: rewrote the fixture across MULTIPLE PHYSICAL LINES (exploiting that a nested string can legally span raw newlines), putting `fakeCloseTrap = 1;` on its own line so a masking bug surfaces it as an independently-extractable symbol. Before trusting any mutation test against a line-oriented extractor, check not just whether the masked span differs under mutation, but whether that difference lands on a line/match slot the extractor actually samples.

## A guard's `expect(code).toContain('installX(...)')` is silently satisfied by the `uninstallX(...)` call site (2026-09-12)
`tests/guards/harness_scope_defaults.test.ts` asserted `expect(code).toContain('installVscode(vscodeScopeFromFlags(opts))')` to pin the inverted scope default at its call site. Mutating that exact call in `src/cli.ts` to the old shape left the assertion GREEN, because `uninstallVscode(vscodeScopeFromFlags(opts))` on another line contains the searched string as a substring -- every `install<Harness>` name is a proper substring of its own `uninstall<Harness>` sibling, so the pair always covers for each other. Only the separate classification assertion in the same file caught the mutation, which is exactly the "a tested exemption hid the untested one" shape. Fix: anchor with a lookbehind, `/(?<!\w)installVscode\(vscodeScopeFromFlags\(opts\)\)/`, rather than a plain substring. Applies to any guard in this repo matching an install/uninstall symbol by literal text, and generalizes to any name pair where one is a suffix of the other (`Config`/`ReadConfig`, `write`/`atomicWrite`): a substring assertion over whole-file source is not a call-site assertion.

## `install --vscode --project` points every installer write at repository-controlled content; the containment check belongs at the bridge entry point, not in `util.ts` (2026-09-12)
Fixing the symlink-follow in `backupFile` (`copyFileSync` follows the SOURCE link, so a repo committing `.github/copilot-instructions.md` as a symlink to `~/.ssh/id_ed25519` gets the key copied into `<repo>/<name>.bak.<ISO>`), the obvious place for the guard -- inside `util.ts::backupFile` -- is not available: `util.ts` cannot import `project.ts::isInsideRoot`, because `project.ts` already imports `util.ts` and the cycle breaks the bundle. The guard therefore lives in a new `src/bridges/project_scope_guard.ts` and is called first in BOTH `installVscode` and `uninstallVscode`, over the full target list (`mcp.json`, the instructions file, and all three files `copilotHooksFilePaths` returns). Two design points that are not obvious and were verified empirically rather than reasoned: (a) a leaf `lstatSync` is NOT sufficient -- a repository can commit `.github` itself as a directory symlink and leave an ordinary file at the leaf, and a junction-based fixture confirmed the outside file was really overwritten under that shape, so the check must be realpath CONTAINMENT (`isInsideRoot`); (b) the refusal must be scoped to project targets only, because a symlinked `~/.copilot/...` dotfile is a common legitimate setup and refusing it breaks real users. Separately: `atomicWriteText` renames a regular file OVER a destination symlink rather than writing through it, so a user-scope symlinked target silently gets replaced by a real file. That is pre-existing, non-disclosing, and was flagged rather than fixed -- a test pins the current behaviour so a future change to it is deliberate.

## A backup written next to the file it protects is only a guarantee if nothing later in the same run sweeps it (2026-09-12)
`installVscode`'s user-to-project migration was implemented as "call `uninstallVscode()` first", and `uninstallVscode` ends by calling `removeCreatedBackups`. So the migration wrote a recovery copy of the user's `mcp.json`/instructions and deleted it seconds later, in the same process -- the one path that rewrites a user file without being asked to was the one place the "every overwritten file has a recovery copy" guarantee failed. Fixed with an explicit `{ keepBackups: true }` option threaded through `uninstallVscode` -> `stripDelimitedBlock` -> `releaseCopilotHooksFile`, deliberately NOT by reordering the call site: ordering is invisible in review and the next refactor restores the bug. The test that proves it must assert the user's OWN pre-migration content is recoverable, not that some `.bak.` file exists -- a backup holding the post-rewrite bytes satisfies the weak check and recovers nothing.

## The dedupe/stand-down check must fail OPEN for the hook and CLOSED for suppression, and the ledger is the only half a clone cannot forge (2026-09-12)
`vscode_duplicate.ts::userScopeCopyIsRedundant` stood down on a bare `existsSync` of `<cwd>/.github/hooks/token-goat.json`, so a repository committing `{}` at that path silently disabled every VS Code hook in that clone -- and a suppression bug is indistinguishable from working, because it produces no error and no output. Two checks now have to agree: the `token-goat.owners` sidecar naming `vscode`, and `hasCreatedConfig` against the created-configs ledger in `dataDir()`. Making the ledger check meaningful required a change elsewhere: nothing recorded the hooks config path before, so `installCopilotHooksFile` now calls `recordCreatedConfig` on every install (not only on creation) and `releaseCopilotHooksFile` calls `takeCreatedConfig`, otherwise a repo-planted file inherits a stale entry after an uninstall. `hasCreatedConfig` is a separate function from `takeCreatedConfig` on purpose: a hook asks repeatedly and must get the same answer. The sidecar is forgeable (it is a plain file in the clone) so this raises cost rather than closing the class -- say so in the comment rather than implying the class is closed. The test's positive control matters more than usual here: `installCopilotHooksFile(..., 'copilot')` writes the same file at the same path with a different owner, and that case is what makes the sidecar check independently discriminating rather than redundant with the ledger.

## The registry sweep cannot see anything the relay does before dispatch; that is where three pre-approval touches have now landed (2026-09-12)
`tests/vscode_pre_handler_path_gate.test.ts` populates itself from the live handler registry, so its population structurally excludes `relay.ts` and everything `relay.ts` calls before `runHook`. A bare `fs.existsSync` on a VS-Code-supplied `cwd` sat there, invisible to it. New guard `tests/guards/pre_handler_fs_touches_are_gated.test.ts` owns that half: it walks the call graph from `relayInProcess` to the first dispatch and reds any DIRECT `fs`/`net` call that is neither gated nor exempted-with-a-reason. Measurements from writing it, useful for anyone extending it: the pre-dispatch closure is ~45 functions, of which 11 touch fs, and all 11 turned out to be dataDir-scoped bookkeeping or generic path primitives -- a tractable exemption table, which is why the inverted default is affordable here. Two design decisions worth reusing: touches are DIRECT only, because propagating them transitively makes `relayInProcess` itself red and the guard useless (stated in the header as the known false-negative -- a payload path laundered through `ensureDirSync` slips past); and a leaf reader is classified when EVERY pre-dispatch caller is gated, non-transitively, which is what makes deleting the gate line from `userScopeCopyIsRedundant` turn `readCopilotHooksOwners` red without anyone remembering to also delete an exemption. Retroactive check on the three historical instances: only the third is in this population. #1 (`view_image` stat) and #2 (every VS Code pre hook stat, fixed 1c6368fd) both sat inside registered handlers, i.e. the other guard's half. The two populations partition the relay; neither alone would have caught all three.

## The fix for a UNC `cwd` is the existing gate, not a local regex (2026-09-12)
The narrow finding was "two lines: reject `/^[\/]{2}/` before the `existsSync`". Routing through `vscodePathAllowed(projectHooksDir, cwd)` instead is the same two lines and strictly better: it carries the UNC/device rejection AND the realpath containment, and -- load-bearing -- it makes the call site match the new guard's `isGated` predicate, so the guard enforces the fix rather than merely having motivated it. Use `vscodePathAllowed` and not `vscodePathDeclined` here: the latter returns false (allowed) unless the event carries a VS Code harness marker, so on a payload without one the UNC rejection would not run at all. A mutation-discriminating runtime test for this needs the two-separator path to be REAL, not just refused-by-shape: install through `\?\C:\...` on Windows / `//tmp/...` on POSIX so the sidecar and ledger both vouch for that exact spelling, and the gate is then the only thing between `false` and `true`.

## `realpathSync` throws on a missing leaf, so a try/catch fallback around it disables link resolution in the installer's ONLY case (2026-09-12)
Sequel to the containment entry above. `project.ts::isInsideRoot` wrapped `realpathSync` in try/catch and returned the canonicalized-but-unresolved path on throw. `realpathSync` throws ENOENT the moment ANY component is missing, so every path an installer is about to create fell back to a lexical prefix test -- containment was enforced only for files that already existed, i.e. never for a fresh install. A repo committing `.github` as a directory junction with NO leaf behind it made `install --vscode --project` exit 0 and write four files outside the project root; with the leaf present the same repo was correctly refused, and that asymmetry is exactly what the existing test covered (the working half). Fix shape, reusable for any "resolve then compare" boundary: walk up to the nearest EXISTING ancestor, realpath THAT, re-append the absent tail. Two non-obvious details found by running it: (a) the first missing segment can be a DANGLING symlink -- realpath refuses it but `readlink` answers exactly, so follow it by hand and repeat, bounded (40 hops) with a sentinel that fails containment in BOTH directions rather than a lexical fallback, since two "unresolvable" paths must not compare equal; (b) stop the ancestor walk when the remnant has no `/` left -- `realpathSync('c:')` SUCCEEDS on Windows and returns that drive's current directory, silently answering about somewhere else. Also: the docstring and CHANGELOG both asserted the coverage the code lacked ("a target that does not exist yet has no link to follow and compares lexically, which is the right answer") -- that sentence was the bug written down, reasoning about the leaf while the link sat on a parent.

## `COPYFILE_EXCL` closes a destination-symlink hole and opens a same-process collision; retry with a suffix, never drop the flag (2026-09-12)
`backupFile`'s `.bak.<ISO>` stamp has 1 ms resolution, and `installVscode` project-scope backs up the SAME instructions file twice in one process (`writeGuidance`, then `syncVisualStudioProjectGuidance` -> `upsertDelimitedBlock`) when a Visual Studio guidance block is present. Measured 4-6 ms apart over 20 fresh installs -- 0/20 failures, which bounds the rate at only ~15% and proves nothing about faster hardware. Unhandled EEXIST aborts the install. Retrying with a numeric suffix does NOT weaken the link defence: EXCL is set on every attempt, so an occupied name is stepped past rather than written through. Two testing notes: do not race this -- pin the clock (`vi.setSystemTime`) so both calls compute an identical stamp with certainty; and assert both backups' CONTENTS, since distinct names alone pass when the second is a duplicate of the first. For the real-binary dogfood, `node --require <preload>` patching `Date.prototype.toISOString` to a constant forces the collision deterministically through the shipped bundle -- pre-fix exits 1 with a raw EEXIST mid-install, post-fix writes `<stamp>` and `<stamp>-1`.

## A `pinnedPopulation` floor records a BELIEF, and nothing in the repo made that belief falsifiable until now (2026-09-12)
`pre_handler_fs_touches_are_gated` pinned floor 40 against a believed population of 45. The real closure was 112 -- the floor could have lost 72 members, 64% of the guard's subject matter, before firing. The arithmetic was fine; the belief behind it was never checked. `pinnedPopulation` now takes an optional `ceiling`, opt-in for populations whose size is a MEASUREMENT (a call-graph closure, a call-site set, an adapter registry) rather than a growing list. Deliberately not enforced as a slack RATIO: a probe across every pinned population in the repo found 28 of them more than 2x below their live count, nearly all legitimate file-count ratchets on a growing tree, so a ratio rule would have churned unrelated guards. Measure a floor by temporarily raising it to 9999 and reading the count out of the failure message -- that is the only reliable way here, and it is now written into the two guards' comments.

## `tests/guards/reachability.ts::parseTopLevelFunctions` was blind to arrow consts; it backs 11 guards (2026-09-12)
It matched only `function NAME(`. `const probeArrow = (q) => fs.existsSync(q)` injected into a real src file came back absent while `function probeFn` came back present. Latent (zero module-scope arrows in the pre-dispatch modules at the time) but it silently weakened every guard built on it. Widening it is cheap for arrows and NOT cheap for class methods -- telling a class body from an object literal is the hard part, and a method-shorthand pattern that cannot would sweep every `{ replace(x) {...} }` into these populations; stated as a limit in the docstring instead. Two parsing details worth reusing: find the assignment `=` by scanning at bracket depth and skipping any `=` followed by `>` or `=`, so a function-typed annotation's own `=>` (`const f: (a: number) => void = (a) => {...}`) is not mistaken for it; and break the scan at a depth-zero newline, since multi-line generic annotations keep their newlines inside `<...>`. Test the widening in BOTH directions -- a `const` that is not a function (`new Map<...>()`, an array literal, an object holding an arrow) must not be reported, or every population built on the helper silently pads with members no guard can act on. Injection can be in memory against the real file's bytes: the parser is a pure function of text, so that is the same evidence as an on-disk mutation and cannot leave a poisoned tree if the run is killed.

## A containment fixture built with `path.join` tests a path the function can never receive (2026-09-12)
`isInsideRoot('<root>/link/../sneak.txt', root)` had to be false with `link` a junction leaving the root. ## `tests/guards/test_bodies_assert_before_returning.test.ts` has an exemption list for test bodies and NONE for setup hooks (2026-09-12)

Write the hook as one `if (candidate !== null) { ... }` with no return, and in the bodies call `ctx.skip(...)` as a bare statement -- vitest's `ctx.skip()` THROWS, so no `return` is needed after it. That was verified rather than assumed (a probe with `ctx.skip()` ahead of `expect(true).toBe(false)` reports 1 skipped, 0 failed on vitest 4.1.11); if it ever stops throwing, the body fails loudly instead of passing silently, which is the right direction.
