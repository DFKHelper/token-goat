# Coder agent notes — token-goat

## Any edit to src/parser.ts (or src/languages/*) bumps PARSER_FINGERPRINT even for non-extraction changes, and the CHANGELOG needs a matching "upgrading reindexes" line (2026-09-08)
`scripts/parser-fingerprint.mjs::extractionSources` hashes the full text of `src/parser.ts` plus every file under `src/languages/`, not just the extraction logic inside them. Adding two pure diagnostic accessors (`treeSitterCoreAvailable`/`treeSitterCoreLoadError`/`setTreeSitterCoreForTesting`) to `src/parser.ts` for a `doctor` check made `tests/parser_fingerprint_gate.test.ts` fail even though no parsed output changed, because the gate hashes the whole file, not a semantic diff. Fix: run `npm run parser:fingerprint` to regenerate `src/parser_fingerprint.ts`, and add a CHANGELOG line ending "Upgrading reindexes: the parser fingerprint changed, so every file is reparsed once on the next worker drain." (exact phrasing already used at CHANGELOG.md, see the `[2.9.6]` entries) -- the gate's own failure message names this remedy verbatim. Anything needing a test-only override for an optional native dependency that `parser.ts` also loads (mirroring `ts_refs.ts`'s `setTsModuleForTesting` pattern) unavoidably touches this file and pays the fingerprint bump; there is no way around it short of moving the loader out of `parser.ts` entirely, which is a bigger change than the diagnostic itself.

## storeBashOutput always redacts on write; a fold comparing LIVE output against a stored body must guard the live side too (2026-09-08)
`bash_output_cache.ts::storeBashOutputSync` unconditionally runs `redactSecrets` before writing `entry.output`. Any function that later diffs/matches a fresh command's raw `output` against a previously-stored body (e.g. a served-lines elision) will see a REDACTED prior body next to a LIVE current one. A row containing a secret in the live output will never match the corresponding (redacted) row in the prior body, so it survives as an "unmatched" row and gets copied verbatim into a composed rewrite — a real leak the `rewritten_output_never_carries_a_secret.test.ts` guard catches. Fix: check `redactSecrets(output).count > 0` on the CURRENT output before ever composing a rewrite from it (mirrors the existing `foldShellReadBodies`/`foldShellReadStructure` pattern in `hooks_bash.ts`), and decline entirely rather than partially. Evidence: `maybeElideServedGenericOutput` in `src/hooks_bash.ts`, reproduced with a two-different-commands fixture (same-command fixtures can hide this because of the next entry).

## An identical rerun of the same command is a finding, not redundancy — don't let a new fold silently re-collapse it (2026-09-08)
`bash_identical_read_collapse.test.ts` pins that `maybeCollapseIdenticalRead` must NOT collapse two identical runs of a non-file-read command (e.g. `npm test` printing the same thing twice means the suite is still green; replacing that with a pointer deletes the answer). Any NEW cross-command elision mechanism keyed on a session-wide store (not per-file) will independently rediscover this exact pair and re-introduce the same collapse through a different door unless it explicitly excludes priors recorded under the SAME command (`getBashOutput(id)?.command !== cmd` filter before matching). This is easy to miss because the existing test's own repro happens to be a same-command rerun, so mutating away an unrelated guard (e.g. the redaction check above) can look "safe" against that one fixture purely because this filter already empties `priorIds` first — write a genuinely cross-command fixture to test each guard in isolation.

## `python3 -c "...open(path,'w')..."` on Windows silently converts the whole file to CRLF (2026-09-08)
Used a `python3 -c` one-liner to patch a single line in `src/hooks_bash.ts` via `open(path, 'r').read()` / `open(path, 'w').write(...)` (text mode, no explicit `newline=''`). Python's text-mode write on Windows translates every `\n` to `\r\n`, so a file that was pure LF came out entirely CRLF (3,358 conversions), caught only by `git diff`'s "CRLF will be replaced by LF" warning — `git diff --stat` alone still showed a small, plausible line count and did not flag it. Fix: re-read as bytes and `.replace(b'\r\n', b'\n')`, or just use the Edit tool for single-line changes instead of a Python rewrite (the earlier README rule against Python writes to `src/` is a stricter version of this same trap). Check `git diff` output for the CRLF warning after ANY out-of-band (non-Edit-tool) file rewrite on Windows.

## Retyping a `\u0000`-style escape from a token-goat-rendered source view can land a raw NUL byte instead of the escape text (2026-09-08)
Moving `GENERIC_SERVED_OUTPUT_KEY = '\u0000<bash-generic-served>'` from `hooks_bash.ts` to `session.ts`, an `Edit` `new_string` composed after viewing the constant via a `token-goat read` command landed a literal 0x00 byte in the new file instead of the six-character escape sequence `\`, `u`, `0`, `0`, `0`, `0` -- `grep`/`cat -n` then reported the file as binary. The tool's rendering of the real NUL character in the surrounding terminal output is visually indistinguishable from a space, so copying that visual slice into a new edit reproduces the raw byte, not the source text. Fixed with a small Node script that finds the raw `0x00` and replaces it with the literal ASCII string `\u0000` via `Buffer.from('\\u0000')` (double backslash in JS source to emit one literal backslash). Verify with a byte-level dump (`[...buf.slice(a,b)].map(b=>b.toString(16))`) after touching any line containing a control-character escape, rather than trusting `grep`/`cat -n`, both of which print a real NUL as blank/whitespace.

## A doubled-delimiter escape (`""` in F#/.NET verbatim strings, likely similar shapes elsewhere) is NOT independently mutation-discriminating against a naive "close on first delimiter" masker (2026-09-12)
Writing `fsharp.ts::endOfFSharpVerbatimString` (the `@"...""..."` `""`-escapes-a-literal-`"` rule), the obvious fixture -- one embedded `""` pair inside an otherwise-normal string, followed by a trailing real closer with nothing else between -- passed unchanged under a mutation that deleted the doubled-quote check entirely. Root cause: the two quote characters of a `""` pair are strictly adjacent, so a masker that (wrongly) closes the string at the first of the pair has its very next character be the second of the pair; the outer per-character masking loop then reopens a NEW string scan right there, which runs forward to the same real closer the correct implementation would have found directly. The two wrong sub-spans compose back to the exact same net masked range whenever there is nothing else (no stray quote, no odd count) between the pair and the real closer -- this is structural, not a fixture-quality accident, and will recur for any language whose "escape a delimiter by doubling it" rule you fixture the same way (SQL `''`, CSV `""`, Pascal string literals, etc.). Detected via this repo's own "mutate once, expect red" discipline -- the mutation went green, which is the signal to distrust the fixture, exactly as `ocaml_idx.test.ts`'s own precedent describes for its char-literal-with-equals tests. Fix used here: keep the doubled-delimiter fixture as an explicitly-labeled correctness/regression pin (not a mutation-discriminating test), and add a SEPARATE fixture for the actual discriminating case -- an escape character (backslash, in F#'s case) sitting directly adjacent to the real closer, which a naive "backslash escapes the next char" masker consumes together with that closer and then runs off looking for a wrong one (`@"C:\"` followed by a next-line definition it should not swallow). Check for this shape before trusting any "doubled/repeated delimiter" test as its own proof: does the wrong-close-then-reopen algebra actually change the net masked range for this exact fixture, or only cancel out?

## For a per-line single-match extractor (`ini_idx.ts`-style: one `BINDING_RE.exec()` per line), a mutation-discriminating fixture for masking bugs must put the fake definition on its OWN physical line (2026-09-12)
Writing `nix.ts::extractNix`'s mode-stack masker, a brace-depth-tracking test for `${ { a = 1; } }`-style nested interpolation (a `}` closing a nested record literal must decrement depth, not pop the whole interpolation frame) initially used a SINGLE-LINE fixture: `'quoted = "value: ${ { a = 1; } "fakeCloseTrap = 1;" }";'`. Mutating the `}` handler to always pop regardless of depth stayed GREEN -- not because the masking was actually still correct, but because `classifyLine`'s single `BINDING_RE.exec()` per line only ever extracts the FIRST match on a raw line, so `fakeCloseTrap` becoming live top-level code (due to the mutation) shared a line with `quoted` and was structurally invisible to the extractor regardless of the mutation's effect on masking. This generalizes the doubled-delimiter entry above: even a genuinely-different-net-masked-range mutation can fail to flip a test if the extractor's own per-line/per-match granularity discards the evidence before it reaches an assertion. Diagnosed by a temporary debug test (`console.log(extractNix(...))`, created and deleted) comparing correct vs. mutated output directly rather than trusting the assertion. Fix: rewrote the fixture across MULTIPLE PHYSICAL LINES (exploiting that a nested string can legally span raw newlines), putting `fakeCloseTrap = 1;` on its own line so a masking bug surfaces it as an independently-extractable symbol. Before trusting any mutation test against a line-oriented extractor, check not just whether the masked span differs under mutation, but whether that difference lands on a line/match slot the extractor actually samples.
