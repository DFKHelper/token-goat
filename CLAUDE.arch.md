# Architecture Reference

token-goat is a TypeScript CLI bundled to `dist/token-goat.mjs` via esbuild. The source lives in `src/*.ts`; tests under `tests/`. Build, test, and release tooling is npm-based (`npm install`, `npm test`, `npm run typecheck`, `npm run lint`). The canonical contributor guide lives in [AGENTS.md](AGENTS.md) — this file is the deeper architecture reference it complements.

**Indexer and Worker (Critical Path)**

| Module | Role |
|--------|------|
| [`src/fingerprint.ts`](src/fingerprint.ts) | `fingerprintFile()` — fast SHA-check used by `processDirtyBatch` to skip unchanged files |
| [`src/index_prune.ts`](src/index_prune.ts) | `pruneDeletedFiles()` deletes file/symbol/ref/chunk rows under a root prefix for paths no longer on disk (used by `token-goat index` and the worker sweep); `recordKnownRootThrottled()` (called from `postEditHandler`) upserts the edited file's project root into the `known_roots` table; `sweepKnownRoots()` prunes dead rows for reachable known roots, tombstones unreachable roots for `KNOWN_ROOT_MISSING_GRACE_MS` (7 days) before forgetting them, and flags rather than prunes a root where the deletion would remove an anomalous share of its rows |
| [`src/parser_fingerprint.ts`](src/parser_fingerprint.ts) | Exports: `PARSER_FINGERPRINT` |
| [`src/parser_refs.ts`](src/parser_refs.ts) | Call-site reference extraction via tree-sitter AST traversal. |
| [`src/parser_stamp.ts`](src/parser_stamp.ts) | Resolves the `files.parser_sha` stamp a row of a given language is expected to carry, from the generated digests in `parser_fingerprint.ts`. |
| [`src/parser_structured.ts`](src/parser_structured.ts) | Extractors for structured textual formats (Markdown, JSON, YAML, TOML, CSS, Dockerfile) and fallback regex symbol recovery. |
| [`src/parser_treesitter.ts`](src/parser_treesitter.ts) | Tree-sitter symbol extractors for typed and compiled languages (TS/JS, Python, Go, Rust, Ruby, Java, C/C++). |
| [`src/parser_ts_types.ts`](src/parser_ts_types.ts) | Minimal structural typings for the node-tree-sitter API surface we touch. |
| [`src/parser_types.ts`](src/parser_types.ts) | Shared types: `SymbolEntry`, `RefEntry`, `FileIndexEntry`, `Language` union (27 values plus `unknown`), `EXTENSION_LANGUAGE`, `FILENAME_LANGUAGE`, `detectLanguage()` |
| [`src/parser.ts`](src/parser.ts) | Tree-sitter orchestration and all symbol/ref/section extraction. Inline tree-sitter extractors for TypeScript/JavaScript, Python, Go, Rust, Ruby, Java, and C/C++; regex/pattern extractors (inline) for Markdown, JSON, YAML, TOML, CSS, and Dockerfile; regex adapters (from `src/languages/registry.ts`, reached through the dynamic `loadRegexExtractors()` so hooks never compile them) for C#, PHP, HTML, Liquid, Kotlin, GraphQL, SQL, INI, Makefile, Proto, and `.env`. Main entry points: `indexFileSync()` (sync, called by worker drain), `parseFile()` (async, calls `parseContent()` then `writeParseResult()`) |
| [`src/reconcile.ts`](src/reconcile.ts) | Catch-up reconciliation: detect index drift caused by edits token-goat never saw. |
| [`src/worker.ts`](src/worker.ts) | Dirty-queue consumer — `runWorkerLoop()` polls every `DEFAULT_POLL_INTERVAL_MS` (2000 ms); `drainOnce()` calls `processDirtyBatch()`, which SHA-checks each dirty file then calls `makeIndexer(dbPath)` (production default: `globalDbPath()`); can run as a Node.js Worker Thread or as a detached child process. Also runs periodic housekeeping in the same loop: snapshot cleanup and a daily `sweepKnownRoots()` pass (see `index_prune.ts`) that prunes dead file rows for known project roots |

## Data Flow

### (a) Initial indexing

`token-goat index [path]` calls `getTrackedFiles()` (via `git ls-files`) to enumerate files, then calls `indexFileSync(absPath, dbPath)` for each. `indexFileSync` in [`src/parser.ts`](src/parser.ts) calls `detectLanguage()` then `parseContent()` (tree-sitter or regex extractor) then `writeParseResult()`, which runs a single transaction: DELETE existing rows for the file, then INSERT new `files`, `symbols`, and `refs` rows. Embeddings are written separately by `embeddings.ts::upsertChunks()`.

### (b) Incremental updates (background worker)

1. Every `Write` or `Edit` tool event fires `postEditHandler()` in [`src/hooks_edit.ts`](src/hooks_edit.ts), which appends the normalized absolute path to `queue/dirty.txt` via `appendDirtyPath()` in [`src/hooks_index.ts`](src/hooks_index.ts).
2. The background worker (`worker.ts::runWorkerLoop`) polls `queue/dirty.txt` every **2 seconds** (`DEFAULT_POLL_INTERVAL_MS = 2000`).
3. `drainOnce()` reads the queue and calls `processDirtyBatch()`, which SHA-fingerprints each file (`fingerprintFile()`), skips unchanged files, and calls `makeIndexer(globalDbPath())(absPath, sha)` which resolves to `indexFileSync()`.
4. The worker runs either as a Node.js `Worker` thread (in-process, started by `startWorker()`) or as a detached child process with the `--worker-daemon` flag (`worker_daemon.ts::startDaemon()`).

### (c) Hook intercept

Installed hook events call the generated shim (`~/.claude/hooks/token-goat-shim.js`), which first tries the in-process path — importing `dist/token-goat-hook.mjs` and calling `relayInProcess()` directly — and falls back to spawning `token-goat hook <event>` only if that is unavailable. That bundle is built with esbuild code splitting, so it is a small entry plus sibling `dist/token-goat-chunk-*.mjs` files; anything that copies the hook library must copy the chunks with it. Those chunks are shared with `dist/token-goat.core.mjs`, because one `esbuild.build()` call emits both entry points — building them separately gave each its own private copy of nearly every chunk and doubled what `dist/` shipped (`tests/guards/dist_chunks_deduped.test.ts`). Splitting is what keeps the CLI surface, the MCP server and zod out of the bytes V8 parses on every hook — without it esbuild inlines a dynamically imported module into the entry, deferring its execution but not its parsing. Sharing chunks across the two entries does not undo that: a module the CLI reaches statically and the hook only dynamically still sits behind the hook's dynamic edge, and that same guard pins the hook's eager set. `tests/guards/hook_bundle_excludes_cli.test.ts` walks the esbuild metafile's static import graph and fails if the CLI becomes eagerly reachable again. `relay.ts::relay()` reads the JSON payload from stdin, calls `hooks_cli.ts::normalizePayload()` for tool-scoped events (translates Codex/Gemini tool name aliases to canonical names), dispatches via `hook_registry.ts::runHook()`, and serializes the result back to the harness wire format via `hook_registry.ts::serializeOutput()`.

Registered handlers by event:

- **PreToolUse / Read** — `preReadHandler` (session hint, diff-on-reread, large-file gate, surgical hint), `preReadImageHandler` (image shrink)
- **PreToolUse / Bash** — `preBashHandler` (cat detection, bash output dedup, compression)
- **PreToolUse / WebFetch** — `preFetchHandler` (image shrink for web content; on a repeat fetch of a URL already retrieved this session, a non-blocking recall hint pointing at `token-goat web-output <id>`)
- **PreToolUse / Skill** — `preSkillHandler` (skill cache dedup)
- **PostToolUse / Read** — `postReadHandler` (snapshot, session record)
- **PostToolUse / Edit, Write** — `postEditHandler` (dirty queue append)
- **PostToolUse / Bash** — `postBashHandler` (cache stdout/stderr)
- **PostToolUse / WebFetch** — `postFetchHandler` (web-output cache)
- **PostToolUse / Skill** — `postSkillHandler` (capture skill body to disk)
- **PreCompact** — `preCompactHandler` (build session manifest), `preCompactIndexHandler` (flush dirty queue)

### (d) CLI surgical reads

Commands such as `symbol`, `read`, `section`, `skeleton`, `outline`, `refs`, and `semantic` query `global.db` via `index_reader.ts` (`querySymbols()`, `queryRefs()`, `searchSymbolsFts()`) or `section_reader.ts` (`readSection()`). Every path argument passes through `resolveIndexPath()` before the DB query so the lookup key matches the write key byte-for-byte.

## Key Design Decisions

**Absolute-normalized index key (`resolveIndexPath`)** — Every symbol and file row is keyed by `normalizePath(path.resolve(base, file))` at write time. Every reader (`skeleton`, `outline`, `read`, `refs`, `imports`, `changed`) routes the user-supplied path through the same `resolveIndexPath()` helper in [`src/paths.ts`](src/paths.ts) before querying. Without this, a relative path (`src/worker.ts`), a backslash path (`src\worker.ts`), or a WSL mount path all produce a key that never matches an absolute forward-slashed lowercase-drive key and the query silently returns nothing. Routing every query site through this one helper guarantees the lookup key matches the write key byte-for-byte across platforms.

**Real-default-path wiring in the worker** — `processDirtyBatch` in [`src/worker.ts`](src/worker.ts) defaults the indexer to `makeIndexer(globalDbPath())`, which calls the real `indexFileSync` from `parser.ts`. A previous release shipped with the worker calling a stub callback, which meant nothing was ever written to the `symbols` table and the parser was tree-shaken out of the built bundle — yet the test suite was green because every worker test injected its own callback. See [AGENTS.md](AGENTS.md) for the full injected-seam trap analysis. Any change touching the worker or indexer must include an end-to-end test on the real default path (drain → index → `symbols` populated → a known symbol resolves) plus a smoke test against the built bundle.

**FTS5 query must name the virtual table directly** — `searchSymbolsFts()` in [`src/index_reader.ts`](src/index_reader.ts) references `symbols_fts` directly in the `FROM` clause and in `MATCH`/`bm25()`. An alias (e.g. `FROM symbols_fts f … WHERE f MATCH ?`) resolves as a bare column reference, raises `no such column: f`, and the catch block silently returns empty results — which is indistinguishable from a search miss. The correct form is `… FROM symbols_fts JOIN symbols s ON s.id = symbols_fts.rowid WHERE symbols_fts MATCH ? ORDER BY bm25(symbols_fts) LIMIT ?`.

**Refs via enclosing-scope resolution** — `extractRefs()` in [`src/parser.ts`](src/parser.ts) tracks the enclosing function/method/class during the tree walk and stores it in `refs.context`, enabling `refs --callers` to group usages by the containing symbol.

**Two-tier testing model** — A fast pre-commit guard tier (`npm run test:guards`, ~2 s, no bundle, no DB, no git fixtures) lives in `tests/guards/`. The pre-push/CI tier runs the full suite plus the built-bundle command matrix (`tests/command_matrix_e2e.*.test.ts`), which indexes a real fixture against `dist/token-goat.mjs` and runs every registered command. Both tiers derive their command set from [`tests/registry.ts::allCommandNames()`](tests/registry.ts), so a newly registered command is automatically in scope for both — there is no second list to maintain. A registered command with no matrix case fails the coverage gate by design. See [AGENTS.md](AGENTS.md) for the full two-tier description.

**Fail-soft hook handlers** — Every handler wrapped by `hooks_cli.ts::failSoft()` catches any exception, logs to stderr, and returns `{ continue: true }`. A broken token-goat must never interrupt the agent's work.

**Session persistence (cross-process)** — The installer wires each hook to the generated shim, so **every tool call still starts a fresh process** — the shim's in-process fast path avoids a *second* spawn, not the first, and there is no long-lived server. The session state in [`src/session.ts`](src/session.ts) (file-read/edit tracking, shown-hint dedup, and the web/bash/curl recall indexes) and the bash/web *content* caches are therefore meaningless if kept only in memory: the maps die when the hook process exits. Three on-disk layers under `tokenGoatHome()` (`TOKEN_GOAT_HOME`, else `~/.token-goat`, mirroring [`src/snapshots.ts`](src/snapshots.ts)) restore the behavior the Python original's `SessionCache` JSON provided:

- **Session state** — [`src/relay.ts`](src/relay.ts) calls `loadSessionState(sessionId)` immediately after building the event and `saveSessionState(sessionId)` after the handler returns, each in its own `try/catch` so a persistence failure can never suppress the handler's real output. Save is **merge-on-save**: it re-reads the on-disk JSON and unions it with the in-memory state (set-union for hints, field-wise for files keeping every read/edit/truncation signal, newest-wins for the indexes), then atomic-writes. Combined with the atomic rename, two overlapping same-session hook processes (e.g. background-task hooks) can at worst drop a hint — never corrupt the file. File entries are capped at 500 (oldest by last-read evicted). An empty `sessionId` skips persistence entirely (no shared `anon` file bleeding across sessions).
- **Bash/web content** — `storeBashOutput()` / `storeWebOutput()` also write a content-addressed blob (`bash_outputs/<id>.json`, `web_outputs/<id>.json`) via [`src/disk_cache.ts`](src/disk_cache.ts); `getBashOutput()` / `getWebOutput()` fall back to a disk read on an in-memory miss, so the session-less CLI (`token-goat bash-output <id>`, `web-output <id>`) and a later hook process resolve a value cached by an earlier one. Blobs are pruned by age (24h) and count (200) on each write.
- **Honest recall hints** — the three bash recall sites in [`src/hooks_bash.ts`](src/hooks_bash.ts) (monitoring, curl GET, build) guard on the *content entry* existing, not just the session index, so a pruned/evicted blob never yields a `bash-output <id>` hint that would error. `preFetchHandler` in [`src/hooks_fetch.ts`](src/hooks_fetch.ts) mirrors this for WebFetch: it resolves the URL via the persisted session index (`getWebFetchCacheId()`) and guards on the cached body (`getWebOutput()`) before emitting a `web-output <id>` recall hint, so the WebFetch cache is recalled in-band instead of silently re-fetched.

All three layers are fail-soft: a disk error never throws into a hook.

**Compaction assist** — Before Claude Code compacts, `preCompactHandler()` in [`src/hooks_compact.ts`](src/hooks_compact.ts) calls `compact.ts::buildManifest()` / `buildManifestAdaptive()` to build a structured, token-budgeted summary (edited files, files read, web fetches, skills) and returns it as `systemMessage`. The budget scales with session age and edit density via `computeAdaptiveBudget()`. Configurable via `config.toml` (`[compact_assist]`) or `TOKEN_GOAT_COMPACT_ASSIST=0`.

**Skill preservation** — `postSkillHandler()` in [`src/hooks_skill.ts`](src/hooks_skill.ts) captures every loaded skill body to `skills/` keyed by `(session, name, content_sha)`, enabling `token-goat skill-body <name>` recall after compaction without re-invoking the skill. `preSkillHandler()` reads the same store via `hasSessionOutput()`: if a body for the skill was already cached this session, the re-load is denied with a `skill-body <name> --compact` recall hint rather than re-injecting the whole body.

**Codex/Gemini compatibility** — `hooks_cli.ts::normalizePayload()` maps Codex tool-name aliases (`shell` to `Bash`) and Gemini aliases (`read_file` to `Read`, `write_file` to `Write`, and others) to canonical names before dispatching, using `CODEX_TOOL_NAME_MAP` and `GEMINI_TOOL_NAME_MAP`. The same `registerHook('pre_tool_use', handler, { toolName: 'Bash' })` registrations fire identically across harnesses.

**Bash output compression framework** — Build/test/tooling commands emit far more output than the agent needs (progress bars, ANSI, repeated lines, passing-test noise). The framework in [`src/tool_filters/`](src/tool_filters/) compresses that output structurally, per tool, before it reaches the model. The pre-bash hook recognizes a command, rewrites it to run through `token-goat compress -f <name> -c '<orig>'`, and the wrapped subprocess captures stdout/stderr, applies the matching filter, and re-emits a compressed view with a one-line savings marker. Layers:

- **`helpers.ts`** — the shared, dependency-free helper layer every filter builds on: normalisation (`normalise` = CRLF→LF + ANSI strip + progress-line collapse), `safeDecode`/`sanitizeControlChars`, run-collapsing (`dedupeConsecutive`, `dedupeNumericRuns` with a high-entropy bypass so UUID/hash/JWT lines are never merged), error-preserving truncation (`truncateMiddleSmart`), byte/token caps (`capBytes`, `capTokens`), and command parsing (`shlexSplit`, `stripPrefixes` resolving `sudo`/`env`/`python -m`/`uv run`/`npx`-style launchers). Family factories and bespoke filters compose these rather than re-implementing them — the DRY foundation that keeps the ported filters small.
- **`base.ts`** — `CompressedOutput` (the result type: text + byte accounting + `withMarker()`) and the abstract `ToolFilter` with the universal 10-step `apply()` pipeline (sanitise → per-stream input cap → normalise → early-exit when normalisation alone suffices → structural `compress()` → line cap → byte cap → notes prepend). Subclasses declare `binaries`/`subcommands` and override `compressBody`; `errorPassthrough` short-circuits to raw combined output on a non-zero exit with stderr; a `postNormalise` hook lets the git family strip CRLF warnings without per-family checks in `apply`.
- **`generic.ts`** — `GenericFilter`, the catch-all the hook selects when it wraps a command no per-tool filter matches: ANSI/progress strip + consecutive-line dedupe, capped at ~2000 tokens.
- **`families.ts`** — filter *family factories*: shared compression skeletons that several per-tool filters configure instead of reimplementing. `makeNodeTestRunnerFilter(cfg)` powers the Node test-runner batch. `makePackageManagerFilter(cfg)` is the package-manager factory — a single line-walk loop (keep if ERROR_SIGNAL_RE, keep if `keepRe` matches, drop by ordered `DropRule` array, emit per-rule collapsed notes) used by BundlerFilter and PubFilter; filters with richer structural logic (npm/pip/uv/conda/gem/composer/nuget/conan/vcpkg) subclass `ToolFilter` directly. Both factories are concurrency-safe (all state is per-call with no shared mutable fields).

- **Hook wiring (`hooks_bash.ts`)** — `preBashHandler` makes the rewrite decision: for a recognized single command with no cached prior run it returns a `rewriteInput` HookOutput, which [`hook_registry.ts::serializeOutput`](src/hook_registry.ts) emits as the `PreToolUse` wire shape `{hookSpecificOutput:{hookEventName:"PreToolUse",permissionDecision:"allow",updatedInput}}`. `updatedInput` replaces the *entire* `tool_input`, so the hook spreads `{...event.toolInput, command: wrapped}` to keep `description`/`timeout`. Filter selection runs on the cd-*stripped* command (`detectFromCommand`, falling back to the `generic` filter for commands no registered filter matches — per-tool filters land in batches, batches A through J now registered), but the wrapper quotes the *full* original command including any `cd … &&` prefix so it still runs in the right cwd. A cached prior run wins over a fresh rewrite (recall is cheaper than re-running and re-compressing). Because the rewrite changes the command the post-hook then sees, `postBashHandler` unwraps `token-goat compress … -c <orig>` back to `<orig>` before keying its output cache — so recall stays keyed on the original command and round-trips across runs. Compounds, pipes, and redirects are never wrapped (`isCompressibleSingleCommand` mirrors `detectFromCommand`'s single-command rule). Honored opt-outs: `TOKEN_GOAT_BASH_COMPRESS=0` and per-filter `[bash_compress] disabled_filters`.

Disable globally with `TOKEN_GOAT_BASH_COMPRESS=0`. The framework is independent of the `src/filters.ts` line-level `Filter`/`FILTERS` (a separate, simpler post-read line filter) — this one is keyed `ToolFilter`/`TOOL_FILTERS` to avoid the name collision.

**Agent-report envelope compaction never summarizes PROSE, and never will** (`hooks_agent_spawn.ts`) — `postAgentHandler` only touches bytes *inside fenced code blocks* (`collapseFencedBlocks` elision, `dedupeFencedBlocks` cross-fence dedup, `collapseBlankRunsInFences` blank-run collapse); every non-fence line is byte-identical between input and output, enforced as an executable invariant in `tests/hooks_agent_spawn.test.ts`. LLM or extractive summarization of the PROSE portion of a subagent's report was explicitly proposed and rejected during design, for three reasons that are load-bearing, not stylistic preferences: (1) **non-deterministic** — a summarizer can silently drop or reword content differently each run, so the same report could compact two different ways with no way to predict which; (2) **unverifiable** — nothing downstream can prove a summary faithfully preserved what the original said, unlike a byte-identical passthrough or a mechanically reproducible elision (fenced content is regenerable from the repo, and the full original stays one `mcp-output <id> --full` away); (3) **destroys the caveat signal the envelope exists to preserve** — prose is exactly where a subagent writes "I did not verify X" or "not tested," and those sentences are what has caught a subagent shipping something it never checked, three cycles running in this repo's own history. A summarizer optimizing for length has no way to know which sentence is the load-bearing caveat and which is filler, so it is not a safe reduction, it is a coin flip on whether the one sentence that matters survives. If this gets re-proposed: the answer is still no, for the same three reasons, and the fenced-block-only design is what makes the "cite evidence, state unverified claims explicitly" report contract in the subagent briefing (`buildSubagentBriefing`) trustworthy in the first place — summarizing the prose that contract asks for would defeat the contract itself.
**Path-key naming in `--json` rows** — A row's path key is `filePath` when the row carries an explicit type-signal field (`kind`, `source`). It is `<type>File` only when the path key *is* the row's sole type discriminator. Worked example: `test-for --json` rows are `{testFile, testFunctions}` with no `kind` field, so the key itself is the only thing saying what kind of file this is — hence `testFile`, not `filePath`. By contrast `callers --json` rows are `{caller, kind, file, line}` and `dead --json` rows are `{name, kind, file, line}`; both already carry `kind`, so the generic `file` key is safe there and a `<type>File` spelling would be redundant. Apply the rule when adding a new row shape rather than copying whichever neighbour was read most recently.

## Adding a New Language

Every language is one row of `LANGUAGE_SPECS` in [`src/language_specs.ts`](src/language_specs.ts). The row's `id` joins the `Language` union, and its columns feed every place that keys on a language: `detectLanguage` (`extensions`, `basenames`, `exactBasenames`), the read hook's diff and source hints (`diffable`, `sourceHints`), the grep hook's hint (`grepSource`), the bash hook's `symbol`/`read` suggestions (`symbolBearing`), `pack`'s code fence (`fence`, `fenceByExtension`), the display name in ref-blind messages (`label`), the `imports` fallback for basename-only files (`basenameImportsExtension`), and the notice for languages whose references are only partly recorded (`partialRefsReason`). The module imports nothing, so any file can depend on it.

The `extraction` column says how symbols are found:

- `tree-sitter`: inline in `src/parser.ts` (TypeScript/JavaScript, Python, Go, Rust, Ruby, Java, C/C++). These need a `tree-sitter-<lang>` npm package, a grammar branch in `loadGrammar()` and a branch in `parseContent()`.
- `regex`: a `SymbolExtractor` in `ADAPTER_EXTRACTORS` in `src/languages/registry.ts`. That map is typed `Record<RegexLanguage, SymbolExtractor>`, so a `regex` row with no extractor fails `npm run typecheck`.
- `own-result`: the language returns its own `ParseContentResult` (symbols plus refs) from a `language === '<id>'` branch in `src/parser.ts` (Vue, Svelte, Astro, Salesforce markup, COBOL, Natural, notebooks). `tests/language_specs.test.ts` fails when a row has no branch.

Prefer a separate file in `src/languages/` for a new extractor. Use `src/languages/kotlin.ts` as a template for class/function extraction, or `src/languages/ini_idx.ts` for flat key-value formats.

Steps:

1. **Add the row** to `LANGUAGE_SPECS`. Spread `CODE` for a programming language or `DATA` for a config format and override single flags. A new extension on an existing language is just an `extensions` entry. `.h` stays C by path: telling C++ headers apart needs file contents. An extension two languages share is settled by content in `CONTENT_SNIFFS` (`src/parser_types.ts`), which is how a `.h` with `@interface` becomes Objective-C.
2. **Write the extractor**: create `src/languages/{lang}.ts` exporting `extractXxx(content: string, filePath: string)`. Use `makeSymbolEmitter` from `src/languages/common.ts` to deduplicate symbols, and export the function from [`src/languages/index.ts`](src/languages/index.ts).
3. **Wire it in**: add the extractor to `ADAPTER_EXTRACTORS` in `src/languages/registry.ts` (a `regex` row), or add the `language === '<id>'` branch (an `own-result` row).
4. **Only if needed, outside the table**: an `extractImports` branch in `src/read_commands.ts` when the import statement is not caught by the generic `import|require|use|#include` fallback, and `CSTYLE_EXTS`/`HASH_COMMENT_EXTS` in `src/pack.ts` when the language uses `//` or `#` comments. An extension shared with another language (`.cls` is Apex, VB6, and LaTeX) cannot be told apart by `detectLanguage`, which is path-only: add a content check to `refineLanguageByContent` in `parser_types.ts`, which `indexFileSync`, `parseFile` and `section_reader.ts` apply after reading the file. Every such check must be a POSITIVE test for the language it routes TO (a marker only that language writes), never a negative test for the default language it routes FROM -- a negative test silently misclaims any third language nobody wrote a check for yet, which is exactly how a LaTeX `.cls` (which has no VB6 or ABL marker) was misclaimed as Apex before this note was added. A consumer holding only a path calls `detectLanguageOfFile`, which reads the head of an ambiguous file and refines it the same way. A language whose call sites the indexer records also needs `REF_LANGUAGES` in `src/parser.ts` and its mirror in `src/ref_blindness.ts`.
5. **Update the pinned lists**: `tests/language_specs.test.ts` compares every derived list with the list it replaced, so a new row shows up there as a named difference to add, and the non-tree-sitter count in `docs/C4_RUNTIME_ARCHITECTURE.md` has to match `nonTreeSitterLanguageCount()`.
6. **Regenerate the parser fingerprint**: `npm run parser:fingerprint` rewrites `src/parser_fingerprint.ts`; `tests/parser_fingerprint_gate.test.ts` fails until you do. The changelog entry must say that upgrading reindexes.
7. **Add tests on the real path**: a `CASES` entry in `tests/guards/language_adapter_produces_symbols.test.ts` (it fails for any table row without one) with a fixture in `tests/fixtures/language_adapter_symbols/` that carries a provenance line, `detectLanguage` assertions in `tests/parser_types.test.ts`, and a built-bundle check: either a case in [`tests/helpers/matrix_cases.ts`](tests/helpers/matrix_cases.ts) (the four `tests/command_matrix_e2e.N.test.ts` shards each run an interleaved quarter of that table) or a standalone test that spawns `dist/token-goat.mjs`, as `tests/vb_bundle_e2e.test.ts` does.

## Adding a New Hook Event

1. **Add the event name** to `HOOK_EVENTS` in [`src/types.ts`](src/types.ts). TypeScript will enforce that every switch on `HookEventName` handles the new value.
2. **Implement the handler** in the appropriate `src/hooks_*.ts` module. Return a `HookOutput` value (`passOutput()`, `contextOutput(text)`, `denyOutput(msg)`).
3. **Register the handler** at module level:
   ```ts
   registerHook('your_event', yourHandler)
   ```
   Module-level registration runs when the module is imported on `token-goat hook <event>`.
4. **Wire into install** if the event needs to be added to `settings.json`: add a `['YourEvent', 'your_event']` entry to `HOOK_EVENT_MAP` in [`src/install.ts`](src/install.ts) and re-run `token-goat install`.
5. **Test** — add a unit test for the handler, and a hook integration test if the event fires in a hook subprocess context.

## Adding a New Command

1. **Implement the logic** — if the command reads from the index, add a `runXxx(opts: XxxOptions): number` function to [`src/read_commands.ts`](src/read_commands.ts). Otherwise implement directly in a new or existing module.
2. **Write a `cmd*` handler** in [`src/cli.ts`](src/cli.ts):
   ```ts
   function cmdXxx(opts: XxxOptions): number {
     return runXxx(opts)
   }
   ```
3. **Register in `buildProgram()`** — call `program.command('xxx').description('...').option(...)...action(guard(cmdXxx))`. The guard in [`tests/guards/cli_registration.test.ts`](tests/guards/cli_registration.test.ts) checks that every `cmd*` function appears in an `.action(...)` call and that every command in `allCommandNames()` appears in `--help` output — it will fail immediately if the handler is declared but not wired.
4. **Add a matrix case** — add an entry to the shared case table in [`tests/helpers/matrix_cases.ts`](tests/helpers/matrix_cases.ts), which the four `tests/command_matrix_e2e.N.test.ts` shards each run an interleaved quarter of. The coverage gate in [`tests/command_matrix_e2e.1.test.ts`](tests/command_matrix_e2e.1.test.ts) fails automatically if a registered command has no case, using [`tests/registry.ts::allCommandNames()`](tests/registry.ts) as the single source of truth shared with the guard.


## Security Boundaries

Ten invariants, each established by a real defect that shipped. A change that touches any of them needs a test that fails when the invariant is removed, not just a green suite.

**Every path that persists bytes goes through `redactSecrets`, and it must run before any truncation, not merely before the write.** `storeBlob()` in [`src/disk_cache.ts`](src/disk_cache.ts) is the funnel for the JSON-envelope caches (bash-output, web-output, mcp-output), and it is fail-safe: a throwing regex does not write raw bytes. `src/skill_cache.ts`'s `storeOutput`/`storeCompact` persist skill bodies and compact slices as plain `.txt` files rather than through `storeBlob()`'s JSON envelope, so they call `redactSecrets` directly at their own write sites, with the same fail-safe shape (a throw propagates to the function's own outer try/catch, which returns without writing anything). Presence of a `redactSecrets` call on a path is not sufficient on its own: `redactSecrets`'s patterns carry a minimum-match-length floor, so a truncator (a `.slice()`, a line-width clip, a middle-cut, a byte cap) that runs *before* redaction can cut a credential's matched span short enough that the pattern no longer recognises what's left, and the fragment ships raw even though the path technically "goes through redactSecrets" downstream. Three sites shipped this exact defect before it was named as its own class: `mcp_cache.ts::mcpInputPreview` (truncated `JSON.stringify(toolInput)` to 120 chars before the caller redacted it), `tool_filters/base.ts::apply()` (redaction ran last, after four separate truncators had already clipped the body), and `mcp_compress_packs.ts::truncateSnapshotLine` via `hooks_mcp.ts::postMcpHandler` (compression, which truncates per-field, ran on raw `resultText` instead of the already-redacted text). All three fixes moved redaction to the boundary the path crosses — right after the raw bytes enter the function, before the first truncator — rather than reordering just that one call site, so a truncator added upstream later cannot reintroduce the class. A fourth, differently-shaped defect hit the same model-facing surface without any truncator being involved: `tool_filters/dispatch.ts::deliverCompressed` — documented in its own comment as "the single definition of what the model actually receives for this command" — computed a correctly-redacted `compressed.text`, then discarded it whenever `compressed.worthApplying(minNet)` (the net-benefit/byte-savings floor) returned false, falling back to the RAW pre-redaction `combineStreams(stdout, stderr)`. The net-benefit gate exists to decide whether *compression* is worth shipping, and shipping the redacted-but-uncompressed original instead is always safe; discarding *redaction* along with compression on that same gate is not a truncation-ordering bug (nothing was cut short here) but the same family of mistake — a value computed correctly upstream gets thrown away by a branch that was only ever supposed to arbitrate a different tradeoff. The invariant this generalizes to: a net-benefit or worth-applying gate may only ever discard the compression it is gating, never the redaction that ran ahead of it. `tests/guards/truncators_are_classified.test.ts` and `tests/guards/session_state_fields_are_redaction_classified.test.ts` turn both halves of this invariant into a structural pre-commit check: every truncation/shortening-shaped function in `src/` must carry an explicit classification (redacted-before-truncating, downstream of an already-redacted input, or otherwise verified safe) or the guard fails, and every field of `SerializedSession` must carry an explicit redaction-coverage classification or the guard fails — so a fifth truncator or a sixth session-state field starts red until someone consciously classifies it, rather than silently inheriting whatever the surrounding code happened to do. The per-session state file, written directly by [`src/session_store.ts`](src/session_store.ts) rather than through `storeBlob()`, has the same shape of gap: adding a new field to `SerializedSession` used to mean redaction depended entirely on that field's author remembering to call `redactSecrets` at its own construction site in [`src/session.ts`](src/session.ts) — `outstandingAgentSpawns` shipped without it, persisting a raw prompt (and any credential pasted into it) verbatim. The fix is two-layered: the field's own writer (`recordOutstandingAgentSpawn`) now redacts at push time, and `saveSessionState` additionally sweeps the fully-serialized JSON through `redactSecrets` once, immediately before the only `atomicWriteText` call that ever writes this file — a defense-in-depth backstop so a *future* field that ships without its author remembering redaction is still covered, rather than relying on that memory a second time. Redaction is a pattern matcher, not a classifier: adding a pattern is cheap, and a credential shape with no distinctive prefix (presigned urls were the last one found) needs an anchor plus a length floor so a generic parameter name stays safe to key on. Persisting redacted is not the same guarantee as *showing* the model redacted text this turn: `postMcpHandler` in [`src/hooks_mcp.ts`](src/hooks_mcp.ts) redacts its compression branch's rewrite, and `postWebSearchHandler`/`postFetchHandler` in [`src/hooks_websearch.ts`](src/hooks_websearch.ts)/[`src/hooks_fetch.ts`](src/hooks_fetch.ts) now redact on every live-rewrite path (computed once, ahead of every early-return caching guard, the same ordering discipline the injection scan below already enforces) — closing the gap where a credential that tripped no injection pattern reached the model unredacted even though the cached copy on disk was clean.

**The line that matters is `rewriteOutput`, not the hook.** A `pass` result is the harness's own tool output, which token-goat neither authored nor can alter; redacting there would be a different feature (suppressing what the model would see regardless), not a leak fix. What must always hold is that text token-goat *substitutes* for a tool result is clean. `postAgentHandler` in [`src/hooks_agent_spawn.ts`](src/hooks_agent_spawn.ts) violated exactly this: it cached the subagent report through `storeMcpOutput` (which redacts) and, on the next line, built its compacted replacement from the same raw string. Redact where the value *enters* the handler, never on the branch that happens to emit — the entry point is the only place a future branch inherits it for free. [`tests/guards/rewritten_output_never_carries_a_secret.test.ts`](tests/guards/rewritten_output_never_carries_a_secret.test.ts) enforces this by firing every registered `post_tool_use` handler and reading what it emits, with the population taken from the registry rather than a list. It is behavioral, not static, for a measured reason: a static "reaches a rewrite must reach the redactor" rule flags `hooks_bash.ts`, whose compression rewrite is redacted inside `compressOutput()` in another module — invisible to same-file call analysis, and silenceable only with the kind of hand-maintained list these guards exist to eliminate.

**A redaction is not a key.** Two inputs differing only inside the redacted span collapse to one entry. Use a digest when the consumer is an exact-match check with a denying effect; use a redaction only when the value is displayed and must stay readable; use both when it is displayed *and* compared, with the readable fields first so display code that reads only the leading field keeps working. Changing a persisted key shape means migrating the old shape at `coerce()` in [`src/session_store.ts`](src/session_store.ts), the single boundary every disk read passes through, including the fresh re-read the save path performs. Skipping the migration does not fail anything: the lookup just misses, the work is silently redone, and the old credential stays on disk for the life of the session.

**A rewrite may carry back only the bytes no string can stand in for.** `postMcpHandler`'s rewrite emits a block array: the redacted, fenced words in one text block, then the image, audio and blob blocks copied verbatim out of the server's own payload. Those copies are a second route to the model running beside the fenced one, so `isTextualContentBlock` in [`src/hooks_common.ts`](src/hooks_common.ts) drops every block that holds words -- text, an EmbeddedResource with `text`, a ResourceLink -- and their content travels in the fenced block instead, the link's `name` and `uri` included so dropping the block loses nothing. Preserving one of them verbatim would hand the model an unredacted, unfenced copy of the exact text the block beside it marks as untrusted. [`tests/guards/a_preserved_block_never_carries_the_servers_words.test.ts`](tests/guards/a_preserved_block_never_carries_the_servers_words.test.ts) drives the live hook over one result holding every block type in the MCP union and asserts both halves: nothing textual survives, and nothing textual is lost. A sixth block type added to that union is the case this is written to catch.

**The injection scan runs before every early return, never after.** `postMcpHandler` in [`src/hooks_mcp.ts`](src/hooks_mcp.ts) computes the scan and a `passOrFence()` closure before the first guard. Three caching guards (error response, missing session id, dedup hit) each used to return above the scan, so a hostile server could flag its own reply as an error, or simply be called twice, and get an unfenced payload through. A guard that exists to save work must never double as a way around a security control. The same rule applies to any new guard added to a hook that fences or redacts.

**Untrusted content is fenced by provenance, not by heuristic.** Every surface fences unconditionally: the scan decides whether the notice names the patterns it matched, never whether the fence appears. Eight sites each restated that rule and each got it wrong the same way (`if (matches.length === 0) return text`), so the decision now lives in one module, [`src/untrusted_fence.ts`](src/untrusted_fence.ts) -- `fenceUntrusted` for a printed block, `fenceWithMatches` where a hook already scanned, `scanAndRecord` for the stat. The one legitimate gate is `injection.enabled = false`, which is explicit user configuration rather than a detector, and it switches off the whole subsystem including the fence. The fence tags in [`src/injection_scan.ts`](src/injection_scan.ts) are per-surface (`UNTRUSTED_WEB_TAG`, `UNTRUSTED_TOOL_TAG`, `UNTRUSTED_FILE_TAG`, `UNTRUSTED_GITHUB_TAG`) so escaping one does not escape another. `neutralizeFenceMarkers` has to match as loosely as an HTML parser reads: case-insensitive, whitespace anywhere inside the tag, junk attributes, and a slash before the closing bracket. Every spelling that reads as a closing tag but is not escaped is a way out of the fence. Cached Bash and MCP output recalled later is third-party text exactly as a fetched page is: `bash-output` and `mcp-output` fence on recall, `web-output` too. So is `recall` (unified search over those same three caches — its no-query browse mode returns a raw excerpt with no scan skipped even when nothing matched a search term), `gdrive-sections` (a Google Doc, fetched over HTTP like a WebFetch page, same `UNTRUSTED_WEB_TAG`), and `pr-slice` (a GitHub PR's title/description/comments/diff, under its own `UNTRUSTED_GITHUB_TAG` since it is neither a page token-goat fetched itself nor a recall of a prior tool call). `_applyFiltersAndPrint` in `src/cli.ts` still defaults its `fenceByProvenance` parameter to `false`, because it also prints the caller's own files; nothing makes that default safe by itself, and every third-party caller passes `true`. A structural guard, [`tests/guards/third_party_content_reaches_fence.test.ts`](tests/guards/third_party_content_reaches_fence.test.ts), parses every function in `src/` and fails when one reaches a named third-party content source (`fetchPrFiles`/`fetchPrDiff`/`fetchPrComments`/`fetchPrDescription`, `fetchDoc`/`getSectionContent`/`getDocSections`, `searchRecall`/`listRecentRecall`) without also reaching a fence terminal (`fenceUntrustedContent`, `fenceUntrusted`, `fenceWithMatches`, `fenceUntrustedOcrText`) or `_applyFiltersAndPrint(..., true, ...)`, transitively through same-file calls, **and** fails when a function that does reach one can still skip it via a zero-match early return — so a new command reusing one of those functions is caught the turn it is written, with nobody needing to remember a checklist. A wholly new fetch primitive that bypasses every name in that list is the one gap the guard discloses in its own header comment; it needs a human to add the new entry point, the same way a newly-lock-worthy config setting needs a human decision in `project_config_lock_coverage.test.ts`'s allowlist. A local file is third-party content too when the caller only *named* it rather than authored it: `pdf-extract`, `pdf-locate`, `pdf-outline`, `docx-text`, `docx-outline`, `pptx-outline`, `pptx-slide`, `pptx-notes`, `pptx-text`, and `xlsx-sheets`/`xlsx-head`/`xlsx-range`/`xlsx-query` in [`src/cli.ts`](src/cli.ts) all fence their extracted text under `UNTRUSTED_FILE_TAG` whatever it says. `--json` is the single documented exception, and it is a wire-format constraint rather than a judgement call: a fence wrapped around JSON is no longer JSON, so those envelopes fence individual fields on a pattern match only, while the printed form of the same command is always fenced. Each exception is named in `CONDITIONAL_FENCE_EXCEPTIONS` in the guard with its reason, and the guard also fails on a stale entry, so an exception that stops being conditional cannot sit there licensing a gap that no longer exists. This family used to be left **out** of `THIRD_PARTY_SOURCE_CALLS` above, on the reasoning that its entry points are also called by [`src/doc_embed_extract.ts`](src/doc_embed_extract.ts) to feed the embeddings/chunking pipeline rather than to print, so listing them would flag that file. That left thirteen document commands outside the guard's view entirely while it reported green. All thirteen are now listed, named by the local alias each is imported under in `cli.ts` (`runPdfExtractText`, `docxText`, `pptxOutline`, `xlsxHeadSheet`, ...), and the false positive is handled where it belongs: a module that *defines* one of these functions, `doc_embed_extract.ts` included, is exempt from the check, so an internal consumer no longer costs the emit paths their coverage. Behavioral coverage for the family stays in [`tests/cli_doc_extract_fencing.test.ts`](tests/cli_doc_extract_fencing.test.ts), which asserts the actual fenced output per command, the same proof strategy the guard's header comment already prescribes for `bash-output`/`web-output`/`mcp-output`.

**The three emit channels are not equally defended, so "which one does this reach" is a real question.** `denyOutput` neutralizes its payload and adds its `[tg]` prefix outside the neutralized region; `emitRewrite` is the boundary the substitution guard walks; `contextOutput` does neither, and its callers carry their own `[token-goat]` prefix inside the payload, which is why it cannot simply be made to neutralize without moving that prefix out at all 54 call sites. The consequence is not hypothetical: adding `<cwd>/.claude/agents` as a scan root in 2.9.7 made the unrestricted-spawn advisory's names repository-authored, and they reached the model through `contextOutput` in token-goat's own voice with nothing between. The fix constrains the name's shape at the parser rather than fencing the notice, because the notice is ours and a fence around it would escape our own prefix. Two further things this cost, both worth carrying: the substitution guard's population is `emitRewrite`/`emitRewriteIfChanged` only, and widening it to `contextOutput` surfaces 11 functions that have never been adjudicated; and `postAgentHandler` was already exempt for a *different* body, so a function-keyed exemption silently covered a second block its written reason never mentioned.

Enumerating the rest of that channel found four more instances of the same shape, which is the reason this paragraph exists rather than a note on one commit. The compaction manifest's web-fetch row was the one row of that manifest not routed through `displaySafeText`. `buildDeltaCapsule` in [`src/evidence_cache.ts`](src/evidence_cache.ts) listed the paths whose cached evidence had gone stale, and those paths come from whatever files a Read touched, so in a cloned repository the repository chooses them. `repeatFailureNotice` in [`src/hooks_tool_failure.ts`](src/hooks_tool_failure.ts) named the tool that failed twice, and an MCP server chooses the names it advertises. In every case the helper already existed and the call site simply did not use it, while its siblings all did. The lesson to carry is the enumeration, not any single fix: when something lands on this channel, walk every other function that reaches it and ask what each one interpolates, because two of these four came from that walk and from no report.

Walking it by hand is not enough, which is the second half of the lesson and the more useful one. The hand-walk described above found two sites; `tests/guards/context_channel_population_is_adjudicated.test.ts` then found nine more, one of them a live defect in the manifest re-read hint. That guard cannot decide whether an interpolation is safe, because whether `'... ' + x + ' ...'` is safe depends on where `x` came from. What it can do is pin who is on the channel and refuse to pass until each function carries a one-line adjudication of what it interpolates, which is the part a person keeps skipping. Its entries are prose and prose cannot fail, so every entry that promises a specific mechanism is paired with a direct assertion that the call still exists.

Three of the eleven candidates that sweep produced turned out to be unreachable, and all three had looked live from the emitting line alone: the Grep hint's extractor refuses any path containing a bracket, `safeSkillName` refuses any skill name outside `[A-Za-z0-9_:-]`, and the snapshot-diff messages leave on the deny channel, which already neutralizes. Read the callers before pricing a site. Getting it wrong costs in both directions: assume live and you publish a security note for a hole that was already closed, assume safe and you ship the hole. Two hints sitting two lines apart in [`src/hooks_read.ts`](src/hooks_read.ts) went opposite ways for this reason: the tsconfig one is gated to fixed filenames, the manifest one matches by extension and so quotes an arbitrary repository-chosen name. The escaping stays on the unreachable sites as the layer that survives those gates being relaxed, since each exists for filename-safety or globbing rather than for injection, and each is now pinned by a test carrying a positive control so a gate that quietly stopped gating fails rather than goes silent.

**Decision, 2026-09-04: Bash output token-goat does not substitute stays unfenced, and undefused.** Recorded here because the reasoning is a measurement, and prose nobody can re-run is how a reachability claim rots. Three numbers, all taken on this machine over the 30 days to 2026-09-04. Volume: 173,739 Bash calls, of which token-goat compresses 3,172, so a fence on every result taxes 98.2% of calls that it changes nothing about, roughly 5.4M tokens a month against 468M saved. Benefit: on a build log impersonating a token-goat truncation notice, a model complied 11 times in 12 unfenced and 6 in 12 fenced, so the fence buys a halving, not a stop. Alternative: escaping the forged prefix reached 1 in 12, on the 0.19% of results (440 of 227,437) carrying a marker-shaped line at all -- strictly better protection for effectively no tokens.

That alternative was built and then withdrawn, which is the part worth keeping. Escaping on the pass-through path fires on any output containing the literal `[token-goat`, and that includes token-goat's own source, its docs, and its changelog: `cat src/tool_filters/node_test_runners.ts` came back with escaped brackets, and a model round-tripping that text writes `&#91;` into the file. The suite caught it, in `tests/read_served_output_producer.test.ts`, as four negative assertions flipping to `rewriteOutput`. A defence whose failure mode is corrupting the files it is defending is not worth a speculative gain on a path where token-goat is not speaking. So the escape lives where the substitution does, inside `fenceUntrustedContent`, and the pass-through paths are exempt from both. Reopen this if the marker prefix ever appears in the model's system prompt or documentation as something to trust, since that is the premise the whole trade rests on.

**Where the fence is available, and where it is not.** [`tests/guards/substituted_output_reaches_fence.test.ts`](tests/guards/substituted_output_reaches_fence.test.ts) walks every function reaching `emitRewrite`, and the eight it found split cleanly in two. Where token-goat's text sits at one end of the body -- the `BashOutput` and `TaskOutput` poll deltas, and the compound-Bash rewrite before them -- the notice goes above the opening tag and the fence covers the rest, which is the shape to copy. Where our markers are spliced *between* the bytes they replaced, there is no such cut: fencing the whole body would run the marker neutraliser over token-goat's own markers and hand the model `&#91;token-goat: 40 lines elided]`. The Bash elisions are no longer in that position. [`fenceUntrustedSpans`](src/untrusted_fence.ts) takes the body already split into spans, each marked with whether token-goat wrote it, and runs the neutraliser on the others and on nothing else. Authorship is positional, declared by the producer that emitted the span, rather than recognised from the text: a rule that spotted our markers by their spelling would exempt a forged one just as readily. Both `hooks_bash.ts` elision sites fence through it, and the fence is priced before the net-benefit gate rather than after, so the gate cannot decline a rewrite for the cost of its own protection. Three remain open: the agent-report compaction, the already-served Read elision, and the browser block join. What keeps them open is the round-trip risk rather than the missing mechanism, since an untrusted span containing the literal `[token-goat` comes back escaped and those three feed the surfaces most likely to be copied into a file. Reopen them when there is a way to escape a span that a model cannot round-trip into an edit, or when a marker-shaped line is measured arriving on one of the three rather than assumed.

**Egress has one choke point and one switch.** Every HTTP request token-goat makes itself goes through `performHttpFetch` in [`src/webfetch.ts`](src/webfetch.ts), redirects included, so the offline check lives there rather than at each command. Three paths bypass it because a third-party library does the download: the embedding model ([`src/embed_model.ts`](src/embed_model.ts), huggingface.co), the OCR language data (`tesseract.js`, cdn.jsdelivr.net), and `screenshot`'s browser navigation. Each has its own guard, and each preserves a warm cache rather than refusing outright. A new dependency that downloads something at runtime is a fourth, and needs the same treatment plus a line in the README's outbound list.

**A per-project config file is untrusted input.** `.token-goat.toml` arrives with the repository, so it is written by whoever wrote the repository. `PROJECT_LOCKED_SECTIONS` and `PROJECT_LOCKED_KEYS` in [`src/config.ts`](src/config.ts) name what it may not set: the `injection`, `webfetch`, `gdrive`, `mcp` and `network` sections, plus `indexing.cross_project_symbols`. A new setting that turns a protection off, narrows an allowlist, or widens a confinement belongs in that list. The environment is deliberately not locked: a repository cannot set it, and a developer exporting a variable is configuring their own machine.

**Containment compares resolved paths, and asks the platform about case.** `isInsideRoot` in [`src/project.ts`](src/project.ts) is the shared helper. `canonicalize` deliberately does not call realpath, so lexical containment alone is not containment: a directory symlink inside a root pointing out of it satisfies a prefix test while naming a confined-away file. Case folding goes through `foldPath`/`isCaseInsensitiveFs`, never a hand-rolled `process.platform === 'win32'` check, which wrongly rejects legitimate paths on a case-insensitive macOS volume. The trailing-separator guard is what stops `/srv/project-secrets` reading as inside `/srv/project`.

**The security scan is in two halves, and the split is deliberate.** Eighty-odd guards in `tests/guards/` each encode a defect somebody already found, which leaves the classes nobody has looked at uncovered. The two files that close that are keyed on shape rather than on a bug. [`tests/guards/dangerous_sinks_are_named.test.ts`](tests/guards/dangerous_sinks_are_named.test.ts) runs in `npm test` and answers *where are the sinks*: `eval`, `new Function`, `node:vm` and string-form `child_process.exec` are asserted absent with no exemption map, and every `shell: true` and `execSync` site has to be named with the reason it cannot be an argv array. It is text-structural on purpose -- [`tests/guards/typescript_compiler_api_available.test.ts`](tests/guards/typescript_compiler_api_available.test.ts) documents what happens when a guard couples to the compiler API, and this one has no need of it. The other half, *does untrusted data reach a sink*, needs interprocedural dataflow and lives in [`.github/workflows/codeql.yml`](.github/workflows/codeql.yml), because no engine that answers it is fast, offline and cross-platform enough for a suite that also runs on Windows and macOS. [`tests/guards/codeql_scan_is_wired.test.ts`](tests/guards/codeql_scan_is_wired.test.ts) holds that job to the extended query suite, a schedule, and a `paths-ignore` that does not cover `src` -- each of which fails silently, leaving a green check and an empty alerts tab that reads as a clean bill of health.

`eslint-plugin-security` was measured before the hand-rolled guard was written, and rejected on the numbers: 1,691 findings across 177 of 255 source files on 2026-09-04. Three rules are 96% of that and none is usable here. `detect-unsafe-regex` (260) is the star-height heuristic, strictly weaker than the automaton analysis `eslint-plugin-regexp`'s `no-super-linear-backtracking` already runs in `npm run lint`. `detect-non-literal-fs-filename` (511) flags reading a file whose name came from a variable, which is the product. `detect-object-injection` (848) flags every computed index including `arr[i]`, and the four `detect-possible-timing-attacks` hits are name matches -- a lock-file token compare, a variable called `auth` holding a hostname -- against a product with no secret-comparison surface. Worth recording rather than quietly not adopting: `detect-object-injection` is the rule that would have flagged the `copilot_cli.ts` prototype-key defect below, so the instinct to reach for it is right and only the granularity is wrong. A suppression file with 1,691 entries is worse than no rule, because it reads as a decision. Reconsider if the plugin gains sink-awareness, or enable single rules scoped to a directory where their false-positive shape does not apply.

**Every bridge shim builds a shell command string, and what goes into it must be a closed set.** Each bridge installs a generated hook shim whose last resort is `spawnSync('token-goat hook ' + event, { shell: true })`. The `shell: true` cannot come off: a global npm install puts a `.cmd` shim on PATH on Windows, and `spawnSync` cannot exec that without a shell. So the property that has to hold is on the value, not the call. Audited by surface on 2026-09-04, the seven concatenation sites split three ways. Four -- [`claudecode.ts`](src/bridges/claudecode.ts), [`codex.ts`](src/bridges/codex.ts), [`grok.ts`](src/bridges/grok.ts), [`kimi.ts`](src/bridges/kimi.ts) -- test the name against a closed `Set` before interpolating, which is the shape to copy. Two -- [`relay_block.ts`](src/bridges/relay_block.ts), used by `opencode` and `openclaw`, and [`pi.ts`](src/bridges/pi.ts) -- validate nothing, and are safe only because every one of their call sites passes a string literal; that is a property of today's callers, not of the code. The seventh, [`copilot_cli.ts`](src/bridges/copilot_cli.ts), read `process.argv[2]` into a plain object literal and gated on the result being truthy. A plain object answers that lookup for the eight members of `Object.prototype`, so `constructor`, `__proto__`, `toString` and five more resolved to a `Function`, were stringified into the command, and reached a shell. Measured, not inferred: with the check reverted, a recording `token-goat` on PATH runs for all eight, and does not for a name that is merely unknown. No member of `Object.prototype` stringifies with a shell metacharacter, so the outcome was a failed spawn rather than a second command -- the defect is argv reaching a shell string through a gate that reads like it stops it, not a payload. It now uses `Object.prototype.hasOwnProperty.call`. [`tests/guards/shell_concat_is_constrained.test.ts`](tests/guards/shell_concat_is_constrained.test.ts) holds all three shapes: a shim reading from argv must carry one of the constraints named in `CONSTRAINTS`, and the two literal-only shims are checked at both hops -- every call site passes a literal, and the delegation that actually builds the string passes through only the parameter the first check constrains. A bare `MAP[key]` is deliberately not a member of `CONSTRAINTS`.

Outside the bridges, `shell: true` appears twice more and neither is this shape. [`src/bash_runner.ts`](src/bash_runner.ts) is the product running the user's own command. [`src/cli_doctor.ts`](src/cli_doctor.ts) spawns the Copilot hook command the user configured, which is their own file and is documented as such in place.

**Decompression is bounded on the output side, not just the input side.** `MAX_ZIP_INPUT_BYTES` and `MAX_ZIP_OUTPUT_BYTES` live once in [`src/zip_bounds.ts`](src/zip_bounds.ts), and every archive read goes through `unzipBounded`. The OOXML reader used to cap only `stat.size`, the compressed size, which bounds nothing: DEFLATE's worst case is about 1032:1, so a compliant 50MB input expands toward tens of gigabytes. `zip-list` and `zip-read` capped neither side. Two checks are needed and neither is redundant. The declared uncompressed size in the central directory is attacker-controlled, so gating on it alone is defeated by an archive that understates it; a running total of bytes actually produced, checked as the stream is pushed in chunks, catches that case regardless of what the entry claimed. The declared-size check is still worth keeping because it rejects an honestly-labeled bomb before any decompression starts. Note what fflate does on its own: `unzipSync` pre-allocates the output buffer to exactly the declared size and never grows it, so memory is already bounded and an understated size truncates silently rather than overallocating. It is CPU that is unbounded, because the full bitstream is decoded either way, and that is what the streaming abort actually buys. Driving fflate's low-level `Unzip` directly loses the end-of-central-directory validation `unzipSync` performs, so `unzipBounded` calls `unzipSync` with a filter that never matches purely to keep the malformed-archive throw.

**An image decoder sizes every buffer from a number the attacker wrote, so the header check is not the bound.** `image_shrink.max_image_pixels` (16 MP by default) used to be sharp's `limitInputPixels`, which libvips enforced *inside* the decode. Since the move to the pure-TypeScript engine it is a check on the header's `width * height`, run in [`probeImageMeta`](src/image_shrink.ts) before token-goat's own decoders, and it sees nothing else -- not the frame count, not how far a compressed stream expands. Three separate bombs went straight through it, all measured on this engine on 2026-09-04: an 11.5 KB GIF declaring a 1600x1600 canvas and 500 frames allocated 5.1 GB, because every frame is a full canvas and all are retained at once, and 1600x1600 is 2.56 MP so the gate passed with 84% of its budget unused; a 510 KB PNG declaring 4000x4000 -- exactly 16 MP, so exactly at the gate -- inflated its IDAT to 512 MB where 61 MB was needed, and 512 MB was the number chosen for the test file rather than a limit the code imposed. `MAX_DECODED_BYTES` in [`src/image_engine.ts`](src/image_engine.ts) is the actual bound, 256 MB, checked before each allocation rather than after; it is deliberately not configurable, and setting `max_image_pixels` to `0` does not lift it. The PNG inflate gets an exact bound rather than a round one: a non-interlaced image's zlib stream is precisely one filter byte plus one row of samples per scanline, so `maxOutputLength` is that figure and anything beyond it is by definition not data the image needs.

**A decoder that cannot handle a format must refuse it, not decode it into a different picture.** The same engine accepted PNG bit depths 1, 2, 4 and 16 and Adam7 interlacing, then ran all of them through a row loop that assumes 8-bit progressive; an opaque red 16-bit pixel came back as `[255, 255, 0, 0]`, a transparent yellow. BMP accepted every bit depth but only had pixel-loop branches for 24 and 32, so an 8-bit file returned the zero-filled buffer -- a fully transparent image, reported as success. Both are worse than the allocation bugs above despite looking milder, because the failure is silent and the wrong pixels are what `shrinkImage` re-encodes and hands to the model *as the contents of the file*. Refusing costs nothing: the throw is caught and the untouched original is passed through, which is the correct picture. The rule for this engine is that an unsupported header field is an error, never a default.

**A read-side ceiling is not a write-side ceiling, and peak memory is their sum.** `MAX_DECODED_BYTES` in [`image_engine.ts`](src/image_engine.ts) bounded the frames a GIF decode allocates at four bytes per pixel per frame. The animated branch of [`shrinkImage`](src/image_shrink.ts) then allocates its own output buffer at *five*, from the same frame count, so a 1600x1600 animation between 22 and 26 frames passed the decode bound and exceeded the ceiling on the way out -- and the process held both at once. The shrink path now runs the same `assertDecodableSize` over the buffer it is about to write, which is why that helper is exported rather than private to the decoders. Verified against the installed build on 2026-09-04: 21 frames shrinks (1,029 KB to 78 KB, 759 ms), 22 frames is declined. When one module states a memory ceiling, every allocation shaped by the same attacker-controlled count has to be measured against it, including the ones in other files.

**Decoding a whole animation to use one frame of it is a bound you did not take.** The still-image branch of `shrinkImage` read `decodeGif(input).frames[0]`, paying a full canvas for every frame it discarded. `decodeGif` takes a `maxFrames` option and that site passes 1. A caller that wants a prefix should say so, because the ceiling is then priced on what is actually decoded rather than on what the file claims.

**Following an offset a file supplies needs a record of where it has already been.** A TIFF's pages are a linked list, each IFD carrying the offset of the next, and nothing in the format forbids that offset pointing at an IFD already visited. `probeBufferMeta` followed it without one: measured, a 64-byte TIFF whose only IFD pointed at itself never returned. It allocates nothing, so it is never OOM-killed -- it holds the thread, and because this runs in a pre-read hook that is an agent whose `Read` never comes back. A synchronous loop like this also cannot be interrupted by a test timeout, which is worth knowing before writing the regression test: the proof that it was broken is that the suite itself hung.

**A budget that bounds memory does not bound work, and a size measured on a name is not the size of the file you read.** `MAX_PDF_TEXT_BYTES`, `MAX_PDF_TEXT_ITEMS`, `MAX_PDF_INPUT_BYTES` and `MAX_PDF_WORK_MILLIS` live once in [`src/pdf_extract.ts`](src/pdf_extract.ts), and every entry point that reads page text opens one `pdfWorkDeadline()` per document. Four things need bounding here and none of them substitutes for another. Text: a content stream's expansion ratio is whatever its author chose, and the measured fixture is 160 KB on disk, 35 million characters of text, 740 MB resident. Items: a budget counted in characters lets a page of a million one-character items sit inside 8 MB while costing hundreds of megabytes to hold, since every item is an object. Encoding: that budget counts UTF-16 code units under a name stated in bytes, and accented or CJK text encodes to two or three times as much, so the finished document is measured with `Buffer.byteLength` before it is returned. Time: pdfjs cannot be stopped part-way through a page -- cancelling the stream closes the web-stream controller while pdfjs still believes its own is open, so the next in-flight chunk throws from inside its message handler as an uncaught exception, and abandoning the reader without cancelling deadlocks `loadingTask.destroy()` -- so refusing frees the memory and leaves the producer running, and the clock is the only thing that ends it. The file read is part of the same invariant: `readPdfFileWithinBounds` opens one descriptor and takes the type, the size and the bytes off that one handle, because a stat and a read are two lookups of one name and the file can grow or be swapped between them, and anything that is not a regular file is refused outright since a FIFO or a character device reports a size of zero and zero passes any ceiling. Where the clock is READ is part of the bound and not a detail of it: a check written in the loop that consumes text items is not reached by a page that produces none, so the clock sits on the awaits that produce, not on the loops that consume: the chunk read, the whole-page fallback, `getPageWithinDeadline` (through which every command walks pages), and the outline and metadata fetches, each of which materialises its whole structure before any cap is consulted. A refusal thrown mid-stream also has to be able to leave, so teardown races `PDF_TEARDOWN_MILLIS`. Bounds on what is retained in the ANSWER are a fifth class beside the four above: `MAX_OUTLINE_ENTRIES`, `MAX_OUTLINE_TITLE_CHARS`, `MAX_LOCATE_MATCHES` and `MAX_LOCATE_CONTEXT_CHARS`, and a snippet is measured against `--context` rather than against however much the caller's pattern chose to match. Finally, `DocumentRefusedError` in [`src/document_refusal.ts`](src/document_refusal.ts) is the one type the indexer asks about when deciding whether a document is worth opening again: a per-format check is a check the next format is added without, which is how the OOXML size refusals spent their whole decompression on every index pass.

## Known Limitations

- **Post-compaction skill re-injection is Claude Code's own native behavior, not something token-goat's `pre_compact` hooks control.** When the harness compacts a conversation, Claude Code itself decides which skills get reloaded into the fresh context — token-goat only gets to shape the manifest text injected alongside that compaction (see [hooks_compact.ts](src/hooks_compact.ts) and [hooks_index.ts](src/hooks_index.ts)), it cannot prevent or filter which skill bodies the harness chooses to re-inject. The load-time gate in [hooks_skill.ts](src/hooks_skill.ts) (deny + redirect to `skill-body --compact` on a same-session repeat `Skill` tool call) is the closest available enforcement point, since it operates on the actual tool call rather than trying to intercept harness-internal re-injection.

- **A default (user-scope) VS Code install goes silently inert for every workspace root but the first, in a multi-root workspace.** `vscodePathAllowed`/`preToolPathDeclined` ([vscode_path_gate.ts](src/vscode_path_gate.ts)) confine a hook's pre-approval stat/read to `getCwd(event)`, the `cwd` VS Code's own hook payload carries. SOURCED (not dogfooded — no live multi-root capture was taken) from the installed VS Code 1.137.0 bundle, `resources/app/out/vs/workbench/workbench.desktop.main.js`, `PromptsService.computeHooks`: for every hook file `w` it discovers, it computes `l = this.workspaceService.getWorkspace().folders[0]` once per hook-list refresh, then `H = (this.workspaceService.getWorkspaceFolder(w.uri) ?? l)?.uri` and passes `H` as the default `cwd` for any hook definition in that file with no `cwd` of its own — which is every hook token-goat installs (`copilot_cli_install.ts` never writes a `cwd` key). Default `install --vscode` (no `--project`) writes to the user-scope hooks directory (`~/.copilot/hooks`, [vscode_install.ts](src/bridges/vscode_install.ts)'s `vscodeHooksDir`), which sits under the home directory and is therefore never inside *any* workspace folder — so `getWorkspaceFolder(w.uri)` is undefined for it regardless of how many roots are open, and `H` collapses to `folders[0]` for the whole session. In a single-root workspace `folders[0]` is the only root, so this is unobservable there. In a multi-root workspace it means every hook invocation gets `cwd = folders[0]`'s path even when the tool call concerns a file in `folders[1..n]`: `vscodePathAllowed` then correctly reports those files as outside the (wrong) root, and `vscodePathDeclined` makes every pre-approval handler (`hooks_read.ts`, `hooks_write.ts`, `image_shrink.ts`) `passOutput()` on them. This fails closed, not open — no path outside the intended root is ever stat'd or read, so the security boundary itself holds — but it silently disables token-goat's read-hint, image-shrink, and edit-interception hooks for every non-first root for the life of the session. A project-scope install (`install --vscode --project`, one `.github/hooks` per root) is not affected, because each root's own hooks file resolves `getWorkspaceFolder(w.uri)` to that same root correctly. No fix is shipped here: the miscomputation is inside VS Code's own bundle, token-goat only reads whatever `cwd` it is handed, and the only lever available (steering multi-root users toward a per-root project-scope install) is a documentation change beyond this note's scope, not a code change to the confinement gate itself.
